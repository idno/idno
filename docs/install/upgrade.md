# Upgrading Idno

Upgrading Idno is designed to be simple: back up, replace the files, and load your site. This page
tells you what to expect, in the order you need it. The first part is for site owners; the last
part is for developers of plugins and themes.

If your site runs on **MongoDB**, it cannot start on this version: Idno 2.0 no longer runs on
MongoDB. The site shows a page that says so (and every command but `idno:import:mongo` and
`idno:upgrade` prints the same line; `idno:upgrade` exits with an error), and nothing is changed. Move
its data to MySQL, MariaDB or SQLite first, as "Moving a MongoDB site" describes, then follow the rest
of this page for the new database.

## Before you start

1. **Check your server.** Idno 2.0 needs PHP 8.4 or later, and MySQL 8.0 or later or MariaDB 10.6
   or later (see [System requirements](requirements.md)). On an older database server the site shows
   a page saying so and changes nothing.
2. **Check your version.** A site older than Idno 1.6.4 must be upgraded to Idno 1.6.4 first (and
   loaded once in a browser), then to this version. If you skip that step, the site tells you and
   changes nothing.
3. **Back up** the database and your Idno directory (including your upload directory and
   `configuration/config.ini`). The upgrade keeps your old data (see "What happens to your data"), but
   a backup is the only way back from anything else going wrong.
4. **Stop every Idno process that runs the old code**: the event queue worker
   (`service-event-queue`), the cron service, and anything else that runs Idno from the command line
   or on a schedule. Do this before you replace the files. Two reasons:
    * anything those processes write while the upgrade runs is not carried over to the new database;
    * an old process running after the upgrade has renamed the old tables creates some of them again.
      While the upgrade is still checking its copy, that stops it with a message until it is sorted
      out (see "If the upgrade stops"); once the upgrade has finished, the site ignores those tables,
      and whatever the old process writes into them is lost.

    You start them again, with the new code, once the upgrade is finished.

## How to upgrade

1. Replace your Idno files with the new release, **except** your upload directory and your
   `configuration/config.ini` file. (If you use a checkout from GitHub, run `composer install`.)
2. Load any page of your site in a browser.

While the database is not up to date, every page of the site shows an upgrade page instead of the
site, to everyone. For a 1.x site it says "Idno is upgrading its database" and shows how far the
copy of each part of your site has got (posts and people, the feed reader, site records, settings),
for example `1500 of 12000 copied`. On a large site this takes several minutes. The page does the
work in short steps and reloads your site by itself when it is done.

* You can close the page and open it again later: the upgrade carries on from where it stopped.
  It only moves on while the page is open in a browser somewhere (or while the command below runs).
* Feeds, the API and other programs that ask the site for something get a short "Idno is upgrading
  its database." answer until it is done.
* You need no shell access. If you have one, you can instead run, from your Idno directory:

  ```
  php bin/console idno:upgrade
  ```

  It does the whole upgrade in one run, printing what it does, and does nothing when the database is
  up to date. `php bin/console idno:upgrade --status` shows where the upgrade stands without changing
  anything. Run it as the user your web server runs as (for example `sudo -u www-data php bin/console
  idno:upgrade`): it creates cache directories under `var/` (and, on SQLite, a lock file beside the
  database) that the web server must be able to write to afterwards. If the database cannot be
  reached, the command prints Idno's database error page and stops, as every command does.
* If the page says **"The old tables are in use by something else, such as a database backup or an
  old Idno process, so they cannot be renamed yet."**, the copy is done and the upgrade is waiting to
  rename the old tables, which something else is reading or writing (a nightly backup that is still
  running, or an Idno process you have not stopped). Nothing is wrong: the upgrade goes on by itself
  when that has finished. If it does not, stop the old Idno processes. (`idno:upgrade` waits up to a
  minute, then stops with the same sentence; run it again later.)

A new installation, and any later release that changes the database, shows the same page for a few
seconds ("Idno is setting up its database", "Idno is updating its database").

## What happens to your data

* **Nothing is deleted.** Idno copies your 1.x data into new tables (`idno_entities`, `idno_settings`
  and others). When the copy is done, it renames all your old tables at once, adding `legacy_` in
  front of their names (`entities` becomes `legacy_entities`), checks the copy against them, and then
  opens the site. Nothing in the old tables is changed. They stay until you delete them (see
  "Afterwards").
* **Rows that cannot be carried over are kept and listed.** A row of the old database that the new
  one cannot hold is not copied. It is kept, with its full contents, in the table
  `idno_upgrade_rejects` (which is never deleted), and listed with its reason on the admin page
  "Legacy tables" (see "Afterwards"). The page shows how many there are while it runs (`3 not
  carried over`). The reasons you may see:
    * *contents are not valid UTF-8*, *contents are not valid JSON*, *contents are not a JSON object
      or array*: the stored record was damaged before the upgrade (it could not have been read by
      Idno 1.x either).
    * *contents are nested deeper than 512 levels*: the record is nested more deeply than PHP can
      read.
    * *the database refused the document: ...*: the database server will not store it. The most
      likely case is a record nested more deeply than the server allows: MariaDB accepts JSON nested
      at most 31 levels deep (MySQL 100). Another is a record whose `access` value is longer than
      255 characters.
    * *its uuid equals that of the copied record ...*: two records whose addresses differ only in a
      way the new database treats as equal. The new database compares text the way the last 1.x
      versions compared post contents: ignoring capital letters, accents and trailing spaces, and
      treating `ß` as `ss`. So `…/straße` and `…/strasse` are now the same address. The first one
      copied is kept; the other is listed here.
    * *its _id ... is that of the copied record ...*: two records with the same internal id.
    * A row that had no search text in the old database (its row in the `_search` table was missing)
      is copied with empty search text: it is not found by the site's search until it is saved again
      (edit and save the post).
    * *superseded configuration*: an older copy of your site's settings. Idno 1.x could keep several;
      the newest became your settings. This one is normal and needs nothing from you.
    * *cannot be the settings: ...*: a settings record that the new settings table cannot hold.
    * *the database refused the settings: ...*: the database server would not store the newest
      settings record (for example a value it cannot hold). The next-newest usable record becomes your
      settings instead; if none can, the site starts with empty settings, and you set them again on
      the admin pages.

## Afterwards

* **Everyone logs in again.** Logged-in sessions are not carried over.
* **Set the site's `url`, if your site uses the queue.** The worker never guesses the site's address: it refuses to start unless `configuration/config.ini` has `url = "https://your.domain/"` (the way to do it: every console command reads it; `IDNO_URL=https://your.domain/` in the environment works too, for each command that needs it). A site made by the installer has no `url` there: the address was worked out from each request. The worker has no request, and the address with its scheme is part of what it signs and sends to other servers, so it must be the address visitors use, `https` for a site served over TLS.
* **Start your queue worker again**, with the new code (for example
  `php bin/console service-event-queue`; see the README). The first time the queue worker starts it
  moves any events the old queue left waiting into the new queue (it says so, and says if one could not
  be moved: such a record, including one whose data holds an object of a class that no longer exists, is
  left where it is). It also removes the old queue's completed records (a few hundred each time it
  starts; nothing reads them any more).
* **Plugin indexes.** Plugins can ask for database indexes on fields they look up often. The upgrade
  page creates Idno's own indexes, not the plugins'. A plugin's indexes are created when you enable
  the plugin on the admin Plugins page, or for every enabled plugin when you run
  `php bin/console idno:upgrade` once. Without a shell, disable and enable each plugin again. Until
  then some plugin pages may be slower on a large site. They show the same content with and without
  the indexes as long as the plugin's records hold a single value in each field it declares, which is
  what declaring an index promises; a record that holds a list in such a field (a plugin that broke
  that promise) is found by the plugin's lookups only until the index exists.
* **Review what was not carried over.** Site administrators see a "Legacy tables" entry in the
  admin menu while there are legacy tables or rows that were not carried over. The page
  (`/admin/legacytables/`) lists the old tables with their row counts, and every row that was not
  carried over with its address and its reason. Their full contents are in the table
  `idno_upgrade_rejects`, which you can read with your database tool (phpMyAdmin, for example).
* **Deleting the old tables.** When you are sure the upgrade went well, delete the `legacy_` tables
  to free the space they take: on the "Legacy tables" admin page, type `delete` in the box and press
  "Delete the legacy tables". With a shell, `php bin/console idno:upgrade --drop-legacy` lists them
  with their row counts, and `php bin/console idno:upgrade --drop-legacy --yes` deletes them. (The
  row counts are the database's own estimates, so they are approximate.) Only
  the renamed 1.x tables are deleted; the rows that were not carried over (`idno_upgrade_rejects`)
  are kept. **This cannot be undone**: once they are deleted, the only way back to Idno 1.x is your
  backup. If the page or the command stops part-way, run it again to finish. If it says that a table
  outside the Idno 1.x tables refers to a legacy table, run again cannot help: a table of an old
  plugin, say, has a foreign key into one of them. The server's error log (or the command) names that
  table; remove it, or its foreign key, first. Idno also refuses to delete anything while the old
  1.x tables are back beside the upgraded site (see "If the upgrade stops").
* **Tables created by an old Idno process.** If an old Idno process was still running after the
  upgrade, it may have created some tables with the old names again (`reader`, `versions`,
  `entities_metadata`, `entities_search`, `site`, `site_metadata`, `site_search`). The site
  never reads them, and the "Legacy tables" page lists them under "Tables created by an old Idno
  process". Stop that process; then remove those tables with your database tool if you wish. Idno
  does not delete them for you. The one exception: if the table `entities` is back as well, so that
  `entities`, `entities_metadata` and `entities_search` are all there, an old Idno process did not make
  them (it never creates `entities`); Idno takes it that the 1.x site was restored, and closes the
  site with the message described under "If the upgrade stops".

## If the upgrade stops

The upgrade page says why it stopped, in one of the messages below. It never shows the technical
details to visitors: those are in the server's error log, and `php bin/console idno:upgrade --status`
prints them (on a `Detail:` line). After you have dealt with the cause, load the page again (or run
`php bin/console idno:upgrade`): the upgrade carries on from where it stopped.

* **"The upgrade stopped. The details are in the server's error log, and php bin/console idno:upgrade
  --status shows them."** Something failed that may involve your content or the server's settings.
  Common causes, each named in the details: a record too large for the memory PHP may use (raise
  `memory_limit`), a record too large for one database statement (raise the database server's
  `max_allowed_packet`), or a database error.
* **"This site's database is from a version of Idno older than 1.6.4 ..."** Upgrade the site to
  Idno 1.6.4 first and load it once in a browser, then install this version again. Nothing was
  changed.
* **"Idno needs MySQL 8.0 or later, or MariaDB 10.6 or later. This database server is ..."** The
  database server is too old. Upgrade it, or move the database to one that is new enough, then load
  the page again. Nothing was changed.
* **"The database cannot be reached right now. The upgrade carries on once it can be."** The
  database server is down or refusing connections (too many at once, for example). It usually passes
  by itself; if it does not, check the server and the settings in `configuration/config.ini`.
* **"The tables of an Idno 1.x site exist under their renamed names ... but no upgrade is on
  record."** The renamed `legacy_` tables are there but the new tables that record the upgrade are
  not (someone deleted them to start again, for example). Nothing was changed. To upgrade that site,
  rename the tables back with the statement under "Undoing the upgrade", then load the page again. To
  set up a new, empty site instead, remove the `legacy_` tables.
* **"This database holds a site already upgraded to this version of Idno and, again, the tables of
  an Idno 1.x site ..."** The upgrade finished once, and then the tables `entities`,
  `entities_metadata` and `entities_search` came back: the upgrade was undone (the tables renamed
  back), or a backup of the 1.x database was restored into the same database. Idno will not choose
  for you, because opening the upgraded site would hide everything written to the 1.x site since,
  and nothing was changed. Choose one:
    * **to upgrade the 1.x site again** (the usual case after going back to 1.x for a while): remove
      ALL the tables whose names begin with `idno_`, then load the page again. If you miss one that
      holds rows, the upgrade does not start and says which (the message "The 1.x tables cannot be
      copied: ... already hold data"); remove it too. The upgrade starts afresh
      from the 1.x tables. **Back up the database first**: removing the `idno_` tables throws away
      everything written to the upgraded site since its upgrade (posts, comments, likes, users'
      changes, settings). If the earlier upgrade's `legacy_` tables are still there as well (you
      restored a backup of the 1.x tables rather than renaming the `legacy_` ones back), the new
      upgrade does not start, because the `legacy_` names the 1.x tables would be renamed to are
      taken (the message "The 1.x tables cannot be renamed"; nothing is copied). Those `legacy_` tables are the earlier
      upgrade's copy of the old site. Once you are sure the restored 1.x tables are the data you want,
      move the old `legacy_` set out of the way with your database tool, for example by renaming it
      (`RENAME TABLE legacy_entities TO earlier_entities, legacy_entities_metadata TO
      earlier_entities_metadata, ...`, one pair for each `legacy_` table there) or by deleting it. The
      admin page cannot do this (the site is closed), and `php bin/console idno:upgrade --drop-legacy`
      refuses too: it deletes nothing while both copies are there, and, once the `idno_` tables are
      gone, nothing while no finished upgrade is on record;
    * **to keep the upgraded site** (the 1.x tables are an old copy you do not need): remove the 1.x
      tables, or rename them out of the way, then load the page again.

  Until you do, neither the site nor `idno:upgrade --drop-legacy` deletes anything.
* **"The upgrade renamed this site's 1.x tables legacy_<name> and was checking its copy against them,
  but ... exist under the old names again"** An old Idno process created tables with the old names
  after the upgrade had renamed the originals. The `legacy_` tables are your site's original data:
  keep them. Stop every process of the old Idno version, then remove the newly created tables named in
  the message (the ones *without* the prefix), and load the page again. Nothing was changed.
* **"Some 1.x tables are renamed (...) and some are not (...)"**, **"The 1.x tables are renamed
  (...) but the copy had not finished"**, **"The upgrade's progress rows are inconsistent"**:
  something other than the upgrade changed the tables while it ran. Most often an old Idno process
  is still running and has created tables with the old names again. Stop every old process. Tables
  under the old names that appeared after the rename are new (the upgrade had renamed the originals):
  check that they hold nothing you need and remove them, never the `legacy_` ones, which hold your
  1.x site. **But if you, or anyone else, renamed tables by hand**, the tables under the old names
  may be the real 1.x tables: compare the row counts of both sets (a new, empty table holds few or no
  rows), and if you are not sure, restore your backup and start again.
* **"The upgrade began with 1.x tables that are no longer there: ..."** Tables the upgrade was
  reading have been deleted or renamed by something else. Restore them (from your backup if need be)
  under the names given; the upgrade then goes on.
* **"The upgrade began without the 1.x table ..., but ... exists now"**: an old Idno process created
  a table during the upgrade. Stop every old process, check the table named in the message and move
  or remove it; the upgrade then goes on.
* **"The 1.x tables cannot be copied: ... already hold data, but no upgrade is on record."** The
  upgrade was about to start copying, and some of the new tables (`idno_entities`, `idno_reader`,
  `idno_site`, `idno_settings`, `idno_upgrade_rejects`) already hold rows. Nothing was changed, and
  the upgrade does not start while they do: copying beside them would keep their older rows instead of
  your 1.x rows wherever the two share a record. Two usual causes:
    * the rows are left over from an earlier upgrade attempt you do not want (you removed its `idno_`
      tables by hand and missed one): back up the database, then remove ALL the tables whose names
      begin with `idno_`, not only the ones named, and load the page again;
    * the database belongs to a site you use on this version, and the 1.x tables were restored into
      it: they must not be in this database. Move the 1.x tables to a database of their own (and
      upgrade that one), or remove them.
* **"The 1.x tables cannot be renamed: X and legacy_X both exist."** The upgrade found a `legacy_`
  table it did not make, either before it started copying (then nothing at all was copied) or when
  it was about to rename the old tables. The tables without the prefix hold your site and are what
  the upgrade is copying. Examine both before moving anything: find out what made the `legacy_` table
  and what it holds (an earlier attempt, a backup someone loaded, another application). Only once you
  are sure it is not your site's data, move it out of this database or rename it; the upgrade then
  goes on. (When tables reappear after the upgrade has renamed the originals, you see the previous
  message instead.)
* Only from `idno:upgrade`: **"Another process has been upgrading the database for 60 seconds ..."**
  (the upgrade page is open in a browser, or another `idno:upgrade` runs: let it finish, or close the
  page, then run the command again) and **"The upgrade made no progress in 5 steps in a row."** (run
  `--status` and look at the error log).

## Undoing the upgrade

**Before the upgrade has finished** (the site has not opened yet), restoring the Idno 1.x files is
enough while your old tables still have their own names. If the page had already shown "Checking the
copy against the old tables", the tables have been renamed: rename them back first (below).

**Renaming the old tables back.** Run this statement with your database tool (phpMyAdmin's SQL tab,
for example), then restore the Idno 1.x files:

```sql
RENAME TABLE
    legacy_entities TO entities,
    legacy_entities_metadata TO entities_metadata,
    legacy_entities_search TO entities_search,
    legacy_reader TO reader,
    legacy_reader_metadata TO reader_metadata,
    legacy_reader_search TO reader_search,
    legacy_site TO site,
    legacy_site_metadata TO site_metadata,
    legacy_site_search TO site_search,
    legacy_config TO config,
    legacy_config_metadata TO config_metadata,
    legacy_config_search TO config_search,
    legacy_versions TO versions,
    legacy_session TO session;
```

The statement renames all of them or none. It fails, changing nothing, if one of the `legacy_` tables
does not exist (leave that line out) or if a table with the old name exists already (an old Idno
process may have created it: check that it holds nothing you need and remove it first). Once the 1.x
tables are back, the new version of Idno no longer opens the site (it shows a message saying both
copies are there) until you either go back to 1.x or remove one of the two sets.

**After you have used the upgraded site**, posts, comments and other changes made since the upgrade
are only in the new tables: going back to the old tables loses them. Restoring your backup loses them
too.

**Upgrading again later.** If you went back to Idno 1.x and want to upgrade again, first delete ALL
the new tables, whose names begin with `idno_` (or restore the backup you made before the first
upgrade). If you miss one that holds rows, the new upgrade does not start: it stops with "The 1.x
tables cannot be copied: ... already hold data" and names it, and changes nothing. If you do not, the new version finds both a finished upgrade and your 1.x tables, and stops
with the message "This database holds a site already upgraded to this version of Idno and, again,
the tables of an Idno 1.x site ..." instead of opening the old copy (see "If the upgrade stops").
If you went back before the upgrade had finished, delete all the `idno_` tables too: otherwise the
upgrade carries on from where it stopped and misses changes made in 1.x to rows it had already copied.

Once the `legacy_` tables are deleted, the upgrade can only be undone from your backup.

## Moving a MongoDB site

`php bin/console idno:import:mongo` copies a MongoDB site (its records and the files it keeps in
GridFS) into a new MySQL, MariaDB or SQLite database and the upload directory. It reads MongoDB with
the PHP extension `mongodb` alone (`pecl install mongodb`); the `mongodb/mongodb` library is not
needed. Your MongoDB database is only read: nothing in it is changed. The MongoDB server must be version 3.6 or later: that is the oldest the `mongodb` extension talks to. To move the data of an older server, dump it (`mongodump`) and restore it (`mongorestore`) into a newer `mongod` first, and run the import against that one.

1. **Stop every process of the site** (the web server's PHP, the queue and cron services of the old version): the import
   must see a database nobody writes to. If it finds the counts changed while it ran, it stops.
2. **Make a new, empty database** (MySQL 8.0 or later, MariaDB 10.6 or later), and a user that can
   create tables in it. For SQLite, choose where the database file will be (not on a network
   filesystem); the file must not exist yet, or be empty. The import refuses a database that holds
   any table at all.
3. **Keep `config.ini` as it is** until the import has finished: the import reads the MongoDB settings from it (`dbstring`,
   `dbname`, `dbuser`, `dbpass`, `dbauthsrc`), and the upload directory (`uploadpath`). Give other
   ones with `--source-uri`, `--source-db` and `--upload-path`.
4. **Run the import**:

   ```
   php bin/console idno:import:mongo --target=mysql://user@host/newdatabase
   ```

   With a user and no password in the URL, it asks for the password (hidden). You can also put the
   password in the URL (percent-encode `@`, `:`, `/` and `%` in it), or give the whole URL in the
   environment variable `IMPORT_TARGET_URL` instead of `--target`. For SQLite:
   `--target=sqlite:///data/idno.sqlite` (relative to Idno's directory) or
   `--target=sqlite:////var/lib/idno/idno.sqlite` (absolute). The files go into the upload directory,
   under the directory named after your site (its `file_path_host`, or its host less `www.`); give
   another with `--file-host`. The import never prints the database password.

   For an SQLite target, the file's name must end in `.sqlite`, in lower case (the web server
   configurations refuse to serve that suffix; the import refuses any other name before it connects,
   and so does the site itself). The import runs as you, so the database file, its directory and the files SQLite
   and the upgrade create beside it (`-wal`, `-shm` and `.upgrade.lock`) are yours, and the web server
   cannot write to them: give them to the web server's user (or make them writable for it), for
   example `chown -R www-data data/`, and run `idno:upgrade` and other console commands on the site as
   that user. The import prints the same reminder when it finishes.
5. **Only once the command has finished with "The import is complete." (exit status 0), put the
   printed lines in `config.ini`**, in place of the MongoDB settings: `database`, `dbname`,
   `dbhost`, `dbuser`, `dbpass` (where it prints `<the password you gave>`, write the password),
   `filesystem = "local"`, `uploadpath` and, only when you gave `--file-host`, `file_path_host`
   (without it, the directory of the files is the one your site's configuration already names, which
   stays in `config.ini` or in the imported settings).
6. **Run `php bin/console idno:upgrade`**, then start the site again. Users log in again (sessions are
   not carried over).

What it carries over: the records of `entities`, `reader` and `site`, the site's configuration (the
`config` document your site loaded, as MongoDB itself answers the query the site made; any other
`config` document is not used, and if the one the site loaded cannot be the settings the import stops
and says why), and every GridFS file, with its
metadata, under its own id, so every link to a file keeps working. Each file's size, and its bytes,
are checked once copied. Other collections are listed at the end and not copied: Idno 2 does not read
them (sessions, for example).

Records read as any record the site saves itself does: a record that had no `siteid` reads
`siteid: null`, and an empty `owner` (the MongoDB backend returned `false` for a user's) reads `''`.

**Rejects.** A record that cannot be kept is not copied, and the import goes on: a record without a
`uuid` or `_id`, one holding a value with no place in the new database (binary data, a regular
expression, ...), one too deeply nested for the database, a second record with a `uuid` another record
has (the database compares them ignoring case, and on MySQL and MariaDB accents too: of the two, the
one created first is kept), or an older configuration. Each is a row of the table
`idno_upgrade_rejects` of the new database, with the record exactly as MongoDB held it (Extended
JSON, in `contents`) and why (`reason`); the import prints each one and how many there were.

**If the import stops** (it says why: a database it cannot reach, a target that is not empty, a file
whose bytes do not check, ...), nothing is lost: MongoDB is unchanged, and the import never asks you
to change it. If a GridFS file is broken (a chunk missing or stored twice), back the MongoDB database
up (`mongodump`) before you remove or repair that file. The new database is then incomplete, and the
import says so: **never point a site at it**. The import holds the last schema step back until
everything is in, so `idno:upgrade --status` shows a migration pending, but that does not keep a site
closed: a site whose `config.ini` named an incomplete database would show its upgrade page, finish
that step itself and open with part of your content. **The import does not clean up after itself:** a
failed import leaves its target as it was when it stopped, and you must drop it by hand (the database
of a MySQL or MariaDB target, the file and its `-wal` and `-shm` files for SQLite), make a new, empty
one, and run the import again. Files already copied into the upload directory are checked and kept,
not copied again; a file that did not copy correctly is not left there.

## Other changes in 2.0

Idno sets PHP's session cache limiter to `nocache` itself, before it starts the session, so every page is sent with `Expires` in the past, `Cache-Control: no-store, no-cache, must-revalidate` and `Pragma: no-cache` whatever your php.ini says. A site that relied on a custom `session.cache_limiter` (`public`, `private` or none) no longer gets it.

Upgrades normally need no cache clearing, because the compiled cache is keyed by the code it was built from (and by the installation's directory). Deleting everything under `var/cache/` is always safe, and is the fix if the site reports a container error after a deploy. It signs nobody out: sessions are not kept there.

!!! warning "Opcache with `opcache.validate_timestamps=0`"
    If your server runs PHP's opcache with `opcache.validate_timestamps=0` (common in production, and set by the bundled Docker image), restart PHP (PHP-FPM, or your web server if it runs PHP) or reset opcache immediately after replacing the files. Until you do, PHP keeps running the old code, and a request in that window can build the new compiled cache from it. If the site reports a container error after a deploy, delete everything under `var/cache/` and restart PHP again. Nobody is signed out by it.

If no `config.ini` exists in your `configuration` directory (or your installation directory) and no environment variable names a database, Idno shows its installer at every address: see [the installation instructions](instructions.md). Because your site's data is there, it asks for the code it has written to `configuration/install-code` on the server before it sets anything up, whatever database you choose (so that only someone who can reach the server's files can set up a site there, or take yours over and set its address); if you point it at the database your site already uses, it also asks you to confirm using it; nothing in the database is replaced, and the upgrade described above then runs. Restoring your `configuration/config.ini`, or `php bin/console idno:install --use-existing`, needs no code.

### Installation and the first account

* **The installer is part of Idno itself.** The `/warmup/` pages and `warmup/CLI/CLIInstaller.php` are gone: the web installer is what an unconfigured site shows at `/`, and the command line installer is `php bin/console idno:install` (see [Command line installation](cliinstaller.md)). `makeconfig`, `generate-manifest` and `check-requirements` have no successor: `idno:install` takes a manifest, and checks the server itself. Scripts that called the old installer must be changed.
* **Registering never makes an administrator.** The first administrator is created by the last step of the installation, which only the browser that installed the site can reach, or by `php bin/console idno:admin:create`. A site with no account at all shows "This site is being set up" and lets nobody register.
* **A site configured by environment variables alone is installed.** If the environment names a database (`IDNO_DATABASE`, `IDNO_DATABASE_URL`), no configuration file is needed and the installer is not offered.
* **The installers write the site's address.** New installations have `url` in `config.ini`; add it to an older one if you use the queue (see above).
* **The onboarding pages are gone**: `/begin/`, `/begin/register`, `/begin/profile`, `/begin/connect` and `/begin/publish`, their images (`gfx/onboarding/`) and style sheet (`css/idno-simple*.css`). After the account is created the administrator lands on `/admin/welcome/`.

Thanks to [Chris Aldich](http://stream.boffosocko.com/2015/upgrading-withknown-on-ones-own-server) for this point.

!!! warning "MongoDB Users"
    Idno 2.0 does not run on MongoDB: see "Moving a MongoDB site" above. A site whose `config.ini` still says `database = 'mongo'` (or `mongodb`, or the old class name `Idno\Data\Mongo`) is held closed, and the installers refuse it.

!!! warning "var/ must be writable by the web server"
    Idno 2.0 keeps its compiled cache in `var/cache/`, so the web server's user must be able to write to `var/` (or set the `IDNO_CACHE_DIR` environment variable to a directory it can write to). If it cannot, Idno uses a private directory under the system's temporary directory instead, which works but is rebuilt whenever that directory is cleared; if no location is usable, the site shows an error asking you to set `IDNO_CACHE_DIR`. Idno's log messages still go to PHP's error log, as before. The only other thing written under `var/` is `var/sessions/`, where a site whose sessions are PHP files (every SQLite site) keeps them when PHP names no session directory of its own: set `IDNO_SESSION_DIR` (or `session_path` in `config.ini`) to put them elsewhere. See "Sessions in a directory of their own" below.

!!! warning "Block web access to the new and private directories and scripts"
    These must never be served or run over the web: `var/` (the compiled cache), `config/` (the kernel configuration), `bin/` (the command line), `Tests/`, `docs/`, `frontend/` (the Idno 2026 front-end sources), `data/` (where an SQLite database lives), `configuration/` (the site's settings), `Uploads/` (uploaded files: see "Uploaded files must not be served" below), `warmup/CLI/`, and the command-line scripts `idno.php` and `known.php`; and any file ending in `.sqlite`, `.sqlite-wal`, `.sqlite-shm` or `.upgrade.lock`, wherever it is. The command-line scripts also refuse to run under a web server, but do not rely on that alone. The bundled `.htaccess` file and the sample configs in `warmup/webserver-configs/` already deny them, case-insensitively.

    * **Your own `.htaccess`**: add `RewriteRule ^(var|config|bin|Tests|docs|data|frontend|configuration|Uploads|warmup/CLI)(/|$) - [F,NC]` and `RewriteRule ^(idno|known)\.php$ - [F,NC]` before the front-controller rewrite, and a `<Files ~ "\.(sqlite|sqlite-wal|sqlite-shm)$">` and a `<Files ~ "\.upgrade\.lock$">` block that deny access (as the bundled `.htaccess` does).
    * **nginx**: before your static-file and `.php` locations, add `location ~* ^/((var|config|bin|tests|docs|data|frontend|configuration|uploads|warmup/cli)(/|$)|(idno|known)\.php$) { deny all; }` (regex locations are tried in order, so it must come first), `location ~* \.(sqlite|sqlite-wal|sqlite-shm|upgrade\.lock)$ { deny all; }`, plus `location = /idno.php { deny all; }`, `location = /known.php { deny all; }` and `location ^~ /var/ { deny all; }` (and the same `^~` form for `/config/`, `/bin/`, `/Tests/`, `/docs/`, `/data/`, `/configuration/`, `/Uploads/`, `/uploads/`, `/frontend/` and `/warmup/CLI/`). See `warmup/webserver-configs/nginx.conf`.
    * **Caddy**: `@denied path_regexp denied (?i)^/((var|config|bin|tests|docs|data|frontend|warmup/cli|configuration|uploads|\.git|\.github)(/|$)|(idno|known)\.php$)` followed by `respond @denied 403`, and `@denied_files path_regexp denied_files (?i)\.(sqlite|sqlite-wal|sqlite-shm|upgrade\.lock)$` followed by `respond @denied_files 403`. See `docker/caddy/Caddyfile`.

!!! danger "Uploaded files must not be served"
    Idno serves every uploaded file through its own file page, which applies the access rules of the post it belongs to, keeps the administrators-only files (the site archive, an import waiting to run) to administrators, and never hands out the `.data` file beside it. If the web server hands out the upload folder directly, anyone who has a file's address reads it without any of that. The installer always puts uploads in `Uploads/` inside Idno's folder, which is inside the web server's document root.

    * **The shipped configurations refuse it** in any letter case: the bundled `.htaccess` and `warmup/webserver-configs/htaccess*.dist` (`Uploads` in the `[F,NC]` rule above), `nginx.conf` (`uploads` in the `~*` location, and `location ^~ /Uploads/ { deny all; }`), the Caddyfile (`uploads` in `@denied`). On Apache the folder also refuses everything itself: `Uploads/.htaccess` holds `Require all denied` (the installers write it if it is missing). An nginx configuration written before this release did not refuse it: add the two rules above.
    * **An upload path of your own inside the document root** (for example `uploadpath = '/var/www/html/files/'`) needs a rule of its own: on Apache a `.htaccess` holding `Require all denied` in that folder (with `AllowOverride` on) or `RewriteRule ^files(/|$) - [F,NC]` before the front-controller rewrite; on nginx `location ^~ /files/ { deny all; }` and the name in the `~*` location; on Caddy the name in `@denied`. Better still, keep uploads outside the document root.
    * **Check it**: ask for `https://your.domain/Uploads/readme.txt` (or a file in your own upload folder). The answer must be `403 Forbidden` (or `404`), never the file. The web installer asks the same question on its first page and will not go on while the file is served.

!!! warning "Upgrading by overwriting files leaves removed files behind"
    Copying the new release over the old one does not delete files that 2.0 removed. Delete these yourself:

    * the directory `Themes/Twenty26` (Idno 2026 is built in now; its sources are in `frontend/`);
    * the retired theme directories `Themes/Black`, `Themes/Cherwell`, `Themes/ElkinsPark`, `Themes/Fauvists`, `Themes/Green`, `Themes/Kandinsky`, `Themes/MarketStreet` and `Themes/Solo`. Idno never loads a retired theme (a site set to one gets Idno 2026), but leftover directories still appear in the admin theme list until you delete them;
    * `Idno/Core/Hub.php` and the `Idno/Pages/Hub/` directory;
    * `Idno/Data/MySQL.php`, `Idno/Data/AbstractSQL.php` and `Idno/Data/Mongo.php`, and `Idno/Files/MongoDBFileSystem.php` and `Idno/Files/MongoDBFile.php` (a database class of your own in `Idno/Data/` still works);
    * `Idno/Core/AsynchronousQueue.php`, `Idno/Core/SynchronousQueue.php`, the directory `Idno/Pages/Service/Queues/` and the directory `ConsolePlugins/EventQueueService/` (a leftover `ConsolePlugins/EventQueueService/` would register a second `service-event-queue` command, which the new one replaces);
    * the directory `warmup/schemas/` (the installers no longer load SQL files: the database is set up by the upgrade page or `idno:upgrade`);
    * `warmup/index.php`, `warmup/WebInstaller.php` and the directories `warmup/templates/` and `warmup/CLI/` (the old installers; the shipped web server rules still refuse `warmup/CLI/`, for a site that has not deleted it), `Idno/Core/Installer.php`, the directory `Idno/Pages/Onboarding/`, `gfx/onboarding/` and `css/idno-simple.css` and `css/idno-simple.min.css`;
    * any `hosts/` directory (it is no longer read).

### Settings that changed

* **MySQL sites:** every `database` setting that worked before still works (`MySQL`, `mysql`, `beanstalk-mysql`, and any other value that is not a database class, which has always meant MySQL), and a `sessions_storage = Idno\Data\MySQL` setting keeps your sessions in the database (now its `idno_sessions` table). Sessions are not carried over: users log in again after the upgrade.
* **MongoDB sites do not start.** MongoDB is no longer a database Idno runs on; move the site with `php bin/console idno:import:mongo` (see "Moving a MongoDB site"). The upload directory then holds the files GridFS kept, and the site's users log in again (sessions are not carried over).

* **A webmention is accepted only for an address on the site's own host.** The webmention endpoint used to look only at the path of the address that was mentioned, so a webmention to `https://old-domain.example/2024/a-post` reached the post at `/2024/a-post` whatever the host name. The rule for what counts as an address of the site (`Idno\Http\Webmention\WebmentionTargets`; the endpoint applies it) is strict: the target must be an `http` or `https` address on exactly the host of the site's `url` setting, on the site's port (or the default port of the scheme), under the site's directory if it is installed in one. A webmention whose target names another host than the site's configured one is refused with `target_not_found`, a `www.` alias (or the bare name of a `www.` site) and a former domain included, and so is an address with no host. There is no setting that lists other hosts: if your site moved to a new domain, mentions of its old addresses are not accepted, and neither are those of an alias; send visitors of the old name to the new one so that new links name the new one. Why: a webmention is a claim about a link to one of your pages, and a page of yours is the address your site gives it; an address on another host is not. A site with no `url` setting (an older hand-written configuration) matches the host it detects for itself, which can follow the request, and logs one warning: set `url`. A mention to an address whose page takes no mentions (a feed, a tag page, an edit page) is also answered `target_not_found`, before the sender's page is fetched.
* **Outbound requests are made by Symfony's HTTP client.** No Idno or bundled plugin code calls curl directly any more. A remote server whose certificate does not verify is no longer talked to, requests have time and size limits, URLs that members type are refused on private networks, and the `cookie_jar` setting does nothing. The list is under "Outbound requests: `Webservice`", below; `proxy_string`, `proxy_type`, `disable_ssl_verify` and `http_allow_private` (new; see below) are read from `config.ini` or the environment only, and the first three still work.

* **The session cookie is `SameSite=Lax`.** A browser no longer sends it with a cross-site POST. The `P3P` header is no longer sent, and `Session::validate()` and its `X-IDNO-DEBUG: Tilt!` header are gone (a subclass override of `validate()` is no longer called).
* **`session_hash_function` is ignored.** PHP has ignored `session.hash_function` since 7.1; the setting is read and dropped, and no longer has a default.
* **Micropub `GET` needs a token.** `micropub/endpoint?q=config` and `q=syndicate-to` (the two queries the endpoint has) answer 401 `unauthorized` unless the request carries an access token or an API signature, as a `POST` always has; a logged-in browser's session cookie is not enough. An anonymous `GET` of the endpoint answers 401 `unauthorized` where it answered 403 `forbidden`.
* **A Micropub delete that is refused is a Micropub error.** `action=delete` of a post that is not there, or one that the token's member did not write (an account's address included), answered with a server error (a 500 page); it is now `400 not_found` or `403 forbidden` as a Micropub client expects.
* **The delete page of a post that is not there is sent away.** Opening `/status/delete/<id>` (and the like, photo, media, event, RSVP and static page delete pages) for an id that names nothing, or a post the member may not read, was a server error and a mail to the administrators; it is sent back as the other delete pages send a missing post away.

### Removed in 2.0

* Known hub integration removed; the `idno_hub` and `known_hub` settings are ignored.
* The eight bundled themes `Black`, `Cherwell`, `ElkinsPark`, `Fauvists`, `Green`, `Kandinsky`, `MarketStreet` and `Solo` are removed. A site configured to use one switches to Idno 2026, which is built in (the setting is saved as no theme, and the administrator is told once). If the retired theme is set in `config.ini` or an environment variable, change it there: Idno draws Idno 2026 meanwhile but cannot update the file. Idno 2026 itself is no longer a theme: see "The look of a site with no theme" under "Templates".
* Multi-tenant host directories (`hosts/<domain>/`) are no longer read: plugins and themes are loaded only from `IdnoPlugins/` and `Themes/`, and the `multitenant` setting is ignored.
* Per-domain configuration files (`configuration/<domain>.ini`, e.g. `configuration/example.com.ini`) are no longer read. Move their settings into `configuration/config.ini` before upgrading, or the site will ignore them (and, if that file was its only configuration, it will look uninstalled). The command-line installer now writes `configuration/config.ini` only.
* Scripts that started Idno themselves with `new Idno\Core\Idno()` must `require` `Idno/start.php` instead, which boots Idno (the Symfony kernel and the legacy application) and returns. While the database needs an upgrade, `Idno/start.php` prints one line saying so and exits with status 1. Command-line tools should be console commands (`bin/console`; `idno.php` and `known.php` are aliases).
* The `IDNO_KERNEL_SECRET` environment variable is replaced by `APP_SECRET` (not used by anything yet).
* The hand-written SQL backend classes `Idno\Data\MySQL` and `Idno\Data\AbstractSQL` (see "For developers" below).
* The MongoDB backend (`Idno\Data\Mongo`) and its GridFS file system (`Idno\Files\MongoDBFileSystem`, `MongoDBFile`). A site configured for MongoDB does not start; `php bin/console idno:import:mongo` moves it to MySQL, MariaDB or SQLite (see "Moving a MongoDB site"). The `mongodb/mongodb` library is no longer used; the import needs only the PHP extension `mongodb`.
* The queue's classes `Idno\Core\AsynchronousQueue` and `Idno\Core\SynchronousQueue`, its worker plugin `ConsolePlugins/EventQueueService`, and the pages `/service/queue/list`, `/service/queue/dispatch/<id>` and `/service/queue/gc` (they answer 404). See "The queue of events" below.
* The cron service (`service-cron`, `ConsolePlugins/CronService`) and its events `cron/minute`, `cron/hourly` and `cron/daily`. Nothing triggers them any more, and no scheduler replaces them. A site that ran `service-cron` removes that systemd unit or crontab line. A third-party plugin that listened to those events needs its own schedule (for example a crontab line running its own console command).
* SwiftMailer. Mail is sent by Symfony Mailer. Nothing changes for existing settings: `smtp_host`, `smtp_port`, `smtp_username`, `smtp_password`, `smtp_secure` and `from_email` mean what they did (an empty port is 25, with `ssl` too; empty `smtp_secure` sends without encryption; `tls` is STARTTLS; `ssl://host` and `tls://host` are encrypted from the start; credentials are ignored with an empty host). This is checked against a capture of SwiftMailer 6.3.0's behaviour on the wire, and `Idno\Core\Email` has the same methods and the same return value. See "Mail" under "For developers".
* The cache classes `Idno\Caching\FilesystemCache`, `APCuCache`, `ArrayCache`, `StaticArrayCache` and `EphemeralCache`, and the `cache` setting that chose one: it is ignored now, with one warning in the log. Idno has one cache, a Symfony Cache filesystem pool in `cachepath` (else `var/cache/pool`; see `docs/install/config.md`). Entries the old `FilesystemCache` wrote under `uploadpath` are not read or deleted (a cache may be lost); remove the directory named by the md5 of your host there if you like. See "The cache" below.
* The PHP `gettext` extension is no longer required. Translations are read from the same `.po` and `.mo` files by Idno itself (see `docs/developers/languages/index.md`), and Idno no longer calls `setlocale()` or `putenv()` for the language, so the process's locale is whatever PHP or the web server set. The core translation domain is now `idno` everywhere (it was `known` for the registration and `idno` for `build-lang`): a core catalogue is `languages/<locale>/LC_MESSAGES/idno.po`. Code that relied on that `setlocale()` call for dates, number formats or sorting (`strftime()` with a name, `sprintf('%f')`, `sort()` with `SORT_LOCALE_STRING`) must set the locale itself. Nothing in Idno or its bundled plugins does.
* **The "Idno" import form** of the admin import page, which offered an Idno RSS file and had no code behind it, is removed. An RSS file exported from another Idno site imports through the WordPress form.
* **Export archives are for administrators only.** The full archive (`/admin/export/` → "Create archive") is stored with metadata that restricts it to administrators: anyone else who has its address is refused (403), and it is sent with `Cache-Control: private, no-store`. Its `config.json` holds the stored settings with every secret removed (never `config.ini` or the environment), its entities' JSON says their `access` and publish status, and attachment addresses in it point at files the archive holds. An archive made before the upgrade has no such metadata, but the one the export page names is restricted all the same, and is marked the next time the page loads (one that is a week old is removed then); an older archive that is no longer named stays readable by anyone with its address: delete it from the file store if you have one. The export page's "Generated" date and the week's expiry count from when the archive was made. Leftovers of an export or import that was killed (its working folders, uploads waiting for an import, archives no longer offered) are removed after a day or a week when the export or import page is loaded; only folders and files Idno recorded itself are looked at, never the whole file store or other files in the temporary directory. A settings save made while an export runs can restore the export's earlier state: the page then shows no archive, and the running flag clears itself after six hours.
* **`Migration` is deprecated.** `Idno\Core\Migration`'s static methods (`exportToFolder()`, `archiveExportFolder()`, `createCompressedArchive()`, `cleanUpFolder()`, `importWordPressXML()`, `importBloggerXML()`, `importFeedXML()`, `importImagesFromBodyHTML()`, `getExportRSS()`) stay for this release as delegates to the services in `Idno\Portability`; call those instead (see "Import and export" below).
* The 1.x database tables (`entities`, `entities_metadata`, `entities_search`, `reader`, `site`, `config` and their `_metadata`/`_search` tables, `versions`, `session`) are no longer read or written. The upgrade copies them into the new tables and renames them `legacy_<name>`.

## For developers

### The installer and onboarding

`Idno\Core\Installer`, `WebInstaller`, `CLIInstaller` and the `Idno\Pages\Onboarding\*` pages are removed; the installation is `Idno\Install\*` (see `AGENTS.md`). The template `shell/simple` and its partials, the templates under `onboarding/`, and `DefaultTemplate::sendSimpleShellHeaders()` are removed: a plugin that drew a page in the simple shell draws it in the ordinary page shell (`drawPage()`). The `onboarding/connect/networks` extension point no longer exists. `Idno\Pages\Account\Register` no longer takes `onboarding` or `set_name`, and no longer triggers `site/firstadmin` (the installation's last step does); the list of required PHP extensions is `Idno\Install\ServerChecks::EXTENSIONS`. A plugin that created the first user by posting to `begin/register` (a test helper, a provisioning script) uses `php bin/console idno:admin:create`, or the service `Idno\Install\FirstAdministrator`.

### The new tables

On MySQL, MariaDB and SQLite, Idno 2.0 keeps its data in these tables, created and changed only by
its schema migrations (`Idno/Storage/Migrations/`, run by the upgrade page and `idno:upgrade`):

* `idno_entities`, `idno_reader`, `idno_site`: one row per record of the collections `entities`,
  `reader` and `site`. Columns: `id` (the record's `_id`), `uuid`, `type` (the entity's alias, see
  below), `owner`, `created` (seconds since 1970), `publish_status`, `data` (the whole record as
  JSON text, exactly as PHP's `json_encode()` wrote it) and `search` (the search text). On MySQL and
  MariaDB there is also `ix_access`, a copy of the record's `access` that the database keeps itself
  (with an index, because every query filters on it), and each declared indexed field adds a
  generated column `ix_<field>`.
* `idno_settings`: the site's settings (the collection `config`), one row per setting (`name`,
  `value` as JSON text, `position`).
* `idno_sessions`: PHP sessions.
* `idno_migrations`: which schema migrations have run.
* `idno_upgrade_progress` and `idno_upgrade_rejects`: the upgrade of a 1.x database (its progress,
  and the rows it could not carry, with their contents).
* `legacy_<name>`: the 1.x tables after the upgrade, until the site's admin deletes them.

**Lookups on fields that are not declared read every document.** In 1.x every field of every record
had a row in the `_metadata` tables, with an index. Now a lookup on a document field
(`getOne(['my_field' => $value])`) uses an index only when the field is declared indexed (below);
otherwise it reads the documents of the types it asks for (about 0.7 seconds per 100,000 entities on
MySQL 8). If your plugin looks records up by a field of its own, declare it.

**Database exports.** `db()->exportRecords()` now exports the new tables: `insert into idno_entities
(...)` statements, and for `config` the rows of `idno_settings`. Such an export cannot be loaded into
a 1.x database.

**The daily optimisation** (`/service/db/optimise`, run once a day from an admin's home page) now
runs `ANALYZE TABLE` on the new tables, which refreshes the statistics without rebuilding them;
`OPTIMIZE TABLE` would rebuild the whole table, holding up writes meanwhile.

**Raw SQL against these tables is not supported.** Their layout belongs to Idno and changes through
migrations from one release to the next. Legacy plugin code keeps using `Idno::site()->db()` and the
entity finders (`Entity::getOne()`, `getFromX()`, ...); new code takes `Idno\Storage\EntityRepository`
(entities) or `Idno\Storage\RecordStore` (raw records) as a constructor argument. See `AGENTS.md`.

### The old SQL backend is gone

The classes `Idno\Data\MySQL` and `Idno\Data\AbstractSQL` have been removed. Code that extended them, created them (`new \Idno\Data\MySQL()`), or checked for them (`instanceof \Idno\Data\MySQL` or `AbstractSQL`, `class_exists()`) must change:

* Legacy plugin code keeps using `Idno::site()->db()`, which on a MySQL, MariaDB or SQLite site serves the same public methods with the same parameters and defaults (except `build_where_from_array()`, which is gone). `getClient()` still returns a `PDO` on the site's one database connection: a `Pdo\Mysql` (PHP's MySQL subclass of `PDO`) or, on SQLite, a `Pdo\Sqlite`, not a plain `PDO`. `checkAndUpgradeSchema()` does nothing: the schema belongs to the migrations.
* To tell whether a site is on SQL, do not check the class of `db()`: use `Idno\Storage\ConnectionParameters::driverFamily(['database' => Idno::site()->config()->database])`, which returns `mysql`, `sqlite`, `mongo` (a site configured for MongoDB, which the schema gate keeps closed) or `other` (a backend class a plugin supplies).

### Uploaded files

Uploads are stored by `Idno\Storage\Files\FileStore` on a Flysystem filesystem, in the layout every site has used (`<uploadpath>/<host>/a/b/c/d/<id>.file` and `<id>.data`), so no file needs moving. `Idno::site()->filesystem()` is now `Idno\Legacy\FlysystemFileSystem`, with the same methods (`findOne()`, `storeFile()`, `storeContent()`, `updateMetadata()`) and failure values; its files are `Idno\Legacy\FlysystemFile`. The classes `Idno\Files\LocalFileSystem`, `Idno\Files\LocalFile` and `Idno\Files\CDNStorable` are removed: code that extended or created them should use `Idno::site()->filesystem()`, or take `Idno\Storage\Files\FileStore` as a constructor argument in new code. `Idno\Files\FileSystem` and `Idno\Files\File` remain as base classes. On a file, `internal_filename` is the absolute path of the file only on a local upload directory; with an `s3://` upload path it is empty, so use `getResource()`, `getBytes()`, `passThroughBytes()` or `write($path)` instead of reading the path. S3 needs no plugin: set `uploadpath` to `s3://<bucket>/<prefix>/`. The `filesystem` setting is deprecated.

Differences from the old local filesystem:

* **Deleting a file removes its metadata (`.data`) file too.** The old code left it behind.
* **A site with an `uploadpath` and no `filesystem` setting stores files locally.** An SQL site used to have no filesystem and its uploads failed.
* **`file_path_host` and the `file/path/host` event work for new uploads.** The old code made the directories under the site's host and wrote under the configured name, so the write failed when they differed.
* **A file id that is not 24 or 32 hex digits is not found**, whatever is on disk under that name.

### Entity type aliases

The `type` column holds a short, permanent alias for each entity class (`status`, `article`, `user`),
not its PHP class name; the record itself still holds the class name in `entity_subtype`, and that
is what loads it. Give each concrete entity class of your plugin an alias, with one attribute line
directly above the class: `#[\Idno\Storage\Attribute\AsEntity('<plugin>_<class>')]` (for example
`banana_peel`), adding `collection: 'reader'` or `collection: 'site'` if its records are not in
`entities`. A class without one is stored under its class name, which works but ties stored data to
the class's name. Never change an alias once records are stored under it. If you rename or move a
class, keep its alias and list its former class names (`legacy: ['IdnoPlugins\Old\Name']`): a query
by class finds the records stored under its alias, its class name and those former names. The
attribute is not inherited: a subclass is stored under its own alias, or its class name.

### Indexed fields

An entity class can ask for a database index on a field that pages look up often, with
`#[\Idno\Storage\Attribute\IndexedField('slug')]`. A field with a declared index matches plain values
only (see the last point of the next list). See [Indexed fields](../developers/plugins/indexed-fields.md).
A new indexed field on a core class (under `Idno/`) ships with a new, empty schema migration (a class
in `Idno/Storage/Migrations/` with its own version and no SQL): that pending migration is what makes
every existing site create the index when it upgrades. A plugin's indexes are created when the plugin
is enabled and by `idno:upgrade`; plugins cannot ship migrations.

### The queue of events

`Idno::site()->queue()` is now one class, `Idno\Legacy\MessengerEventQueue`, on Symfony Messenger. `event_queue = 'AsynchronousQueue'` still turns the asynchronous queue on; any other value (or none) runs events at once, in the request. `enqueue($queueName, $eventName, array $eventData, $runAsUser = null)` keeps its signature and returns an id, or `false` when the event could not be queued. What differs from the old queue:

* **`Idno\Core\AsynchronousQueue` and `Idno\Core\SynchronousQueue` no longer exist.** A plugin that tested `$queue instanceof \Idno\Core\AsynchronousQueue` asks `Idno::site()->queue()->isAsynchronous()`. A site whose `event_queue` names any other class gets the events-run-at-once form and one warning in the log. `AsynchronousQueue::dispatch()` and `gc()` have no successor: nothing needs them.
* **Queued events run in the worker's process** (the command line), not in a web request the worker made to the site. A listener that reads the request (`$_SERVER`, the current page) sees none. The worker needs an explicit `url` in `config.ini` (or `IDNO_URL`) and refuses to start without one; the site is https there exactly when that `url` is. A site served over TLS must have an https `url` configured, or what its worker signs and sends (an ActivityPub `keyId`, for example) names http.
* **The worker runs for a long time, and re-reads nothing in between.** It empties its cache of loaded users and entities after every event, and runs each event as the user it was queued for, read fresh (a user who has been deleted since makes the event fail, it does not run as nobody). Settings and the plugin list are read when it starts: it stops itself after an hour (`--time-limit`, 0 for no limit) and after memory use, exiting 0, for a supervisor to start again; restart it to apply a changed setting at once. `messenger:stop-workers` stops it after its current message.
* **`service-event-queue` is the only worker.** Messenger's own `messenger:consume` is not available.
* **The error kept with a failed event** (`messenger:failed:show -vv`) can include the arguments of the failing call unless PHP's `zend.exception_ignore_args` is on (the production php.ini default): treat that output as sensitive.
* **`/service/queue/list`, `/service/queue/dispatch/<id>` and `/service/queue/gc` are gone** (404), and with them the `AsynchronousQueuedEvent` records of new events: a queued event is a message in the `idno_messages` table (a database that was upgraded earlier needs one more upgrade step, the upgrade page or `idno:upgrade`, to get it).
* **A failed event is kept** in the `failed` queue with its error, instead of being marked complete; nothing retries it by itself (`messenger:failed:show`, `retry`, `remove`). An event runs again only when an operator retries it with `messenger:failed:retry <id>` (the ids `messenger:failed:show` lists; without an id the command is refused, and it also needs the `url` configuration the worker needs), once for each retry. One that fails again is kept under a new id and is hidden from the plain `messenger:failed:show` list for a minute; Messenger's hint to run `messenger:consume failed` does not apply. Retrying an event that had partly succeeded sends it again to whoever already received it. **Completed events leave no record** (the old queue kept them for five minutes).
* **`isComplete()` and `getResult()` no longer report on asynchronous events** (false and null). They still report on an event that ran at once.
* **A worker that was killed mid-event** leaves its message in the queue, and nothing runs it again by itself; the worker says how many there are when it starts, and `--requeue-abandoned` puts them back. Use it only when no other worker is running: an event can take longer than an hour (a video transcode), and one still running would run twice.
* **A worker stops itself when it has used a lot of memory** (80% of PHP's `memory_limit`, at most 256 MiB), exiting 0: a supervisor (systemd `Restart=always`, or cron with `--once`) must start it again. `--once` waits out a busy database and gives up, exit 1, only after 30 seconds of it.
* **The command line and link previews.** Two side effects of events running in the worker: in a console process (no request) `Page::isSSL()` follows the configured `url`, and link previews are fetched for entities published from the console, since the link preview listener is now registered there too.

### Translation

`Idno\Core\Language` keeps `_()`, `esc_()`, `get()`, `getTranslation()`, `register()` and `getLanguage()`, and `GetTextTranslation` keeps its name and arguments (`new GetTextTranslation($domain, $path)`: the domain defaults to `idno`, not `known`), but it reads the catalogue with `Idno\Translation\CatalogueLoader` (`symfony/translation`'s `.po` and `.mo` loaders) instead of the `gettext` extension, and it is registered only when a catalogue exists for the current locale. `ArrayKeyTranslation` subclasses work as before. `Language::uncurlQuotes()` now delegates to `Idno\Storage\QuoteNormaliser::normalise()`, which gives the same result byte for byte (the search text of every record goes through it); new code calls that. Translations now appear where they did not before. The old code translated only when the server had the visitor's locale installed (`fr_FR.UTF-8`, say) and, on the web, only for an `Accept-Language` header naming more than one language (it cut the header at the first comma); and a catalogue with a `.po` file and no `.mo` (the bundled Check-in French one) was never read. Now the visitor's language is matched against the catalogues directly: the exact locale (`fr_CA`), then the language (`fr`), then the first `fr_*` catalogue in sorted order, so `fr`, `fr-fr` and `fr-CA` all get `fr_FR` when that is all a plugin ships. The region is normalised (`fr-fr` is `fr_FR`, `zh-hant` is `zh_Hant`); an `Accept-Language` header over 1000 bytes is ignored, and a value that is not a locale identifier is `en_US`. A locale passed in code is treated the same way, with an encoding removed: `new Language('en_US.UTF-8')` is `en_US`. Plural entries are not supported: a `.po` entry with `msgid_plural` is read as its forms joined by a bar (one warning per file in the log), and never matches a string passed to `_()`. A `language` attribute on the logged-in user (nothing in Idno sets one) now chooses the locale when no locale is passed; it used to leave the `Language` object half built.

### Symfony Security knows who is making a request

Idno now runs Symfony Security's firewall on every request, so that new controllers can ask for a logged-in user or a role (`#[IsGranted('ROLE_USER')]`, `#[IsGranted('ROLE_ADMIN')]`). It authenticates nobody itself: the legacy session still does, and Symfony never reads or writes the session. What changes for sites and plugins:

* **An API request is a property of the request, not of the session.** A request authenticated by an API signature (`X-IDNO-USERNAME` and `X-IDNO-SIGNATURE`), a Micropub access token or a plugin's `user/auth/request` listener holds its user in memory for that request and writes nothing to the session. A signed request that also carries a browser's session cookie acts as the signed member and leaves the browser's session as it was; before, that session was destroyed when the request ended. `$_SESSION['is_api_request']` is no longer written or read.
* **`Session::setIsAPIRequest()` is deprecated** and logs one line a process. It now sets the request's flag only. A plugin that authenticates requests by a credential of its own either returns the `User` from its `user/auth/request` listener, or calls `Idno::site()->session()->authenticateStatelessly($user)` (see [Making and accepting API calls](../developers/plugins/api.md)). An administrator authenticated this way is still not an administrator for the request.
* **An anonymous session started by an API request is destroyed when the request ends**, as before, so API clients leave no session behind.
* **A refused controller answers 403**, never a login redirect: the site's 403 page for a browser, `{"error":"forbidden"}` for a client that asks for JSON.
* New dependency: `symfony/security-bundle`. Run `composer install` and clear `var/cache/`.

### Form tokens

Form tokens are now the session's own, kept by Symfony's CSRF token manager (`symfony/security-csrf`, new dependency: run `composer install` and clear `var/cache/`): one token for a session, 64 hex characters, the same in every form, posted as `__bTk`. The time (`__bTs`) and action (`__bTa`) a form still prints are ignored, and a token is valid for as long as the session is, so the `form_token_expiry` setting is read by nothing (it is harmless to leave). A token no longer comes from `site_secret` (which still signs ActivityPub quote stamps). A form that was open when the site was upgraded fails once with "Invalid token." and changes nothing; the member reloads the page. Logging in gives the session a new token. `Bonita\Forms::token()` keeps its signature and ignores its arguments; `Forms::validateToken()` keeps its signature and treats a malformed token as an invalid one (it used to be a server error). A plugin that built a token itself from the action, the time and the site secret must call `Forms::token()` instead. `Page::debugLogToken()` is gone: a token, or part of one, is never logged. The JSON and JSONP output of a form page no longer has a `csrf` list (it held the token of each form of the page, and JSONP is a script any other site can load), and no shell prints the token whatever puts it among a page's variables; an API client that logged in through the login form read its token from that list and now reads it from the HTML form of the same session (`__bTk`), as a browser does. The administrator's diagnostics report no longer prints the session's form token.

### Signing in and out

* **Sessions in a directory of their own (SQLite sites, and MySQL sites with file sessions).** When a site keeps its sessions as PHP files and PHP's `session.save_path` names no directory (the default on most hosts, which means the system's shared temporary directory), Idno now keeps them in a private directory of its own: `IDNO_SESSION_DIR` when set, else `var/sessions/`, else a per-site directory under the system's temporary directory. The directory is created readable by the web server's user only, and PHP's garbage collection is switched on for it (one request in a thousand), because a host that collects sessions by a cron job (Debian sets `gc_probability` to 0) never reaches it. Why: a shared directory is collected by every site and process of the machine, and one collection over a directory holding hundreds of thousands of files stalled single requests for tens of seconds. **Members of such a site are signed out once by the upgrade**, because their session files stay in the old directory; they sign in again. A directory named by the host (`session.save_path` in `php.ini`, for example Debian's `/var/lib/php/sessions`) or by the `session_path` setting is used as it is, and nothing changes for those sites. A site whose sessions are in the database is unchanged. If no private directory can be made, PHP's own is used and one warning naming `session_path` and `IDNO_SESSION_DIR` is logged. The old session files in the temporary directory are not deleted by Idno; PHP's collection removes them in time. Only a web request creates it: the command line, the queue worker and any script that loads `Idno/start.php` from the command line never do, so a deploy user's script cannot take ownership of it. `IDNO_SESSION_DIR` must be an absolute path (a relative one is refused). A directory your user owns that is readable by others is made private (0700). If `var/sessions` or `IDNO_SESSION_DIR` exists but cannot be used (another owner, a link, not writable), one line an hour in the log (remembered in the site's cache) says so, naming it and the fix (`chown -R <web user> var/sessions`, or `rm -r var/sessions`), and sessions go to the next directory; members are signed out when the directory changes.

* **Too many failed logins are refused.** Five attempts for one ACCOUNT in five minutes (the handle and the email address of an account share the count, however they are spelled: the database's own comparison decides, so case and accents are ignored on MySQL and MariaDB), and the next attempt is refused without the password being looked at, even a right one, until the five minutes are over; a successful login or a password reset clears the count. The attempt is counted before the password is checked, so parallel requests cannot each get a guess; with no lock, a burst can still get a few more than five through. A name that no account has is counted by the name, folded. The counts live in the site's cache pool: with the cache disabled, nothing is limited; deleting the pool directory (`cachepath`, else `<cache base>/pool`) clears every count; two installs with the same host name on one cache base share counts. It is for the account, not the visitor's address, because a site behind a reverse proxy cannot yet tell its visitors' addresses apart. Two consequences to know: anyone who knows a login name can keep that account locked by repeating failures every five minutes (the member waits five minutes, or resets the password, which clears the count), and trying spellings tells someone that a name exists. Small timing differences remain: a login for an unknown name does one bcrypt at cost 12, which differs from a member whose hash has an older cost, and makes one more lookup. `symfony/rate-limiter` is a new dependency: run `composer install` and clear `var/cache/`.
* **One message for a wrong password and a name nobody has**: "Oops! That username or password isn't right. Please try again." A theme or a language catalogue that translated the two old messages needs the new one (`languages/source/idno.pot`).
* **Changing a password ends the member's other sessions**, and so does a password reset; the session that makes the change stays signed in, and the browser of an ended session lands on a page that says so. A session started before the upgrade stays signed in only while the member has never changed their password since this release; after a first change it is ended too. Signed API requests are not affected. The replacement of an old password hash by a new one at login is not a change of password and ends nothing. A plugin that writes `$user->password` directly no longer has it stored by a save, and ends no sessions: use `User::setPassword()` (a change of the password) or `User::setPasswordHash($hash)` (a ready hash). A plugin that logs a user on through `Session::refreshSessionUser()` carries the user's fingerprint with the login.
* **Account settings ask for the current password** to change the email address or the password (a wrong one counts as a failed login for the account, and nothing is changed); other settings need none. A custom settings template should add the `current_password` field.
* **Signing out**: the redirect only goes to a page of the site (a foreign or odd `Referer` goes to the home page), and the "You've signed out" message is now shown on the page the visitor lands on (it was lost before). The session cookie is replaced by the cookie of a new, empty session instead of being expired. A logout by a signed request adds no message.
* **The login page and the logout are served by controllers.** Their addresses and what they do are unchanged. Differences: a GET of `/session/logout` (it answered an empty page and did nothing) and a PUT or DELETE of either address are the site's 404 page; the logout is a POST with the form token, as before. A POST of the login or logout form by script (`X-Requested-With`) with a missing or wrong form token is the site's 403 page, as for every page that controllers serve (it used to end with an empty answer). A login form that sends a field that is not text (`email[]=bob`) is a failed login, no longer an error page. A single sign-on plugin that replaces `/session/login` with `hijackRoute()` keeps working.
* **Redirects after signing in or out stay on the site's own address.** The one rule for where a redirect taken from a request (the sign-in form's `fwd` field, the `Referer` of a sign-out) may go now also refuses any address with user information before the host (`https://user@site.example/`): it goes to the site's home page, as an address on another host always did. An `http://` address of the site's own host is made `https://` (path, query and fragment kept) when the site is https, that is when either the configured `url` or the current request is https; an `https://` address is never made `http://`.
* A test of your own that makes private sites should give each its own `cachepath` (`IDNO_CACHEPATH`), as `PrivateSiteTestCase` does: the cache's namespace is the host name without the port.

### Passwords

Passwords are hashed and checked by `Idno\Security\Passwords` (`symfony/password-hasher`). Existing hashes keep working: members log in as before, and a successful login stores a new hash (bcrypt at cost 12, as before) only when the stored one's cost or algorithm differs from what a new one would be. A password that someone sets from now on and that is longer than 72 bytes, or holds a NUL byte, is hashed in full. A hash made before this release of such a password is not replaced at login: it only ever covered the first 72 bytes (or the part before the NUL byte), so what a member types after that is not verified, and the login succeeds with the stored hash unchanged until the member sets the password again. For that reason the old check keeps accepting, for any bcrypt hash made before this release, a typed password of more than 72 bytes whose first 72 bytes are the whole stored password (someone who already has the password). `User::setPassword()` and `User::checkPassword()` keep their names and return values (a password longer than 4096 bytes is refused by `setPassword()`); a plugin that hashes or verifies `$user->password` with `password_hash()` and `password_verify()` itself still verifies, and should call these methods or `Idno\Security\Passwords` to get the upgrade. The account settings page now asks for the member's current password to change the email address or the password (see "Signing in and out"). A plugin's `user/auth/request` listener must authenticate only from a credential the request presents itself (a signature, a bearer token): never from a cookie, HTTP Basic, `REMOTE_USER` or a client certificate, which a browser sends without being asked; see [the API guide](../developers/plugins/api.md).

### Mail

`Idno\Core\Email` is now an adapter over Symfony Mime and Symfony Mailer. Its methods (`setSubject()`, `setFrom()`, `addTo()`, `addBcc()`, `setReplyTo()`, `setHTMLBody()`, `setHTMLBodyFromTemplate()`, `setTextBody()`, `setTextBodyFromTemplate()`, `send()`) and the number `send()` returns are unchanged. What differs:

* **`Email::$message` and the `email/send` event carry a `Symfony\Component\Mime\Email`, not a `Swift_Message`.** The event is triggered with the `Idno\Core\Email` as its data and the message as the value a listener may replace: a listener that returns another `Symfony\Component\Mime\Email` replaces the message; anything else it returns is ignored. A plugin that called `Swift_Message` or `Swift_Mailer` methods on it, or built a `Swift_Message` itself, must be changed to the Symfony Mime API (`->subject()`, `->html()`, `->text()`, `->addTo()`, and so on); the `swiftmailer/swiftmailer` package is no longer installed.
* **`send()` counts the To and Bcc recipients** (the adapter has no Cc, so this is every recipient it can add). With `smtp_secure` `tls` on port 465, SwiftMailer tried STARTTLS on a plain connection, as Idno still does (a server that expects TLS at once on 465 never worked with `tls`; use `ssl` for it). One difference remains, in a case where both fail: with `tls`, a server that does not offer STARTTLS used to be sent the STARTTLS command anyway and refused; Idno stops without sending it. The connection and every read of it now give up after 30 seconds (SwiftMailer's own bound).
* **`Email::lastFailure()`** says why the last `send()` returned 0, in a fixed vocabulary: `settings: <name>` (a mail setting cannot be used), `message` (an address or name was refused, or the message has no sender or body) or `transport` (the mail could not be delivered). The admin test mail page uses it to name a bad setting.
* **A refused address does not throw.** An address or a name with a line break in it, or one that is not an address, makes the message refuse to be sent: the setter does not throw, `send()` returns 0 and logs `Error sending mail: <exception class>`.
* **Failures log the class of the error only.** The message of a transport's exception can quote the SMTP server and the user name, so it is never written to the log.
* **New code** that sends mail asks for `Symfony\Component\Mailer\MailerInterface` from the container (the service is not shared: it is built at each fetch from the settings as this process last loaded them: a change an administrator saves reaches the next mail of the web requests that follow, and a queue worker's mails only when the worker next starts, which it does itself every hour). It needs the site booted, because the settings are stored in the database.
* `egulias/email-validator` and `doctrine/lexer` are still installed, as dependencies of Symfony Mailer.

### The cache

The one cache pool is the container service `Psr\Cache\CacheItemPoolInterface` (also `Symfony\Contracts\Cache\CacheInterface`): a Symfony Cache `FilesystemAdapter` whose namespace is the md5 of the site's host, in `cachepath`, else `<cache base>/pool` (the cache base is `IDNO_CACHE_DIR` or `var/cache`, without the compiled container's per-build directory, so an upgrade does not empty it), else the system temporary directory. New code asks for the pool by injection; it needs the site booted (for the host). `Idno::site()->cache()` still works for one release: its `load($key)` (null on a miss), `store($key, $value, $ttl = null)`, `delete($key)`, array access and magic properties are an adapter over that pool, and any string is a key (a key with the characters `{}()/\@:`, or a long one, is hashed). `Idno::site()->cache()` is now a `PersistentCache` that is no longer an `Idno\Common\Component`, and its `size()` and `getCacheEngine()` methods are gone. A pool is shared by installs with the same host name on one cache base (give one of them a `cachepath`). The directory must be private to the web server's user: where `cachepath` and `var/cache` are trusted as the compiled cache is, a pool in the system temporary directory is used only if it is owned by that user and not writable by others, and otherwise the cache is disabled (one warning in the log; nothing breaks, HSTS is just not remembered). A plugin that named one of the removed cache classes, or set `cache` in its own configuration, should use the pool or `Idno::site()->cache()` instead. Idno itself keeps one thing in the cache: the HTTPS-only hosts it has seen (`Strict-Transport-Security`), each for its `max-age` (at most a year). As the specification says, only the final response of a request counts, only over https, and only for the host that sent it; a header with no `max-age` is ignored and `max-age=0` removes the host's entry.

### Templates

Templates are found and drawn by `Idno\Templating` (a cascade of directories, a locator and a renderer, container services); `Idno\Core\DefaultTemplate` is still what `Idno::site()->template()` returns, and `draw()`, `__()`, `extendTemplate()`, `prependTemplate()`, `replaceTemplate()`, `extendTemplateWithContent()`, `setTemplateType()`, `templateTypeExists()` and `drawPage()` keep their signatures and what they draw. What differs:

* **`Idno\Core\HybridTwigTemplate` is gone.** It could draw Twig files, and no template of Idno or its bundled plugins was one. A `template` setting that names it (in any case, with or without the leading backslash) now gives `DefaultTemplate`, and the old class name stays as an alias of `DefaultTemplate` for one release, for a class that extends it. The Twig cache it kept in `twig/` under the upload path is no longer written: you can delete that directory.
* **Device template types are gone.** Idno no longer looks at the `User-Agent` header to choose a template type (`android`, `iphone`, `ipad`, `blackberry`, ... and `Bonita\Main::detectDevice()` and `Templates::detectTemplateType()`, which no template directory ever matched). A request names its type with `?_t=`, as before; a `_t` that is not a plain value (`?_t[]=x`) asks for no type, where it used to be a server error.
* **`Bonita\Main::additionalPath()` still works.** It, `getPaths()` and `getAdditionalPaths()` now forward to the container's `Idno\Templating\TemplateCascade`: a directory added is searched before the ones added earlier, and Idno's own directory is always the last one, in a command-line process (the queue worker) too. `Bonita\Main::$additionalPaths`, `$cache` and `cached()` are removed (nothing set the cache). `additionalPath()`, `getPaths()` and `getAdditionalPaths()` need the booted kernel: called before it boots (from a script that calls them before `Idno/start.php` has booted it), they throw a `\LogicException` ("The service container has not been set"), where they used to store the path in a static array that `Bonita\Main::$additionalPaths` held. A plugin or a theme does not call it: every enabled plugin's directory and the theme's directory are added when they load, after the kernel has booted. Code that reads `Bonita\Main::$additionalPaths` calls `Bonita\Main::getAdditionalPaths()` instead.
* **`$template->extensions`, `prepends`, `replacements` and `rendered_extensions`** are read-only views of the registrations (arrays, as before, and `isset()` and `empty()` on them and on a key of them work as they did); register through `extendTemplate()` and the other methods. Writing one (`$template->extensions = [...]`) no longer changes the registrations: it stores a template variable of that name, and changing a key in place (`$template->extensions['x'][] = 'y'`) is a PHP notice. A template class that extends `DefaultTemplate` need not call its constructor to register or draw. A template object copied with `clone` has registrations of its own, as it always had.
* **`Templates::$trace` is `Idno\Templating\TemplateRenderer::$trace`**, the hook the test environment uses to record each template a draw looks for.
* **The look of a site with no theme changes to Idno 2026.** Idno 2026 (the look that was the `Twenty26` theme) is core's own: its templates are the `default` templates of core and of the bundled plugins, and its style sheet and script are `css/idno-2026.min.css` and `js/idno-2026.min.js` (they were `Themes/Twenty26/dist/modern.min.css` and `.js`; a page or template of yours that links the old addresses must change them). The `Themes/Twenty26` directory is gone, `Themes/` holds only the themes you install, and the themes page lists "Idno 2026 (built in)" and them. A site whose `theme` setting is `Twenty26` is unchanged: the name is resolved to the built-in look when the site loads, and nothing is saved or announced. A site with a retired theme is told once and saved as having no theme. The page for a member's drafts, `/drafts/`, is now a page of core and no longer needs the theme. A `?_t=` that was added to the address of a search that forwards to the home page (`_t=modern`) is gone.
* **The `modern` template type is deprecated.** It was the type of the Twenty26 theme's templates. A `templates/modern/` directory of a third-party plugin or theme still works for this release (the only template types are single words: `?_t=classic/` or any type with a slash is refused, and a request cannot select the mail types `email` and `email-text`): its files are drawn before the `default` ones on web pages, and the first one drawn in a request logs one `Deprecated:` line in the log that names it. Move its files to `templates/default/`, where they override core's like any other; the `modern` type is removed in 3.0. `?_t=modern` is the same as the default type. `getTemplateType()` now returns `default` where it returned `modern` on a Twenty26 site, so a plugin that tests for `modern` must test for `default`; what a plugin registered for the type `modern` (`extendTemplate($name, $extension, false, 'modern')`, `replaceTemplate($name, $replacement, 'modern')`) is applied to web pages for this release, instead of what the plugin registered for `default` for the same template name, with its own `Deprecated:` line in the log (once a request).
* **Feeds, JSON, ActivityPub, KML and mail keep the entity templates they always drew.** Those types fell back to core's `default` templates, which were the Bootstrap-era ones; now that `default` is Idno 2026, those templates live in `templates/classic/` (core's and each bundled plugin's), which these types try after their own and before `default`. A web page never draws `classic`, and `?_t=classic` is refused. A third-party plugin that overrode one of those `default` entity templates to change what a feed or a mail contains must now override it for the type (`templates/rss/`, `templates/email/`, ...), or in `templates/classic/` of its own: `classic` is tried before a plugin's `default`.
* **Templates nothing drew are gone, and the helper robot with them.** The first-run helper robot (`Idno\Core\HelperRobot`, the page `/robot/remove` and the `robot/wizard` and `robot/post` templates) is removed; a user's stored `robot_state` stays in the database, unused, and registration no longer sets it. The logged-in JSON home page no longer lists the helper robot's form token. The Bootstrap-era partials `shell/toolbar/**` (and StaticPages' `shell/toolbar/content/default` and `staticpages/toolbar`), `settings-shell/*`, `onboarding/publish`, `entity/search` and `shell/messages/async`, and the `classic` shells (`shell`, `settings-shell`, `shell/bootstrap`, `shell/css`, `shell/footerjavascript`, `shell/javascript`, `shell/nav`) no longer exist. A third-party theme whose shell draws one of those partials draws nothing there, and must carry its own. A plugin that registered a template for `shell/toolbar/links` registers it for nothing.
* **JSON on `/admin/` and `/account/` pages is JSON.** The settings shell those URLs use applies to web pages and to JSONP only; a request for `?_t=json` (or any other type but `jsonp`) on one of them is drawn with the shell of its own type, where it used to get the settings shell's HTML. `?_t=jsonp` on those URLs still returns the HTML settings shell, in any letter case: a JSONP page is a script any site can load, and these pages hold the account's and the site's settings. The JSON of a settings page holds what its HTML form holds (form tokens, field descriptions, lists the page shows) and is subject to the same login and admin checks.
* **A template type with no shell of its own now ends at Idno 2026's shell.** `classic/shell` and `classic/settings-shell` (the Bootstrap-era shells) are deleted, so a type whose directory has no `shell` (a third-party type, or `email-text`, which has none) falls back through `classic` to `default/shell`, the Idno 2026 shell, where it used to draw the Bootstrap one. Core's own types all have a shell of their own except `email-text`, which no core path draws a shell for (its mails are the templates of `email-text/`), so no core output changes; a third-party type that relied on the fallback must add its own `shell`.
* **`frontend/` is not served.** The sources of the Idno 2026 style sheet and script (Vite and Tailwind CSS) moved from `Themes/Twenty26` to `frontend/`, a directory every shipped web server configuration refuses, like `config/`. A site with its own web server rules adds `frontend` to the directories it denies.
* **HTMLPurifier's cache moved.** Its serialised definitions are kept in the kernel's cache directory (`var/cache/.../htmlpurifier`), not in the upload path, so an upload path that is served (or an `s3://` one) no longer holds them. You can delete the `HTMLPurifier` directory in the upload path.
* **Run `php bin/console cache:warmup` after an update, as the web server's user.** It compiles every Twig template of core, the bundled plugins and the themes into `var/cache/` (the compiled templates are kept for each build, so an update starts with none). Without it each template is compiled the first time a page draws it. If the web server cannot write the cache directory (run as another user, or a read-only file system), pages still draw: Twig compiles in memory, which is slower, and the log gets one `Twig could not write its compiled template cache` line a process.
* **`__()` no longer changes the template.** `$template->__(['templateType' => 'x'])`, `['vars' => ...]` and `['fallbackToDefault' => false]` used to set the template object's own properties of those names (with no check of the type). They are now template variables like any other, and the object's type, fallback and variables change only through `setTemplateType()` and the other methods. Code that changed the type through `__()` must call `setTemplateType()`.
* **A theme's `chrome/manifest` template no longer applies.** The web app manifest (`/chrome/manifest.json`) is built by the controller that serves it, and no template is drawn. The page's output is the same JSON.
* **No core template sends an HTTP header.** `shell/headers` has no file of its own any more; the shells still draw it, so it stays a place for a plugin to extend (an extension that calls `header()` still runs). `Content-type: text/html` and `Access-Control-Allow-Origin: *` are sent by `DefaultTemplate::drawPage()` for the default type, the simple shell's headers (and its webmention `Link`) by the pages that draw that shell, and `text/plain` of `robots.txt` by its page. The header values are what they were. A third-party page or theme that draws `shell` (or `admin-shell`, `account-shell`) itself with `draw()`, not through `drawPage()`, no longer gets those two headers from the template: call `$template->sendShellHeaders()` before drawing it (the page that draws `shell/simple` calls `$template->sendSimpleShellHeaders()`). Core's two headers are now sent before a plugin's `shell/headers` extension runs, so an extension that sends a header of the same name replaces core's (it used to be replaced by it). `Actions::createLink()`, `createForm()`, `DefaultTemplate::drawSyndication()` and `drawPagination()` draw on a copy of the template object: the variables of a link or form (`url`, `label`, `class`, `title`, `data`, `body`, `action`...) no longer stay on the site's template object, so a later template (or a JSON page) no longer sees them. The only variables they still publish on it are the ones a page's JSON output has: `items_per_page` (pagination) and `services`, `content_type` and `posseLinks` (the syndication control); `createForm()` now posts to the address it is given.
* **The page shells are Twig templates.** `shell`, `account-shell`, `admin-shell` and `settings-shell`, the partials under `shell/` (`shell/nav`, `shell/head`, `shell/footer`, `shell/metatags`, ...), the `js/`, `assets/` and `txt/robots` templates and the onboarding shell `shell/simple` are drawn from `.html.twig` files. A `.tpl.php` file of your theme or plugin with one of those names still replaces core's (it is given the page's variables and the template object as before), `extendTemplate()`, `prependTemplate()`, `replaceTemplate()` and `extendTemplateWithContent()` still apply to them, and a theme can now `{% extends '@core/default/shell.html.twig' %}` and replace one of its blocks (`head`, `nav`, `content`, `footer`). The pages are the same, with these differences. Values that a visitor or member supplied and that the old templates printed as they were are escaped: the page's address in the body's classes and in the Open Graph tags, and the page's description there (a request path with a quote or `<` can no longer open an attribute or a tag); a profile address is linked as an identity (`rel="me"`) only when it is http or https, or a `mailto:`, `sms:` or `tel:` address with no white space, and a `javascript:`, `data:` or `vbscript:` address, a bare word or a `mailto:` with a space in it is no longer printed; the page's icon and the Open Graph image are printed only when they are http(s) addresses; the script that `js/idno` prints encodes `&`, `<`, `>`, `'` and `"` as `\u` escapes (the same values to JavaScript), and the service worker script writes the site's address as a JavaScript string. The structured data keeps its flags and is unchanged. The Dublin Core creator name now prints its characters as they are, not as named entities (`é`, not `&eacute;`), which is not about a value from outside.
* **The templates of entities, annotations, content, streams, drafts, the file picker and the error pages are Twig templates.** `entity/shell`, `entity/feed`, `entity/User` and its parts, `entity/annotations/*`, `content/*`, `drafts`, `file/picker/*` and `pages/*` are drawn from `.html.twig` files. As with the shells, a `.tpl.php` file of your theme or plugin with one of those names still replaces core's, and the extension functions still apply. A Twig template draws the templates it includes on a copy of the page's template object, so what an included template sets with `__()` is not left on the page's template: a user's profile page now describes the profile in its Open Graph and Dublin Core tags (it described the last note of its feed). The JSON, JSONP, feed and KML pages draw `classic` copies of the page bodies that leave variables on the page's template (`entity/wrapper`, `entity/User/profile`, `pages/home/blurb`), so the JSON of those pages is as it was; the other ported page bodies leave nothing, and their JSON is the same too. Differences, on purpose: a link to a post a reply answers, and a link to where a post was syndicated, appear only for an http or https address (any other address is shown as text, with no link); an RSVP answer other than yes, maybe and no is listed as "Other responses", and the delete link of an RSVP names the RSVP (it used to name its place in the list, and deleted nothing); the file picker writes its messages for a script; a profile's contact links are drawn only for `mailto:`, `sms:`, `tel:` and `facetime:` addresses (other schemes were drawn with an unescaped `href`), and the text of a profile field is escaped; the name of a syndication account in the onboarding toggle is escaped for the HTML the toggle script inserts it as.
* **The form templates are Twig templates.** Everything under `forms/` (the inputs, `forms/action`, `forms/token`, `forms/link`, `forms/usersearch`, the outputs and the row of the user search) is drawn from `.html.twig` files; a `.tpl.php` file of your theme or plugin with one of those names still replaces core's. The controls are drawn as they were, with these differences, on purpose. Values that a member, a request or another site supplied and that the old templates printed as they were are escaped: the name, id, class, type, pattern and script attributes of an input, the name, id, class and option values of a select, the name, class, id and height of a text area, the id of the rich text editor (it is written as a JavaScript string where it starts the editor), a tag, the address a form posts to, the id, class, name, address and template of the user search, and the label and help of a field of `forms/input/form-list`. The address of `forms/output/url` is a link only when it is http or https (`FILTER_SANITIZE_URL` let a `javascript:` address through). Non-ASCII text in a value is printed as the characters, not as named entities (`é`, not `&eacute;`). A text area or rich text field whose value is `0` keeps it. A boolean attribute of an input or select (`required`, `disabled`, `checked`, `multiple`, `readonly`, `autofocus`) given `false`, `0`, `'0'` or an empty string is no longer printed (the old template wrote `required=""`, which a browser reads as set), and a text area's height is a number. `forms/input/form-list` no longer prints `required="Array"` for a field that is not required. A link in a response to an XHR request is followed by the hidden form it submits (the old template stored it in a global that only the admin user search read, so such a link elsewhere did nothing; the user search's script now sends `X-Requested-With: XMLHttpRequest`, so the action links in its results work). The controls take the variables a `.tpl.php` page set with `__()` off the page's template again when they are drawn, as before. The JSON of a page keeps documenting its form fields: the controls it draws (`forms/input/text`, `email`, `url`, `hidden`, `password`, `file`, `datetime-local`, `timezones`) have `classic` copies, like the other controls.
* **The account and onboarding templates are Twig templates.** `account/*` (settings, tools, export, login, registration, the password pages, the feedback pages, the follow bookmarklet's cards) and `onboarding/*` are drawn from `.html.twig` files; a `.tpl.php` file of your theme or plugin with one of those names still replaces core's. Values from a request or another site (the address and code of a password reset link, a remote card's name and addresses) are escaped, and the site's address inside the bookmarklet and the API key script is written as a JavaScript string. A new Twig function, `can_add_users()`, says whether the site takes new users.
* **The admin templates are Twig templates.** Everything under `admin/` (the settings, plugins, themes, users, email, import, export, homepage, statistics, logs, dependencies, diagnostics and about pages, the legacy tables page and the admin menu) is drawn from `.html.twig` files; a `.tpl.php` file of your theme or plugin with one of those names still replaces core's, and a plugin's `admin/menu/items`, `admin/home/settings/*` and `admin/users/extensions` extensions apply as before. A name or value an administrator or a plugin supplied (a plugin's name in a dependency label, the labels and values of the statistics, an invitation's address, a blocked address) is escaped, and the pages that load their own address in a script (diagnostics, logs) write it as a JavaScript string. The homepage settings page no longer prints the content types' icons and a copy of its form inside HTML comments. The JSON of `/admin/plugins/`, `/admin/themes/` and `/admin/legacytables/` has a new key each (`plugins_visible`, `themes_with_preview`, `restored_message`). New Twig functions: `system_info()`, `extension_loaded()`, `version_compare()`, `can_make_site_private()` and `legacy_tables_in_menu()`.
* **The mail templates are Twig templates.** The HTML mails (`templates/email/`: the shell, the password reset, the invitation, the test mail, the export and import results and the error mail) are drawn from `.html.twig` files and the plain text parts (`templates/email-text/`) from `.txt.twig` files, in which nothing is escaped: a site title with `&` or an apostrophe appears in a text mail exactly as written. A `.tpl.php` mail template of your plugin or theme still replaces core's, and a mail it draws is placed inside core's shell as before. What mails look like now: the footer of the HTML mail shell no longer carries the postal address of the company that once ran the project, and its link to Idno no longer ends in a tracking query built from the path of the request (the link is `https://idno.co/`, and is the same whether the mail is sent by a web request or by the queue worker); the shell escapes the `title` and `preheader` it is given, which are text; the invitation prints its title, "Join us!", which the old template never printed, and escapes the name of the inviter and the site's title in its HTML part. The mails are otherwise as they were, byte for byte in the plain text parts. The HTML parts that changed are the ones the test goldens `mail-invite.html`, `mail-emailtest.html`, `mail-export.html`, `mail-export-failure.html`, `mail-import.html`, `mail-import-failure.html`, `mail-oops.html` and `password-reset-mail.html` pin.
* **The bundled plugins' post templates are Twig templates.** How a note, article, photo, audio or video post, bookmark, check-in, event, RSVP and static page is drawn in a stream and on its page, its icon and its edit form are drawn from `.html.twig` files, and a `.tpl.php` file of your plugin or theme with one of those names still replaces them. The body of an Event, a Checkin, a Photo and a Media post is purified again when it is drawn (it is already purified when it is saved, so a post made in the site is unchanged; a body a Micropub client or an import stored uncleaned no longer shows a script or a handler). A static page's body is not purified: static pages are written by administrators, and the page is printed as stored, a form, an anchor's `id`, a style block or an embed from any host included. An address from a post (a picture, an audio file, a bookmark, a static page's forward address) is printed only when it is http or https, and a photo post drawn with no page at all (the archive the queue worker makes) shows every picture, as it did.
* **The bundled plugins' pages are Twig templates, and with them every template of core and of the bundled plugins.** The admin, account, menu, head and footer templates of ActivityPub, Bridgy, Checkin, IndiePub, Media, StandardSiteSync, StaticPages, Styles and Webhooks are drawn from `.html.twig` files. A `.tpl.php` file of your plugin or theme still replaces any of them by name, and `extendTemplate()` and the other registrations still apply (the plugins' menu entries and head links keep their place). What a Twig template draws, it draws on a copy of the template object: **a `.tpl.php` override that a Twig template includes is given a copy of the including template's object as `$this`**, so what it sets with `__()` is no longer left on the page's template, and a later template does not see it (a theme that relied on one template's `__()` reaching the next must pass the value explicitly). Differences, on purpose: the secrets of the plugins' pages are drawn only into the body of the page, never kept as a variable of the page, so the JSON of `/account/bridgy/` no longer has the Bridgy key (`twitter_key`); the IndiePub account page links a client address and the authorization page links its Cancel address only when it is http or https (a `javascript:` address was linked); the Bridgy key and the values the admin pages print are escaped; the scripts of the Bridgy page, the static pages page and the custom CSS page write the site's address and their label as JavaScript strings; the Bridgy Twitter button template (which nothing draws, and which raised an error) prints the site's address. The error mail still goes out when its templates cannot be drawn: a short plain text alert is sent instead.
* **The `.tpl.php` files of core and of the bundled plugins are gone.** Every template of the types `default`, `email` and `email-text` in core and in the bundled plugins is a Twig file, and the PHP template that was beside it is deleted. What this changes for your plugin or theme: a template of yours that draws a core template by name (`$this->draw('shell/nav')`, `{{ idno_include('forms/token') }}`) is unaffected, because the name finds the Twig file; a `.tpl.php` override of a core name still wins over core's Twig file; but code that `include`s or `require`s a core template FILE by its path (`templates/default/.../x.tpl.php`) finds nothing, and a theme that copied a core `.tpl.php` file into its own `templates/default/` and relies on `$this->draw()` of the siblings it has copied still works, and draws core's Twig files for the names it did not copy (they draw on a copy of the page's template object, as above). The `classic` templates (what feeds, JSON, JSONP, JSON Feed, ActivityPub and KML draw) and the type shells (`templates/rss/`, `json/`, `jsonp/`, `jsonfeed/`, `kml/`, `activitypub/`) are still `.tpl.php` files, and the `.tpl.php` engine stays for them and for yours. Language catalogues: `languages/source/idno.pot` and the plugins' templates now point at the `.html.twig` and `.txt.twig` files; the translated catalogues are unchanged and every string a Twig template uses is still extracted by `build-lang`.
* **A Twig template reads only the settings on an allow-list.** `setting('name')` returns the value for the names that core's and the bundled plugins' templates use (the site's title, description and address, who may register, the hub, the mail host and port, and the like: `Idno\Legacy\LegacyTemplateHelpers::TEMPLATE_SETTINGS`) and null for every other name, including the database settings, `uploadpath`, `oops_notify`, and anything that looks like a password, key or token. A third-party plugin that reads a setting of its own from a Twig template calls `\Idno\Core\Idno::container()->get(\Idno\Templating\TemplateHelpers::class)->allowSettings('my_plugin_setting', ...)` once, from its `registerPages()`; a name that looks like a secret is refused with an `\InvalidArgumentException`, so pass such a value to the template as a variable from your page.
* **Unused public methods of the template classes are removed.** `Idno\Core\Bonita\Templates::drawList($items, $style)` (it drew `list/<style>`, a template no directory holds: draw the items yourself, `$template->__(['items' => $items])->draw('list/mystyle')`), `Templates::drawObject($object)` (it drew `object/default` for an object that implemented `Idno\Core\Bonita\Drawable`, an interface whose file was never loaded: call `$entity->draw()` for an entity, or draw your own template), `Templates::process($content, $processor)` (it drew `processor/<name>` and returned the content when there was none: draw the template you mean, or format the text yourself), `Idno\Core\Bonita\Forms::draw()` and `Forms::setTarget()` (a form object with a target address that added a token and a time to its template: use the `forms/token` template, `signForm()` and `\Idno\Core\Bonita\Forms::token($action, $time)`, which remain), and the file `Idno/Core/Bonita/BonDrawable.class.php`. `Forms::token()`, `validateToken()`, `formSubmitted()` and `obfuscateField()` are unchanged.
* **Bootstrap-era style sheets and scripts are deleted, and the guide to converting a template is new.** The files `css/idno.css` and `css/idno.min.css` (the style sheet of the look Idno 2026 replaced; with `css/scss/idno.scss` and the partials under `css/scss/idno/` that only it used) and `js/modernizr/modernizr-custom.js` are removed, together with the Grunt `modernizr` task and the `css/idno*.css` targets of the `sass` task that built them (`grunt-modernizr` and `modernizr` are gone from `package.json`). Nothing in Idno or its bundled plugins loads them: a third-party theme or plugin that links one of those addresses must carry its own copy. `css/idno-simple.css` and `css/idno-simple.min.css` are deleted with the onboarding pages (see above). `js/idno.js` and `js/idno.min.js` (the script of the look Idno 2026 replaced, with their source maps and the sources under `js/src/classes/` and `js/src/lib/`, and the Grunt `concat` target that built them) are deleted too: no template or page loaded them, and the two form templates that called their `Template`, `ImageTools` and `EXIF` globals (the image file input and the image picker) threw a ReferenceError on every file selection; the picture preview of those forms now comes from Idno 2026's script (the input) and a plain script of the picker page. A third-party theme or plugin that loads `js/idno.js` must carry its own copy. `Tests/Unit/Templating/StaticAssetsTest` fails for a shipped style sheet or script that nothing names. How to convert your own `.tpl.php` templates is in [Upgrading your plugin or theme's templates](../developers/plugins/upgrading.md); `.tpl.php` support ends in 3.0.
* **`render()` and `controller()` are not available in Twig templates.** TwigBundle's HTTP kernel extension is removed (a template draws no other request); `path()` of Symfony's routing stays.

### Pages that controllers serve

The home page (`/` and `/content/<types>`) is served by a Symfony controller, and `Idno\Pages\Homepage` is a deprecated shell that draws the same page through the same service; a plugin's page that extends it, or that takes the root with `hijackRoute()`, still works and logs one deprecation line a process. The StaticPages plugin no longer uses one: its class `IdnoPlugins\StaticPages\Pages\Homepage`, which extended the shell and took the root, is deleted, and a static page chosen as the home page now answers the new event `homepage/replace` (see [Replacing the home page](../developers/plugins/upgrading.md#replacing-the-home-page-the-homepagereplace-event)). A site that chose one sees the same page; the body class of that page is `idno_pages_homepage`, where it was `idnoplugins_staticpages_pages_homepage`, and the `page_class` of its page events is `Idno\Pages\Homepage`, where it was the deleted class; no deprecation line is logged for it. A chosen page the viewer may not read (private, in another group, a draft) gives the ordinary home page, where the old class redirected to `/` for ever. A chosen page that has been deleted (or is no static page) is dealt with by an administrator's first request for the home page: the setting is cleared and the stream is served at once, where the old class cleared the setting and redirected to `/`; a member's or visitor's request changes nothing. The site's statistics now count the event `homepage/replace` on every request for the root. Code that names the deleted class (a `hijackRoute()` of it, a subclass) must go. See [Pages that controllers now serve](../developers/plugins/upgrading.md#pages-that-controllers-now-serve). One header behaviour differs: the old router answered an XHR request of the home page with its own headers (`Content-Type: application/json` before the page's, `Expires: Mon, 26 Jul 1997 05:00:00 GMT`, two `Cache-Control` lines, `Pragma: no-cache` and a `Last-Modified` of the moment). An XHR GET or HEAD of the home page now gets the headers of the same request that is not XHR: the session's `Expires`, one `Cache-Control: no-store, no-cache, must-revalidate`, `Pragma: no-cache`, and the newest post's `Last-Modified`.

A post's permalink (every content type's address, and `/view/<id>`) is served by a controller too, and `Idno\Pages\Entity\View` is a deprecated shell that serves its POST, DELETE and webmentions through the same service; a content type of a plugin that registers its own pattern for that class, and a plugin's page that extends it, still work (a subclass logs one deprecation line a process). Changes you may see: a conditional request (`If-Modified-Since`) is answered `304 Not Modified` when its date is not before the post's last change, where it was answered 304 when the date was not after it (the comparison was the wrong way round: a browser holding a current copy got the page again, and one holding an old copy got a 304), a date that is not an HTTP-date is ignored, and a viewer who may not read a post is never told it is unchanged, and is answered with the same "this content isn't here" page (410) as for a post that is not there (a post the finders returned but the viewer may not read, which a plugin's read rule can make, was a 403: the address no longer tells which posts exist); an XHR GET or HEAD of a permalink gets the headers of the same request that is not XHR (the old router sent `Content-Type: application/json`, an `Expires` in 1997, two `Cache-Control` lines and a `Last-Modified` of the moment); a PUT or DELETE with no valid form token, to any page, is answered with the site's 403 page, and nothing is reported or mailed to the administrator (it was the reported 500 page, which anyone could trigger); and the JSON `{"location": ...}` that answers a signed API request is sent as `application/json`. See [Pages that controllers now serve](../developers/plugins/upgrading.md#pages-that-controllers-now-serve).

The shortlink of a post (`/s/<code>`) and the pages of a post's annotations (the list at `<post address>/annotations/` and `/view/<id>/annotations/`, one annotation at `.../annotations/<id>`, and the delete of an annotation) are served by controllers too, and their page classes `Idno\Pages\Entity\Shortlink`, `Idno\Pages\Annotation\View` and `Idno\Pages\Annotation\Delete` are deleted. **If a plugin of yours extends one of those classes, disable it before you upgrade**: the site cannot start while the plugin names a class that is gone. Core still registers the legacy pattern of each where it always did, with a placeholder in place of the class, so a plugin's registration of the same pattern or of an exact key is served as before. What you may see: the title of the list of annotations ("Annotations on: ...") is translated, where it was English whatever the language; a request to these addresses with a method the page does not take (a POST, PUT or DELETE to the shortlink or to the list, a GET of the delete address, a POST that asks to be handled as a DELETE with `X-HTTP-Method-Override`) and a request with a malformed `Host` are the site's 404 page, where they were an "Invalid token." redirect, the 403 page, the 501 page or the page itself; the JSON that tells a signed request where to go after a delete or a shortlink is sent as `application/json` (it was `text/html`); an XHR GET gets the headers of the same request that is not XHR; a `permalink` field of the delete that is not text is no permalink (it was a 500 page). A post that the person asking may not read is the same "this content isn't here" page (410) as a post that is not there, now checked again by the page itself. **A webmention can no longer take an address of your site, or replace an annotation made on it.** An annotation a webmention stored was keyed by the address the source page declares for itself (`u-url`), so a page could declare the address of a member's existing comment or like and overwrite it, or declare an address in the format the site invents and have its mention look made here. Such an address (any scheme, port or spelling of this site's host) is now ignored and the webmention's source is used; a webmention never replaces an annotation the site made. A webmention now records the page that sent it and replaces only an annotation that page sent: a second page that declares the first page's address is stored under its own, and the first annotation stays as it was (a repeated mention from one source still updates only its own, and a 410 from a source removes only its own). An author address of this site in a remote page's h-card is not stored, so a remote page cannot show a member of your site as the author of a comment. Annotations received before this remain as stored, and one stored without its source is still replaced by a mention that declares the same address. **Who may delete an annotation changes:** the author of an annotation may now delete it. Until now only the post's editor (or an administrator) could, and a member who had commented on or liked someone else's post was shown the delete link, and clicking it did nothing. The author is the member whose profile address an annotation made by the site records as its owner: the post page's like or reply, a Micropub annotation or an imported comment (those carry the new stored mark `made_here`; Micropub and imports name whom their sender chose). An annotation received as a webmention never counts. Annotations stored before the mark existed count when their address is their own key; a record a remote page forged that way before (see below) lets the member it names delete it, and nothing more. The post's editor and administrators keep their right, and the link is drawn only for those who can use it.

A member's profile (`/profile/<handle>`, its friendly content paths such as `/profile/<handle>/notes`, and `/actor/<handle>` where the ActivityPub plugin is not enabled) is served by a controller too, and `Idno\Pages\User\View` is a deprecated shell that serves the profile edit form's POST and the profile's webmentions through the same service; a plugin's page that extends it, or registers its own address for it, still works (a subclass logs one deprecation line a process). The ActivityPub plugin still takes `/actor/<handle>` for its own page. **A DELETE of a profile's address no longer deletes anything**: it looked the handle up as the id of an entity and deleted whatever held that id (an account, or a post), and never the profile of a handle; it is answered as a page with no DELETE handler answers it (a request with a valid form token is answered `501` and sent to the home page, a request with no token the 403 page). An account is deleted by an administrator from the Users page, which is unchanged. Other changes you may see: an XHR GET or HEAD of a profile gets the headers of the same request that is not XHR (the old router sent `Content-Type: application/json`, an `Expires` in 1997, two `Cache-Control` lines and a `Last-Modified` of the moment); the JSON that tells a signed API request where to go after it edits a profile is sent as `application/json` (it was `text/html`); and on a single-user site a webmention to the home page is passed to the profile's service, not to whatever page the legacy router finds at the profile's address. See [Pages that controllers now serve](../developers/plugins/upgrading.md#pages-that-controllers-now-serve).

The page that serves a stored file (`/file/<id>` and `/file/<id>/<name>`) is a controller too, and its page class `Idno\Pages\File\View` is deleted. **If a plugin of yours extends it, disable it before you upgrade**: the site cannot start while the plugin names a class that is gone. Core still registers the legacy pattern where it always did, still public, with a placeholder in place of the class, so a plugin page registered for it with `hijackRoute()`, with `addRoute()` of the identical pattern or of an exact key, or with a pattern that matched first still takes the path. The file is sent as it was: who may have it (a file attached to a post only to those who may read the post, an archive of the site only to an administrator), the three sets of caching lines, `Range` requests with exactly their bytes, the type and `nosniff`. The page streams the file, so a large file is never held in memory. What you may see: a public file's `Expires` is an HTTP date in GMT (it was a date with a numeric offset in the server's time zone); a download (a file the browser could run, or that is not a picture, a PDF, audio or video) is named after the last part of its address, so `/file/<id>/report.zip` is saved as `report.zip` (it was named after the file's id, and an address with no name is saved as `download`); a HEAD request reads nothing of the file; a file is dated by its own modification time (its `Last-Modified` was the time of the request) and a request with an `If-Modified-Since` that is not before it is answered "not modified" (it was answered so when the date was not after the change, the other way round), a revalidation of any file, a restricted or an archive of the site too, so is a 304 that carries the file's caching lines, also when it asks for part of the file, and a date that is not an HTTP date or comes beside an `If-None-Match` is ignored; a file attached to a post the person asking may not read is the 404 page of a file that is not there (it was a 403); a picture, PDF, audio or video is sent as its own type and every file but a PDF is sent with `Content-Security-Policy: sandbox`; a range that no byte of the file satisfies is answered with `Content-Length: 0`; a POST, PUT or DELETE to a file's address, a request with a malformed `Host` header and `/file//<id>` answer the site's 404 page (a POST was an "Invalid token." redirect, the others the 403 page or the file itself); an XHR GET gets the headers of the same request that is not XHR. See [Pages that controllers now serve](../developers/plugins/upgrading.md#pages-that-controllers-now-serve).

**A post's address has one layout, `/YYYY/slug`.** The "Permalink Structure" setting is gone from Admin, Site configuration (`permalink_structure`): a post's address is its year and its slug, which was the default, and a value a site stored for it is ignored (it does no harm: nothing reads it). If your site had chosen `/:year/:month/:slug` or `/:year/:month/:day/:slug`, every post's address changes to `/YYYY/slug`, and the old addresses keep working: a GET or HEAD of `/YYYY/MM/slug` or `/YYYY/MM/DD/slug` is answered `301` with the post's new address (a post that is not there, and one the person asking may not read, are the same "this content isn't here" page, status 410). The address of an ANNOTATION in an old layout (`/YYYY/MM/slug/annotations/<id>`, the list at `/YYYY/MM/slug/annotations/`, and the same with the day) is answered the same way, `301` to the annotation's address under the post's new one. Annotations that people made on the site (a comment or a like from a member) while it used an old layout were stored under the address the post had then: the annotation pages find them by their own id whatever address they were stored under, the post's pages print their address as the post has it now, and the delete link finds them; nothing stored is rewritten. What the site's old layout does NOT keep: the delete and Markdown (`.md`) forms of an old-layout address, and a POST to one, which are `404`. What a post is known by elsewhere does not change: its identifier (`uuid`, which is the ActivityPub object's `id` and the feeds' `guid`) was stored when the post was first saved and is `<site>/view/<id>`, whatever the layout was; only the `url` that ActivityPub, the feeds and syndicated copies carry is the new address, and a copy of it that another site remembers reaches the post through the `301`. A layout of `/:slug` or `/:id` was never offered; an address in one is no longer answered at all. A plugin that calls `\Idno\Core\Idno::site()->config()->getPermalinkStructure()` gets `/:year/:slug` (the method is deprecated); `\Idno\Common\Entity::getPermalinkRoute()` is the fixed pattern.

The feeds (`/feed.xml`, `/feed`, `/rss.xml`), the search (`/search`) and the tag pages (`/tag/<tag>`) are served by the same controller, and their page classes `Idno\Pages\Feed`, `Idno\Pages\Search\Forward` and `Idno\Pages\Search\Tags` are deleted. **If a plugin of yours extends one of those classes, disable it before you upgrade**: the site cannot start while the plugin names a class that is gone. Core still registers the legacy pattern of each of those pages (`/feed\.xml`, `/feed/?`, `/rss\.xml`, `/search/?`, `/tag/([^\s]+)\/?`) where it always did, with a placeholder in place of the deleted class, so the legacy router's own rules decide what a plugin's registration does: a plugin page registered for one of those paths with `hijackRoute()`, with `addRoute()` of the identical pattern or of an exact key (`/feed.xml`), or with a pattern that matched first, still takes the path, as before (in the spellings of the address that the legacy router itself resolves to the plugin's page: with an exact key such as `/feed.xml`, `//feed.xml` is now the site's 404 page, where it reached core's feed); a page registered after core's with any other pattern, however broad (a short-link page, a catch-all), did not take these paths then, because core's page was first, and does not now. Addresses and output are the same, with these changes: a tag is decoded once (`/tag/a%2Bb` lists the tag `a+b`, where it listed `a b`), a trailing slash is not part of the tag (`/tag/books/` lists `books`), a tag that is only slashes is not a tag (`/tag//` was the tag `/`, listing `#/`, and is the site's 404 page), and the tag wins over a `q` in the query string everywhere the page shows it; a feed's page events fire once, and its `Link` headers (the webmention endpoint, the hub) are sent once, where they were sent twice; a POST, PUT, PATCH or DELETE to one of these paths, and a request with a malformed `Host` header, answers the site's 404 page (a POST to `/feed.xml` or `/search` was a redirect to the home page); a webmention to one of these addresses is answered `target_not_found` (it was refused with `source_not_supported` or `target_not_supported`); `/search?q[]=x` redirects with an empty query (it was a 500 page); and an XHR request of these pages gets the headers of the same request that is not XHR. See [Pages that controllers now serve](../developers/plugins/upgrading.md#pages-that-controllers-now-serve).

The webmention endpoint (`/webmention/`) is a controller too, and its page class `Idno\Pages\Webmentions\Endpoint` is deleted (a plugin that extends it stops the site booting until it is disabled: see `docs/developers/plugins/upgrading.md`). What a site owner sees: a mention is received as nobody whoever sends it (a mention sent with a member's cookie no longer reaches a post only that member may read); the refusals are sent as `application/json` (they were `text/html`), with the code `source_not_allowed` for a source the site may not fetch (it was `target_not_supported`, with the self-mention text); a mention to a shortlink (`/s/<code>`) is accepted again as a mention of the post it names; a mention of `/index.php` is a mention of the home page and one of `<post address>.md` a mention of the post; a source or target that holds white space or a control character, or is over 2048 bytes, is refused with `unknown_error`; PUT and DELETE of the endpoint are the 404 page. A mention of an address that names nothing a visitor may see (a post that does not exist, a private or draft post, an account or shortlink that does not exist, the home page of a multi-user site) is `target_not_found`, the same answer for each, before the sender's page is fetched. A like, a reply, an unlike, a deleted annotation, a Micropub annotation or a webmention no longer sends an ActivityPub `Update` of the post to your followers, by any path (only an edit of the post does); an unlike by a member who cannot edit the post, which was not saved, now is, and a webmention that changes nothing stored saves nothing. The JSON of a refusal, which repeats the sender's address, is no longer sent as HTML. The rule for which addresses of the site take mentions is the one stated above (the site's own host, strictly): the endpoint applies it before it fetches the sender's page, so a mention that will be refused costs no request.

The WebSub callback (`/pubsub/callback/<subscriber>/<subscription>`, the address a hub verifies your subscriptions to other sites' feeds with and delivers their content to) is a controller too, and its page class `Idno\Pages\Pubsubhubbub\Callback` is deleted (a plugin that extends it stops the site booting until it is disabled: see `docs/developers/plugins/upgrading.md`; the name `Idno\Pages\WebSub\Callback` is only the label the page's events and body class carry). The address does not change. What you may see: a hub can now verify a subscription on a private site (the walled garden refused it); a verification must name the topic you subscribed to and arrive within a day of the follow, and it removes the subscription from the list the site keeps of those it is waiting for, keeping the list in the shape the next follow needs (before, any topic was confirmed, an entry never expired, and one verified subscription broke the following of the next one); an unsubscription is verified (it never was); a request that is not a verification, a challenge over 512 bytes, or a list that is not what the callback reads is the 403 page, where some were a 500 page; a subscriber that is not a member is the 410 page; a HEAD request removes nothing. **A delivery is accepted only for a subscription you have** (you follow the user and they have a hub: before, a post to any two user ids was accepted), is handed to the listeners of the event `websub/received` (it was `pubsubhubbub/ping`, now `websub/ping`, which publishes your own posts to your own hub), acts as nobody, and a body over the `webservice_max_download` limit is refused with `413`. **New subscriptions are signed.** When you follow someone whose hub is https the site sends it a random secret, and the hub's deliveries must carry a valid signature, or they are ignored. Subscriptions you made before this upgrade, and those to a hub on plain http, have no secret: unfollow and follow again to get one. The subscription request is not redirected (a hub that answers it with a redirect, to another https address as well, has not made the subscription: the site logs a warning that says so, and the member follows again once the hub's address in the followed site's feed is the one that answers), and following again someone whose hub has become plain http makes the subscription with no secret. A hub that signs its deliveries only with SHA-1 has the deliveries to a new subscription ignored. PUT, DELETE and a request with a malformed `Host` are the site's 404 page.

A member's drafts page (`/drafts/`) is a controller too, and its page class `Idno\Pages\Drafts` is deleted (a plugin that extends it stops the site booting until it is disabled: see `docs/developers/plugins/upgrading.md`). It shows a signed-in member's own drafts and nothing else; a visitor is answered with the site's 403 page, as before, and a signed request acts as its member. Core still registers `/drafts/?` where it always did, with a placeholder in place of the class, so a plugin's page registered for that address still takes it. What differs: a request with a method the page does not take (a POST, a PUT, a DELETE) or with a malformed `Host` is the site's 404 page (a POST was a redirect to the home page), and an XHR GET gets the headers of the same request that is not XHR.

**The feed reader is removed.** Following a feed to read its items on your site could not work on any supported PHP (the reader's parser calls a function that has been an error since PHP 8, so adding a feed answered the 500 page, and nothing linked the pages), so it is deleted: `/following/`, `/following/add/`, `/following/confirm/`, `/following/refresh/` and `/stream/` are the site's 404 page, a plugin of yours that registered its own page for one is no longer shadowed by core's, and a plugin that extends or names the reader's classes (`Idno\Core\Reader`, `Idno\Entities\Reader\Feed`, `FeedItem`, `Subscription`, `Idno\Pages\Following\*`) stops the site booting until it is disabled (see `docs/developers/plugins/upgrading.md`). Following a *person* is unchanged; the follow bookmarklet no longer offers to subscribe to their feed afterwards. **Nothing you stored is deleted.** The upgrade still copies the records of the 1.x `reader` tables into `idno_reader` (the feed reader's feeds, items and subscriptions), they stay in your database and in the archive the admin exports, and nothing shows them. Their `type` is the class name, not an alias. A database made by an earlier 2.0 development build also keeps the indexes it made on `idno_reader` (`ix_feed_url`, `ix_slug` and the others); they are unused, and a new database has only `ix_access` there.

The small public endpoints are controllers too: `robots.txt`, the web app manifest (`/chrome/manifest.json`), the service worker script, WebFinger (`/.well-known/webfinger`), the mention search (`/search/mentions.json`) and the form token endpoint (`/service/security/csrftoken/`). Their page classes `Idno\Pages\Txt\Robots`, `Idno\Pages\Chrome\Manifest`, `Idno\Pages\Chrome\ServiceWorker`, `Idno\Pages\Webfinger\View`, `Idno\Pages\Search\Mentions`, `Idno\Pages\Service\Security\CSRFToken` and `Idno\Pages\Entity\Bookmarklet` are deleted. **If a plugin of yours extends one of those classes, disable it before you upgrade**: the site cannot start while the plugin names a class that is gone. Changes: `/bookmarklet.js` is gone (404; it answered an HTML fragment as `text/html` and nothing linked it); `/service-worker.js` now serves the shipped script `js/service-worker.min.js` (it was a 500 page unless the Grunt build had written `js/service-worker.js`); `/search/mentions.json` is `application/json` (it was `text/json`); the form token endpoint needs no `url` (a request without one was a 500 page) and answers `Cache-Control: no-store`; `robots.txt` is sent as `text/plain; charset=UTF-8`; WebFinger answers `resource[]=x` with the 404 page (it was a 500 page). POST, PUT, PATCH and DELETE of these addresses (a POST to `/.well-known/webfinger` was a redirect to the home page), and a request with a malformed `Host` header, answer the site's 404 page; a webmention to one of them is answered `target_not_found`; an XHR request gets the headers of the same request that is not XHR. Core still registers the legacy pattern of each of these pages where it always did, with a placeholder in place of the deleted class, so a plugin page registered with `hijackRoute()`, with `addRoute()` of the identical pattern or of an exact key, or with a pattern that matched first still takes the path of every one of them but WebFinger, and one registered after core's did not and does not. WebFinger's registration is made after the plugins' (as it always was), so core's own pattern replaces a plugin's identical one and WebFinger stays core's unless the plugin uses an exact key or a different pattern it registered before core's. `/bookmarklet.js` has no registration: it is the 404 page unless a plugin's pattern matches it. See [Pages that controllers now serve](../developers/plugins/upgrading.md#pages-that-controllers-now-serve).

### Names that changed

#### WebSub (formerly PubSubHubbub)

The protocol that tells a hub when a site has published something was renamed WebSub when the W3C made it a standard, and Idno calls it that
everywhere: the settings page ("WebSub hub"), the documentation, the code and the tests. Nothing needs doing on a site: the hub setting (`hub`) is the
same setting, the address hubs call back (`/pubsub/callback/<subscriber>/<subscription>`) is the same address, so subscriptions made before the upgrade
go on working, and the fields stored on members (`pubsub_pending`, `pubsub_self`, `pubsub_hub`, `pubsub_secrets`) keep their names. No data is migrated.

For plugins, the earlier names still work, except the page class that was deleted, and are deprecated:

| Earlier name | Name now |
|---|---|
| class `Idno\Core\PubSubHubbub` | `Idno\Core\WebSub` |
| class `Idno\Pages\Pubsubhubbub\Callback` | deleted (see "Pages that controllers serve"); the page's name in its events and body class is `Idno\Pages\WebSub\Callback` |
| event `pubsubhubbub/ping` | `websub/ping` (`Idno\Core\WebSub::PING_EVENT`) |

* The earlier class name of the component is an alias of the new class, so `instanceof`, static calls and `new` behave the same under either name, and
  the autoloader finds it from its earlier file name.
* The two event names are one event. A listener added for either name is called when either is triggered, and a listener added for both is called
  once. Events that were waiting in the queue under the earlier name when the site was upgraded are still delivered.
* No template was named after the protocol, so there is nothing for a theme to rename. What a theme can see: the callback page's body class made from the name of its page class, `idno_pages_pubsubhubbub_callback`, is `idno_pages_websub_callback` (the page is answered to hubs only: a challenge is plain text), and the `page_class` of its events is `Idno\Pages\WebSub\Callback`; the classes made from its address (`page-pubsub...`) are as they were. The labels of the hub setting changed ("WebSub hub"), so a
  translation of the earlier labels needs the new ones. The comment `<!-- WebSub hub -->` in the head of a page replaces the earlier one.

### The built-in look loads no jQuery

Idno 2026 (the built-in look) loads one script, `js/idno-2026.min.js`; no template of it calls jQuery or a plugin of it, and no page of the site loads jQuery (the onboarding pages, the last that did, are gone). What changes for plugins and themes that override templates of the look:

* **Assets deleted.** `templates/default/assets/mediaelementplayer.html.twig` and `templates/default/assets/fitvids.html.twig` (the MediaElement.js player and the FitVids jQuery plugin, `vendor/npm-asset/vanilla-fitvids/jquery.fitvids.js`, which every page loaded), the Media plugin's `IdnoPlugins/Media/external/wavesurfer/` (the whole vendored WaveSurfer library), `IdnoPlugins/Media/templates/default/media/shell/head.html.twig` and `IdnoPlugins/Media/templates/default/media/shell/footer.html.twig` (the plugin no longer extends `shell/head` and `shell/footer`), `templates/default/js/mentions.html.twig` (a commented-out script: the @-mention autocomplete is in the look's script) and `js/src/Idno.js` (an unused source file). The default of the `assets` setting is now empty; a stored `assets` entry that names a deleted template draws nothing. The Photo plugin no longer registers the `exif-js` script on every page.
* **Media player.** An audio or video post plays in the browser's own `<audio controls>` / `<video controls>` element, with the file's address in `src`. The waveform is gone. A theme that styled `.waveform-player`, `.audio-play-button` or `.known-media-element` can drop those rules.
* **Static pages are edited as source.** The page's body is a plain `<textarea name="body">` of HTML, not a rich-text editor: the editor only keeps the markup it knows and would rewrite a page that holds a form, an `id`, a `<style>` block or a frame. The stored body is exactly what was typed. A browser submits a text area's line breaks as CRLF, so a page saved from this form stores CRLF line breaks; it renders the same. The TinyMCE script that form used to start is gone.
* **Cancel buttons** of the Media, RSVP and static page forms are links back to the post or the home page (the `hideContentCreateForm()` they called does not exist).
* A template of your own that still calls `$(...)` in the built-in look does nothing; write it in plain DOM JavaScript or Alpine. The Composer packages `npm-asset/mediaelement`, `npm-asset/exif-js`, `npm-asset/vanilla-fitvids`, `npm-asset/tinymce--tinymce-jquery` and `tinymce/tinymce` are removed from `composer.json` (and with them `vendor/npm-asset/mediaelement/`, `vendor/npm-asset/exif-js/`, `vendor/npm-asset/vanilla-fitvids/`, `vendor/npm-asset/tinymce--tinymce-jquery/` and `vendor/tinymce/`); a third-party plugin that loads one of them must require it itself. `npm-asset/jquery` stays for the onboarding shell.

### Outbound requests: `Webservice`

`Idno\Core\Webservice` keeps every public static method, its parameters and its result array (`header`, `content`, `response`, `effective_url`, `error`), and the `webservice:headers` event still fires. In new code, inject `Symfony\Contracts\HttpClient\HttpClientInterface` instead (a URL that a remote party supplied, such as a webmention source or an ActivityPub actor, goes through the client injected as `$remoteClient`, or `Webservice::safeSend()`, which refuse loopback, private, link-local and reserved addresses on the request and on every redirect). What differs from 1.x:

* **A certificate that does not verify is an error.** Verification used to be switched off whenever redirects could be followed. `error` says why; `disable_ssl_verify` still turns verification off.
* **Time limits.** A request that receives nothing for 10 seconds, or lasts 60 seconds, fails with a non-empty `error`.
* **A larger response is cut at the limit.** `webservice_max_download` (default 10 MB) was only checked against a declared `Content-Length`; a response with none is now cut at the limit, with a non-empty `error`. A response that declares a length over the limit is refused as before, except for a HEAD, which is never refused for the length it declares: the old client refused it, which made large files impossible to probe.
* **Remote-party URLs, and URLs members type.** A fetch through `safeSend()`, `safeFileGetContents()` (the same as `file_get_contents()`, on that client) or the `$remoteClient` service fails when any hop resolves to a private or reserved address (unless `http_allow_private` allows it, below). These are used for webmention sources and targets, ActivityPub actors, inboxes and keys, Micropub media URLs, feeds, WebSub hubs a followed site advertises, and URLs a logged-in member types or shares (sharing or bookmarking a URL, link previews, Bridgy). A member can no longer unfurl, share or bookmark a URL on the site's own private network or on localhost. A site that is itself served from a loopback or private address (a development or intranet install) can likewise no longer discover and subscribe to the hub of a profile or feed on that same address, since those fetches go through the client that refuses private networks. URLs the site's admin configures (the WebSub hub, a webhook) are unchanged; a webhook from a member's own list is a URL a member typed, and goes through the client that refuses private networks.
* **`http_allow_private`, the way back from the private-network refusal.** A new setting, read from `config.ini` or the environment only (never from the settings saved in the database): a list of IP addresses and CIDR ranges (IPv4 or IPv6) that remote-party and member URLs may reach although they are private, or the single entry `*`, which turns the refusal off. Intranet, single-user, split-horizon-DNS and development installs, which lose webmentions to their own posts, feeds, sharing and hub discovery under the refusal, set it: `http_allow_private[] = "192.168.1.0/24"` in `config.ini`, or `IDNO_HTTP_ALLOW_PRIVATE="192.168.1.0/24,fd00::/8"` in the environment. An entry that is not an address, a range (with a prefix length of 1 or more) or `*` is an error when the first remote request is made. `*` removes the protection against a remote party or a member steering the server at its own network: use it only on a site whose every member is trusted. A proxy from `proxy_string`, or from the standard proxy environment variables when that is empty (`http_proxy`, `https_proxy`, `all_proxy`, and `HTTP_PROXY` on the command line only), is recognised: its own address is not refused as the address Idno connected to, so a site behind a proxy works without further configuration. The target's address is checked before each request wherever the server can resolve it. Behind an HTTP proxy or a `socks5h` proxy the proxy resolves the target's name for the real connection, so the server's own lookup is only a pre-check: the protection against a name that resolves differently for the proxy (DNS rebinding) does not apply, and anything the proxy can reach, including services on the proxy host's own loopback, can be reached through a hostname; enforce egress rules at the proxy. With a `socks5` proxy (names resolved by the server) or no proxy, the address checked is the address connected to. A prefix length of 0 (`0.0.0.0/0`, `::/0`) is refused like any invalid entry: `*` is the way to switch the check off, and use it if the server cannot resolve external names at all.
* **`trusted_proxies`, the proxies whose forwarded headers are believed.** A new setting, read from `config.ini` (`trusted_proxies[] = '10.0.0.0/8'`) or the environment (`IDNO_TRUSTED_PROXIES`, comma-separated) only, never from the settings saved in the database: IP addresses and CIDR ranges, or `REMOTE_ADDR` and `PRIVATE_SUBNETS`. With it, `X-Forwarded-Proto` and `X-Forwarded-Port` are believed from those proxies alone. **A site that sets nothing behaves as before**: `X-Forwarded-Proto: https` is believed from anyone, so a site behind a proxy keeps its secure session cookie and its https address, and a visitor can still claim https for their own request. Sites behind a proxy should set it, and the proxy must overwrite `X-Forwarded-Proto` (and `-For`, `-Port`) rather than append to what the client sent, because the leftmost value is believed. With the setting on, port 443 alone no longer means https (the web server's `HTTPS` variable, with any value but `off`, `0` or empty, or the proxy's header does). `*` and a range with a prefix of 0 are refused, unlike in `http_allow_private`; `REMOTE_ADDR` trusts whichever address made the request. An entry that is not an address or range stops the WHOLE site until it is fixed: visitors get a generic error page and every console command exits 1; the message naming the setting and the entry is in the error log and on the console. Without the setting, `HTTPS` counts only when it is `1` or `on`.
* **No compression.** The client sends `Accept-Encoding: identity`, as the old one effectively did (it asked for none): the new client would otherwise decode a compressed body a chunk at a time, and a few kilobytes of gzip can decode to megabytes in one chunk, which `webservice_max_download` could not bound. A server that compresses anyway has its bytes returned as they were sent.
* **`error` holds Symfony's message, not curl's.** It is empty when a response was received and kept whole; it is not empty when no response arrived, or when one was refused or cut for its size (`response` is then its status). `send()` never throws for a transport failure.
* **Addresses the old client tolerated are errors.** An address with no scheme (`example.com/page`), a scheme other than http or https, a backslash, or a leading space gives an error result (`response` 0) instead of a request. Pass a full URL, or run the address through `Webservice::sanitizeURL()` first.
* **Headers given by name are sent.** `['Content-Type' => 'application/json']` used to be silently dropped (only `'Name: value'` lines reached curl); it is sent now, for every verb (the WebSub hub ping passes its Content-Type this way). A line with no colon is not sent.
* **After more than five redirects**, `file_get_contents_ex()` returns the failed result and `file_get_contents()` returns `false`; neither throws (they used to raise a PHP warning, an exception on a site with `pedantic_mode`).
* **No Referer on redirects**, and `Authorization`, `Cookie`, `Signature`, `X-Idno-Service-Signature` and `DPoP` headers are not sent to a different host on a redirect.
* **No cookie jar.** The `cookie_jar` setting is gone and nothing is written to the temporary directory.
* **`getLastRequest()`** returns the request line and the headers Idno sent, rebuilt, not curl's byte-exact copy, with the values of `Authorization`, `Proxy-Authorization`, `Cookie` and `Signature` replaced by `[redacted]`.
* **Micropub media downloads have limits.** When a Micropub client gives the site a URL to download a photo, audio or video from, the download is made by the client that refuses private networks, is cut off after 10 seconds without data or 60 seconds in all, and is refused when the file is larger than `webservice_max_download` (10 MB by default): the download fails, as for any other failed download, and no partial file is kept. Raise `webservice_max_download` if your Micropub clients send larger files by URL.
* **The Standard.site (AT Protocol) plugin** makes its requests through the client that refuses private networks, because the addresses it contacts (a handle's server, the personal data server and authorization server a DID document names) come from a member's input and from remote documents. A response is read up to 1 MiB and cut there, which these small JSON documents never reach; a longer one fails as a document that does not parse. A request that gets a redirect on a POST (a token or authorization request) is not followed, as before; a GET follows up to five. A request fails after 30 seconds in all. Its error messages no longer quote a server's raw response: they hold the server's error text, or the status code.
* **`webservice_exec()` is removed** (it took a curl handle; nothing in Idno called it).

### Import and export

The import and export pages use bounded services in `Idno\Portability`, which the container wires (all public; they need the site booted):

* `ArchiveExporter::export($requestedByUuid)` makes the administrator's complete archive as one zip file, from files written to a private working directory (mode 0700, an unpredictable name, removed also on failure), copies attached files as streams (never read whole), and stores it in the file store with the metadata `restricted = admin`. `exportToFolder()` and `zip()` are its two halves. `FeedExporter::rss($hidePrivate, $userUuid, $wxr)` yields the RSS or WXR document in chunks (`stream()` gives a readable stream for a page that needs the size); nothing is written to the temporary directory.
* **The full archive needs the PHP `zip` extension** (`ext-zip`, a Composer suggestion, not a requirement). Without it the export page shows a notice instead of the create button, and the archive is not made; the RSS and WXR downloads and the imports do not need it. Install it (`php-zip`) on the web server's PHP and the worker's.
* `WordPressImporter::import($path, $ownerUuid)` and `BloggerImporter::import(...)` (which also reads RSS) read the file from its path through `SafeXml::load()` (a size limit of 32 MiB, no document type declaration or entity, no network) and return `['posts', 'comments', 'media', 'skipped']`; a file that cannot be read or holds no post is zero posts, never an exception, and an item that fails is skipped, logged (the exception's class and the item's title, cut) and counted, while the import goes on. A staged upload is run once: a job that finds it already started (a message put back after a worker was killed, or a duplicated job for the same upload) refuses it and mails the administrator to check the posts before uploading the file again. Uploading or submitting the same file twice is not caught (each submit stages a new upload): importing the same file twice creates its posts twice. Pictures go through `ImportedMedia` (the remote HTTP client, `webservice_max_download`, http and https on their own ports only, the source domain and its subdomains only, jpg, jpeg, png, gif and webp, and the bytes must really be such an image).
* `PortabilityJobs` runs the work and mails the result. The pages queue it as the events `portability/export` (data: `user`) and `portability/import` (data: `user`, `file`, the id of the staged upload, and `type`, `wordpress` or `blogger`) when `Idno::site()->queue()->isAsynchronous()`, run as the user who asked; otherwise it runs after the page has answered, without the old ten-second wait. A job never throws: any failure (an `\Error` too) is logged, clears what it set and sends the failure mail. The import's upload waits in the file store, restricted to administrators, and is removed when the import ends.
* **Nothing an import brings in is announced.** While an importer runs, `Idno::importInProgress()` is true (a flag on the `Idno\Portability\ImportMode` service, reset when the import ends, so a long-lived worker is not affected afterwards). The ActivityPub and Standard.site hooks on `saved` and `updated`, `Entity::syndicate()`, the WebSub ping and `Webmention::pingMentions()` honour it. A plugin that announces a new post from a `saved` listener should ask it too. The `IDNO_NOMENTION` constant still stops webmentions, for scripts that define it.
* **Posts send their webmentions through the queue.** Every bundled content type now sends the webmentions of a saved post as the queued event `webmention/sendall`, through `Idno\Core\Webmention::queueMentions($url, $text)`, so with the asynchronous queue a save no longer waits for the sites its text links to (a post with many links used to be able to reach PHP's `max_execution_time`); with the default queue the event runs at once, in the request, as before. A plugin that announces its own content type should call `queueMentions()` instead of `pingMentions()`, which still works and sends at once. The helper sends nothing on a site that is not public, while an import runs, or when the request carries `nomention` (the worker has no request to ask). One link that fails no longer stops the links after it. Deleting a draft sends nothing (its address was never public); deleting a published public post still tells the sites it linked to.
* **Files with the metadata key `restricted`** (whatever it holds) are served by `/file/<id>` to administrators only: anyone else gets 403 before anything is read, and the response is never cached. Use it for any file that must not be public.
* `Idno\Portability\SettingsRedactor` is the one rule for which settings are secrets (passwords, keys, tokens, JWT and HMAC values, authorization, cookies, sessions; user names and passwords inside addresses; a webhook's address is reduced to its scheme and host); the diagnostics page (its configuration, `$_SESSION` and `$_SERVER`) and the archive's `config.json` both apply it, and `config.json` leaves out every setting your `config.ini` or environment defines.
* `Migration::archiveExportFolder()` (deprecated) now makes its zip in a private directory of its own in the temporary directory and returns the path in it, not `<temporary>/<host>.zip`; remove the file and its directory when you are done.
* `File::getFileDataFromAttachment()` is removed: nothing in Idno called it any more (the archive export fetches an attachment the file store does not have itself, through the site's own client for the site's origin and the remote client, which refuses private addresses, for any other). A plugin that needs the bytes of a stored attachment uses `File::getFileDataByID($id)`; for an address, `Idno\Core\Webservice::safeFileGetContents($url)` (an address a remote party supplied) or `Webservice::get()` (one the site chose).

A queue worker now has the site's host (the host of the `url` in `config.ini`): it was empty, so the worker's upload directory, which is named after the host, was not the one the pages use.

### What Idno sends to other servers

What a site sends to other servers may change when the change is an improvement that stays compatible with ActivityPub. These changes are deliberate:

* **An ActivityPub `Create` is published when its post was.** The activity's `published` used to be the moment the activity was built, a second or more after the post's own `published` (and, for the outbox, the moment the outbox was asked for, so it changed on every request). It is now the post's creation time, the same value as the object's `published`, so a `Create` built again, or listed in the outbox, is the same each time. Remote servers read the object's `published`, which is unchanged.
* **An ActivityPub `Update` says when the post was last changed.** Its `published` is the post's last-saved time (the object's `updated`), or the time the post was published when it was never edited, where it used to be the moment the activity was built. The object's `updated` is now sent only when it is later than `published` (a post saved for the first time sent one when the clock ticked during the save). `Delete` and the acceptance of a quote request still carry the moment they are built, and the follow `Accept` still carries no time. Activity ids, addressing, the `@context` and signatures are unchanged.

* **A post's address, asked for as ActivityPub, answers with the post.** A server that fetches a post by its address or its `id` (`/view/<id>`), to show a reply to it or a quote of it, is sent the post as an ActivityPub object, the one that was delivered to followers (with its interaction policy, its quote terms and, for an article, its name). It was sent the post's author. Only a public, published post is given; a draft, a post for the members or only for its author, and any page that is neither a post nor a member (the home page) answer 406 with `{"error": ...}` to a request that asks for ActivityPub, and a post the visitor may not read, a deleted post and a missing one answer 410 as the page does. A member's profile address answers with the actor document, as `/actor/<handle>` does, which now has the same contents at both addresses. An answer to an ActivityPub request carries `Access-Control-Allow-Origin: *`, and one that is an error (a 403, 404, 406 or 410) is plain `application/json`. The `<link rel="alternate" type="application/activity+json">` in the head of a post's page now names the post's own address (it named its author's actor); a profile's names the actor, and a page that is neither a post nor a profile has none. Every page whose type is chosen from the request's `Accept` header (every page) now sends `Vary: Accept`, so a cache keeps the page and the ActivityPub or JSON form apart.

* **A check-in whose location is protected names the place nowhere.** A member can protect the location of a check-in for 24 hours ("Protect my location for 24 hours"). A visitor who is not signed in was told "somewhere near..." and shown an inexact position, but the place still reached them in the post's address (made from its title), in the page's microformats and structured data, in RSS (with the exact position), JSON Feed, JSON, KML and the Markdown form, and in search, which looks in the stored title. The inexact position was also a new random one for each request, so enough requests averaged out to the exact one. Now, while the location is protected, a visitor, and so every other server, gets no place name and no address anywhere and a position rounded to about a kilometre that is the same each time; members who are signed in see everything; once the 24 hours are over everybody does. The post fetched by address, the outbox and the delivery to followers carry no `location` for a protected check-in. A check-in made with a protected location now has an address that does not name the place (`/2026/checked-into-somewhere-near`). **A check-in that exists keeps its address and its stored title:** one made before this release keeps the address and the title that name the place, so a search by the place name still finds it, and a visitor who is given its address is told the place name by the address itself. Edit the check-in and save it to make its stored title neutral; its address cannot be changed without breaking the links to it, so a member who wants a past check-in not to name the place should delete it and check in again.

* **A check-in's page is dated by the end of its protection.** The `Last-Modified` of a check-in whose location was protected for 24 hours moves to the moment the protection ended, so a browser or a cache that kept the page from inside the 24 hours asks again and is told the place; it was the time of the last save, which never moved.

* **A quote of a post can be verified by other servers.** The address of the QuoteAuthorization stamp held the two posts' addresses percent-encoded in its query string, which Mastodon rewrites before it requests it and then rejects, so a quote of a post of this site showed as unavailable to everyone but the person who quoted. A stamp's address is now `/activitypub/quote-stamp/<quoted>/<quoting>/<signature>` (the earlier address is still served). A quote request is accepted, and a stamp served, only for a public, published post of this site; the Accept sent back holds the request's ids only.

### What behaves differently

On a MySQL, MariaDB or SQLite site, `db()` and the entity finders behave differently from the old
classes in these ways, all deliberate:

* **A query MySQL cannot run counts 0.** A search the old code turned into invalid SQL, or that MySQL rejected for its value (for example a `created` value that is not a date, which is now checked before the query is sent, on every database), finds nothing as before, but `countRecords()` and `countObjects()` now return `0` instead of `false`.
* **Fewer error-log lines.** Those unanswerable queries, and any query or write on a collection (table) that does not exist, are no longer logged; database errors on queries that do run are logged as before.
* **A save the database refuses returns `false`.** `saveRecord()` and `saveObject()` return the id only when the record was really stored. When the database refuses the data (for example a record with another record's `uuid`, new or re-saved, or, on MySQL and MariaDB, an `_id` longer than 36 characters or a record nested more than 100 levels deep, 31 on MariaDB), they return `false` and store nothing (an update leaves the previous version, and the other record is untouched). The old code returned the id even though nothing was stored, so `Entity::save()` reported success and fired `saved` or `updated` (and federated the post); now it returns `false` and fires neither. Check the return value of `save()`. (The old code on MySQL also overwrote the other record when an existing record was re-saved with its `uuid`.)
* **An empty condition on `access` or `entity_subtype` no longer removes the filter.** A search array passed to `getObjects()`, `countObjects()` or `getFromX()` whose `access` or `entity_subtype` condition comes to nothing (`[]`, `['$in' => []]`, an operator with an empty value) used to remove the reader's access check (or the type filter) entirely; it is now ignored, so the reader's access groups (or the requested types) still apply. A non-empty condition on those fields still replaces the default one, as before.
* **Records whose class no longer exists are left out.** `getObjects()` no longer returns `false` in their place (`getFromX()` already left them out). Counts still include them.
* **`isHiddenByPublishStatus()` overrides are not consulted by `getObjects()`.** Drafts and other unpublished entities are hidden by the standard rule (visible to their owner and to admins only); an entity class that overrides `isHiddenByPublishStatus()` still has its override applied by `canRead()`, but not when entities are looked up.
* **A string `$readGroups` works.** Passing one access group as a string to `getObjects()` now means that group; the old code failed and found nothing.
* **A record whose `created` is not a timestamp is refused.** `saveRecord()` returns `false` (and logs why) for a record whose `created` is not a number of seconds; the old code failed with a PHP `TypeError`.
* **A lost database connection is replaced.** After the connection to MySQL is lost (a long-running process that outlives the server's `wait_timeout`, a server restart), the first query fails as before (logged, the usual failure value), and the next one runs on a new connection by itself; `getClient()` then returns the new connection's `PDO`, so do not keep the `PDO` it returned earlier. The PHP session handler stays on the connection it was given when the request started and is not reconnected.
* **`getObjects()` reads the ignore-access flag once per call**, when it builds the query, where the old code read it again for each entity it returned. Changing it with `setIgnoreAccess()` from code that runs while the results are being built (an entity's `loadFromArray()`, for example) no longer affects the rest of that call.
* **Only database failures become a failure value.** As before, each method turns a failure of its database statement into its old failure value (`false`, an empty array) and logs the driver's message. Any other exception raised inside it propagates as it did with the old code: one from the session's access-group lookup or its `permission:read:ids` event, from loading an entity (`loadFromArray()`), from `canRead()`, from an event listener, or a programming error. (An `\Error` thrown while an entity is constructed or loaded is still logged and the record skipped, as before.)
* **A plain list, an empty array or an unknown operator as a field's value finds nothing.** A search array whose value for a field is an array must be a map of the operators `$not`, `$in`, `$lt` and `$gt` (`['$in' => ['a', 'b']]`). A plain list (`['a', 'b']`), an empty array, an unknown operator (`$regex`, `$ne`, `$exists`), alone or beside known ones, and an operator whose value it cannot use (`['$in' => []]`, a list for `$lt`) used to be dropped silently, leaving the rest of the query to run (so a lookup meant for one value could match the newest record instead). The whole search now finds nothing, as the next item describes. A plugin that passed a list meaning "any of these" writes `['$in' => $list]`. `$lt`, `$gt` and `$not` with `0` or an empty string now compare with it instead of being ignored; a `$not` of an empty `$in` still excludes nothing. A viewer with no read group reads nothing.
* **The finders take text only.** `Entity::getByID()`, `getByUUID()`, `getByShortURL()`, `User::getByEmail()`, `getByHandle()`, `getByProfileURL()` and `UnfurledUrl::getBySourceURL()` return `false` for a value that is not a non-empty string (an array a request sent, for example) without querying.
* **Invitations are for administrators.** An invitation (and the code in it) is stored with an access value no group has, is readable by administrators only (its `/view/<id>` address is a missing page for everyone else) and serialises to nothing. `Invitation::validate()` and `getByEmailAndCode()` need a string email and code and compare the code with every invitation for the address; a plugin that looked an invitation up with `Invitation::get()` or `getByID()` as a visitor must use `Invitation::unrestricted(fn () => ...)`. Invitations saved before this change keep their old access value until the registration lookup or the administrators' list reads them, which makes them administrators' invitations; their `canRead()` refuses everyone but an administrator all the same. An invitation has no title, description or address and is never federated.
* **Search arrays that cannot be understood find nothing.** A search array with an operator applied to something it cannot use (an array where a value is expected, `'$not' => ['$in' => []]`, a non-array `$in`, ...) finds nothing (`getRecords()` returns `false`, `getObjects()` an empty array, the counts `false`) and logs one warning naming the method and the query's shape (never its values).

The new tables also change what some queries match:

* **Items with the same `created` time come back in a fixed order**: the one with the greater id first (also from page to page). The old order was undefined.
* **Values are compared whole.** The old code compared only the first 255 bytes of a value, so a longer value was found by its first 255 bytes and not by itself; now only the whole value finds it.
* **A list or object inside a list or object cannot be queried.** A field holding a list or an object is still found by any of its plain values (never by its keys), as before; but an element that is itself a list or object is no longer found by its JSON text.
* **Emoji and long field names are stored.** Four-byte characters (emoji) anywhere in an item, and field names longer than 64 characters, are stored and can be queried; the old code on MySQL refused such a save.
* **Text comparison.** On MySQL and MariaDB all text (field values, the search text, and identifiers such as `uuid`, `owner`, the entity type and the publish status) compares with the `utf8mb4_unicode_520_ci` collation, the one the last 1.x schema used for field values and the search text: without regard to case or accents (`café` finds `CAFE`), `ß` equal to `ss`, trailing spaces ignored (`word ` finds `word`), `_` sorted before the letters, and every emoji distinct. What is new is that identifiers use it too (in 1.x they compared with `utf8` `general_ci`): for example the uuids `…/straße` and `…/strasse` were two different values in 1.x and are the same value now, so a second item with one of them is refused (and the upgrade lists such a row as not carried over). On SQLite only the case of the letters A to Z is ignored (`ÉTÉ` does not find `été`, `café` does not find `cafe`, `straße` does not find `strasse`, trailing spaces count), and `_` sorts after the letters.
* **SQLite sessions are files.** SQLite cannot lock a session row, so an SQLite site keeps its PHP sessions in PHP's session files, whatever `sessions_database` and `sessions_storage` say, and the `idno_sessions` table is not used. People logged in to an SQLite development site log in again after this change.
* **A relative SQLite path is relative to the Idno directory.** `dbname = "data/idno.sqlite"` is `<Idno directory>/data/idno.sqlite` (it used to be used as written, so it depended on the working directory of the process). In `IDNO_DATABASE_URL` (or `KNOWN_DATABASE_URL`), `sqlite:///data/idno.sqlite` is that relative path, `sqlite:////var/lib/idno.sqlite` is the absolute `/var/lib/idno.sqlite` and `sqlite:///:memory:` is an in-memory database; every other scheme is read as before.
* **Search on SQLite** has no full-text index: a term of more than 5 bytes matches any of its words inside longer words, and boolean operators (`+word -other`) are plain characters. MySQL and MariaDB search with their full-text index as before, with the site's `boolean_search` and `bypass_fulltext_search` settings.
* **Field names in a query are exact.** A query on `colour` no longer finds a field stored as `Colour`.
* **One row per item in `site`.** The `site` collection keeps exactly one row per item. Re-saving a site record with a new `uuid` now updates its one row (the old code kept the old row too, so two rows had the same id), and re-saving it with another record's `uuid` is refused.
* **A type name with a leading backslash matches nothing.** `getObjects('\\IdnoPlugins\\Status\\Status')` finds nothing, as before: types are compared as they are stored, without a leading backslash. A query by class finds the records stored under the class's alias, its class name and its former names (above), never its subclasses.
* **Collection names ignore case, on every database.** `getRecords(..., 'Entities')` reads the `entities` collection; on MySQL the old code found no such collection.
* **Dates in queries are read in the time zone of the query.** `created` is now stored as a timestamp, and a date such as `'2024-06-01 12:00:00'` in a query is read in PHP's default time zone when the query runs (the old code compared it with the date as it was written in the time zone of the save). A `created` value that is not a date finds nothing, on every database.
* **Decimal numbers are compared as their JSON text.** A number still finds itself, but the string `'0.3'` no longer finds the number `0.1 + 0.2` (stored as `0.30000000000000004`). On MySQL 8 (not MariaDB or SQLite) a number that JSON writes in exponent form (`1.0e+25`) is not found by the same number.
* **Settings.** The `config` collection holds one document (saving another replaces it), and a settings key that ends in a space is refused.
* **Indexed fields match plain values only.** A field that an entity class declares as indexed (`#[IndexedField]`) no longer finds an item where that field holds a list or an object, once its index exists. Declare only fields that hold one value in every record of the collection, whatever class stored it.
* **`access` is one plain value of at most 255 characters.** The database indexes every item's `access` (who may read it), so it behaves as an indexed field does: an item whose `access` is a list or an object is not found by any query on `access`, so listings show it only to administrators. On MySQL and MariaDB an item whose `access` is longer than 255 characters is refused when it is saved (`false`), as an over-long `uuid` or `owner` is; that relies on the server's strict SQL mode, which is the default. Idno itself only ever stores `PUBLIC`, `SITE`, or the address of a user or an access group there.
* As before, a whole decimal number (`1.0`) reads back as the integer `1`.
