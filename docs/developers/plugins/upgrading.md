# Upgrading your plugin or theme's templates

Idno's own templates, and those of its bundled plugins, are Twig templates. Yours do not have to be: a `.tpl.php` template of a plugin or a theme keeps working for the whole 2.x series, and is not drawn any differently. This page tells you what still works without any change, what changed for a PHP template that one of core's Twig templates draws, and how to convert a template of your own to Twig. Support for `.tpl.php` templates ends in Idno 3.0.

For the template cascade, the template types and the list of Twig helpers, see [Templates in Idno](../templating/index.md).

## What still works without converting

* A `.tpl.php` file in your plugin's or theme's `templates/<type>/` folder, with the name of a template core draws, replaces it. Within the cascade the order is the template type, then the folder, then the format, so your `.tpl.php` file still beats core's Twig file of the same name and type (a Twig file beats a `.tpl.php` file only when both are in the same folder).
* `extendTemplate()`, `prependTemplate()`, `replaceTemplate()` and `extendTemplateWithContent()`, and the `[Extensions]` and `[Prepend Extensions]` sections of a theme's `theme.ini`, apply to a template whether it is a Twig file or a PHP file, and whether the extension is one or the other.
* `$this->draw('some/name')` in your PHP template draws core's Twig file of that name.
* A `templates/modern/` folder is still drawn before `default` on web pages for one release, and the first file drawn in a request logs a deprecation line. Move its files to `templates/default/`; the `modern` type is removed in 3.0.

What changed is the object a PHP template gets when a core **Twig** template draws it. The Twig template draws it on a copy of the page's template object, so `$this` in your file is that copy:

* what you set with `$this->__([...])` is not left on the template for the templates drawn after yours (pass the value explicitly, or draw the template that needs it from yours);
* what you register with `extendTemplate()` and the other methods on `$this` inside such a file is lost with the copy: register in your plugin's `registerPages()` (or your theme's `theme.ini`), as the documentation always said.

Code that `include`s a core template by its file path no longer finds a `.tpl.php` file there: draw it by name.

## Converting a `.tpl.php` template to Twig

### Where the file goes

Put the Twig file in the same place as the PHP file, with the extension `.html.twig`: `templates/<type>/<name>.html.twig`. The plain-text mail type, `email-text`, uses `.txt.twig`, in which nothing is escaped. If both files are in one folder the Twig file is drawn, so you can keep the PHP file beside it until you are sure of the port, and then delete it. Twig is compiled into the cache: after you install or change a Twig file on a production site, clear the cache (`php bin/console cache:clear`, or delete `var/cache/`).

### An example

This is the template of a note (the Status plugin's `entity/Status`), as a PHP template:

    <?php
        $tags = '';
        $rel = '';
    if (!empty($vars['object']->tags)) {
        $tags = $this->__(['tags' => $vars['object']->tags])->draw('forms/output/tags');
    }
    ?>
    <div class="idno-entry-content">
    <p class="p-name e-content entry-content"><?= nl2br($this->parseURLs($this->parseHashtags($this->parseUsers(htmlentities(html_entity_decode($vars['object']->body), ENT_QUOTES, 'UTF-8') . $tags, $vars['object']->inreplyto)), $rel)) ?></p>
    </div>
    <?php

    // Render cached link preview if available (server-side, no JS needed)
    if (!empty($vars['object']->link_preview) && empty($vars['object']->hide_preview)) {
        echo $this->__(['preview' => $vars['object']->link_preview])->draw('entity/LinkPreviewCard');
    } elseif (!substr_count(strtolower($vars['object']->body), '<img')) {
        // Embed known media types (YouTube, Vimeo, etc.) -- no JS unfurl fallback
        echo $this->draw('entity/content/embed');
    }

and as a Twig template:

    {# A note: its text is read as plain text (character references decoded, then escaped), linked, and followed by its tags; line breaks become <br />. #}{% set post_tags = entity_value(object, 'tags') %}{% set tags_html = post_tags ? idno_include('forms/output/tags', {tags: post_tags}) : '' %}{% set note_text %}{{ entity_value(object, 'body')|decode_entities }}{{ tags_html }}{% endset %}<div class="idno-entry-content">
    <p class="p-name e-content entry-content">{{ note_text|parse_users(entity_value(object, 'inreplyto'))|parse_hashtags|parse_urls|nl2br }}</p>
    </div>
    {% if entity_value(object, 'link_preview') and not entity_value(object, 'hide_preview') %}{{ idno_include('entity/LinkPreviewCard', {preview: entity_value(object, 'link_preview')}) }}{% elseif '<img' not in ((entity_value(object, 'body') ?? '')|lower) %}{{ idno_include('entity/content/embed') }}{% endif %}

The two draw the same markup for the same note (a test of Idno's own suite draws both and compares them). Every variable of the PHP template's `$vars` is a Twig variable of its own name (`object`, not `$vars['object']`).

### The rules

* **Drawing another template.** `$this->draw('x')` is `{{ idno_include('x') }}`: the template type, then `default`, either kind of file, with the extensions plugins and themes registered. `$this->__(['a' => 1])->draw('x')` is `{{ idno_include('x', {a: 1}) }}`. The included template gets your variables and the ones you pass, and draws on a copy, so it cannot change yours; and a variable that a later template only saw because an earlier `__()` left it on the template object must now be passed.
* **Translating.** `\Idno\Core\Idno::site()->language()->_('Posted by %s', [$name])` is `{{ t('Posted by %s', [name]) }}`. A string that holds markup is `{{ t_html('Posted by <a href="%s">%s</a>', [url|http_url, name]) }}`: the string is trusted as markup and everything you put into it is escaped. Because the translation is trusted, the first argument of `t_html()` must be a string you wrote in the template, never a variable or a concatenation. `php bin/console build-lang all` also finds only the strings written in the template.
* **Escaping.** A `.html.twig` template escapes everything it prints. Remove your `htmlspecialchars()` calls. Use `|raw` only for HTML your own code built and escaped, or that `sanitize_html` purified (`{{ body|sanitize_html }}` already is markup and needs no `|raw`). `|raw` on a title, a comment, an address or any other value a member or another site supplied is a security hole: it switches the escaping off for that value.
* **Addresses from outside.** An address that a member or another site supplied goes through `|http_url` where it is an `href` or `src`: `<a href="{{ url|http_url }}">`. It gives the address when it is http or https and an empty string otherwise, so a `javascript:` address cannot run.
* **Values in a script.** Inside an inline `<script>`, `|e('js')` belongs INSIDE a quoted JavaScript string: `var title = '{{ title|e('js') }}';`. Outside a string, `{{ x|e('js') }}` is not a JavaScript value. To print a whole value (a number, a list, an object), encode it as JSON in the template and print the result with `|raw`, the one other place `|raw` is right: `var data = {{ value|json_encode(constant('JSON_HEX_TAG') b-or constant('JSON_HEX_AMP') b-or constant('JSON_HEX_APOS') b-or constant('JSON_HEX_QUOT'))|raw }};`. The four flags turn `<`, `>`, `&`, `'` and `"` into escapes JSON allows, so no value can end the script element or the attribute. This is the form core's own templates use. `js_string(value)` is for a double-quoted attribute that holds JavaScript (`onclick="go({{ js_string(x) }})"`), never for the inside of a `<script>`. Idno's test suite lists every `|raw` of core and the bundled plugins with its reason (`raw-allowlist.php`); that list is how Idno checks its own templates, and nothing in it runs against your plugin: it is advice, and the reason to ask of each `|raw` you write.
* **Entity attributes.** A stored attribute of an entity is read with `entity_value(object, 'body')`. A method is called explicitly: `object.getTitle()`. Do not write `object.body`: Twig would call a method named `body()` or `getBody()` if the entity has one.
* **The site and the request.** A Twig template has no `Idno::site()`, no superglobal and no static call. What it needs is a variable your page passes, or a function from the list of helpers in [Templates in Idno](../templating/index.md#helpers) (`site_url()`, `current_user()`, `setting()`, `form_token()`, ...).
* **Whitespace.** PHP drops the newline after `?>`; Twig keeps the newline after `}}`. Use `-}}` where text must run into a tag.

### Extending core's shell

A page shell (`shell`, `account-shell`, `admin-shell`) has four blocks: `head`, `nav`, `content` and `footer`. A Twig file of your plugin or theme extends core's own copy and replaces one:

    {% extends '@core/default/shell.html.twig' %}
    {% block nav %}<nav>My navigation</nav>{% endblock %}

`@core/default/<name>.html.twig` is core's file, which a file of yours with the same name cannot extend by its plain name (that would extend itself).

## Pages that controllers now serve

Some core pages are Symfony controllers, not `Idno\Common\Page` classes run by the legacy router: the home page, the feeds, the search, the tag pages, the member's drafts page and the small public endpoints. A controller draws a page through a service and `Idno\Http\Page\PageRenderer`; the page's events, body class, headers and access rules are the page's as they were. A plugin that extends one of the deleted classes stops the site booting (the autoloader throws while the plugin registers its pages): disable it before you upgrade. What differs for your plugin, in one list:

* A plugin's `hijackRoute()`, an identical `addRoute()` or an exact key for one of these paths still takes it (WebFinger is the exception, below), because core still registers each pattern where it did, with a placeholder, `Idno\Legacy\ControllerRoute`, in place of the deleted class.
* POST, PUT, PATCH and DELETE of a moved path nobody registered a page for, and a request with a malformed `Host`, answer the site's 404 page (a POST to `/feed.xml` was a redirect to the home page).
* A webmention aimed at one of the moved non-content paths (the feeds, the search, the tags and the small endpoints) is refused with `target_not_found`.
* `/bookmarklet.js` is gone. `/tag//` is the 404 page (it was the tag `/`). A static home page's body class and `page_class` are `idno_pages_homepage` and `Idno\Pages\Homepage`.
* A feed or a tag page fires the page's events once, with `page_class` `Idno\Pages\Homepage`.

The details, for the home page and then for each group of pages:

* **`Idno\Pages\Homepage` is a deprecated shell, removed in 3.0.** It has no logic of its own: its `getContent()` hands the request to `HomePages`, so there is one implementation. A page of yours that extends it, and a `hijackRoute()` or `addRoute()` of it, still serve the home page, through the same service. Constructing or serving a *subclass* of it logs one deprecation line a process (`Deprecated: <your class> extends Idno\Pages\Homepage ...`). Extend `\Idno\Common\Page` instead and draw your own page. The line is logged once for each shell, in each process.
  What a subclass of a shell no longer controls: the service reads the request through the page's context, so an override of `getInput()`, `setLastModifiedHeader()` or any other method the old `getContent()` called on `$this` has no effect on what the service reads or sends; only the page's `$arguments`, its owner and the values it gave `setInput()` reach the service. While the page draws, `Idno::site()->currentPage()` is an `Idno\Legacy\ControllerPage`, not your subclass, so a template or listener that calls a method of your own class on the current page fails (it is your page again once the service has answered). What still works: your `getContent()` and `webmentionContent()` overrides that call the parent's, the route you registered, and the page's events. A page served through a shell ends the request when it is drawn, as the legacy page did: code after `parent::getContent()`, the router's `after_handler` hooks and `kernel.terminate` do not run. A subclass also carries the page's flags from the shell it extends (the controller action's `#[SitePage]`: account and settings page, default type, Markdown form, `Vary: Accept`): a constant `ACTION` of its own is ignored, and an account page refuses a signed API request on whatever route the subclass is registered.
* **A plugin's `hijackRoute()`, or an identical `addRoute()`, still takes the path** (WebFinger is the one page where core registers after the plugins, and its identical pattern is core's: see the small endpoints below). The controller's route is matched first, and then the legacy router is asked which page it would serve the path with: a page that is not one the controller replaces keeps the path, so your page is served as it was.
* **`Idno::site()->currentPage()` is an `Idno\Legacy\ControllerPage` while a controller's page is served.** `getInput()`, `getOwner()`, `isPermalink()`, `currentUrl()`, `xhr` and the other members templates and plugins ask a page answer from the request. Where a legacy page exited, it throws what the controller turns into a response: `deniedContent()`, `noContent()`, `goneContent()` and `forward()` throw instead of exiting. A listener of yours that calls `exit` during a controller's request skips `kernel.terminate`, which runs the work a page asked to be done after its response.
* **The page's events are the same**: `page/ready`, `page/head` and `page/get` (`page/head` and no `page/get` for HEAD) fire in the same order with the same data (`page_class` is `Idno\Pages\Homepage`).
* **The feeds, the search and the tag pages are the home page controller's too, and their classes are deleted.** `Idno\Pages\Feed` (`/feed.xml`, `/feed`, `/rss.xml`), `Idno\Pages\Search\Forward` (`/search`) and `Idno\Pages\Search\Tags` (`/tag/<tag>`) are gone, with their routes in `Idno::registerPages()`: `HomepageController::feed()`, `search()` and `tag()` replace them, calling `Idno\Http\Controller\Home\HomePages::feed()`, `search()` and `tag()`, which draw the same stream the home page does. There is no shell: nothing extended them, and a plugin that does extend one of the three classes stops the site booting (the autoloader throws while the plugin registers its pages), so disable it before you upgrade. What differs for your plugin:
  * **The page's events fire once.** A feed or a tag page is the home page's stream, so `page/ready`, `page/head` and `page/get` fire once, with `page_class` `Idno\Pages\Homepage` and the body class `idno_pages_homepage` (a feed was `idno_pages_feed`, a tag page `idno_pages_search_tags`, and each fired the events a second time for the home page it built: the feed fired `page/ready`, `page/head` and `page/get` twice and sent your `page/head` listeners' headers, the `Link` headers of the webmention endpoint and the hub among them, twice; the tag page fired a trailing `page/ready`). A listener that counted on the second set, or on the feed's own class, must change. For the feed `page/ready` fires with the template type `rss` already selected (it fired in the default type, and `page/head` and `page/get` in `rss`).
  * **`hijackRoute()` and `addRoute()` of these paths.** Core still registers the legacy pattern of each (`/feed\.xml`, `/feed/?`, `/rss\.xml`, `/search/?`, `/tag/([^\s]+)\/?`) where and when it always did, with a placeholder, `Idno\Legacy\ControllerRoute`, in place of the deleted class, so the legacy route table is what it was and the legacy router's own rules decide what your registration does. The controller serves the path unless the legacy router would choose another page for it: your `addRoute()` of the identical pattern replaces the placeholder in place; your `hijackRoute()` of it, or of any pattern that matches, puts it in front; an exact key (`addRoute('/feed.xml')`, `addRoute('/')`) beats every pattern; a pattern you registered before core's matches first. Your page serves the spellings of the address that the legacy router itself resolves to it (the plain one, and for a pattern the ones it matches), for every method. One consequence: if you registered an EXACT key (`addRoute('/feed.xml')`), a spelling the legacy router used to route to core's page (`//feed.xml`) is now the 404 page, because the controller never serves an address a plugin took. A pattern registered AFTER core's with `addRoute()` (a short-link page's `/([a-z0-9\-]+)/?`, a catch-all) did not take these paths before, because core's came first, and does not now; it serves the paths core never had. (WebFinger's pattern is registered by `Idno\Core\Webfinger`, which is built after the plugins: a pattern you registered earlier and broader matches first there, and a `hijackRoute()` of the identical pattern you made at plugin time is overwritten by core's registration, as before.)
  * **Other methods and a malformed `Host`.** The controller takes GET, HEAD and OPTIONS. POST, PUT, PATCH and DELETE of these paths, and a request whose `Host` header is not a host name (Symfony rejects it before routing and the legacy router answers), are the legacy router's: a path nothing is registered for, which is its 404 page. A POST to `/feed.xml` or `/search` was the invalid-token redirect home, or, with a token, a redirect home that did nothing.
  * **Webmentions.** The webmention endpoint finds the target's page with the legacy router, and these paths have none: a webmention to `/feed.xml`, `/rss.xml`, `/search` or `/tag/x` is answered `400 target_not_found` (it was refused with `source_not_supported`, or `target_not_supported`).
  * **The tag is decoded once.** `/tag/<tag>` takes the tag from the path as it was sent and decodes it once: `+` is a space and `%2B` a plus (`/tag/a%2Bb` lists `#a+b`; it listed `#a b`, because the path was decoded twice). One trailing slash is not part of the tag (`/tag/books/` lists `#books`, not `#books/`), and the tag wins over a `q` in the query string (`/tag/books?q=x` lists `#books`; the request's `q` replaced it). A tag with a space in it was no page and still is none, and a tag that is only slashes is none either: `/tag//` was the tag `/` (the page listed `#/`) and is the site's 404 page, as a deliberate change.
  * **`/search` with a `q` that is not text** (`?q[]=x`) is a redirect with an empty query; it was a 500 page.
  * **XHR.** An XHR GET of these pages gets the headers of the same request that is not XHR (see the home page above).
* **The small public endpoints** (`Idno\Http\Controller\Discovery\`, in the table above) each have a controller and a service that holds the logic.

  `Idno\Core\Webfinger` still exists and registers the placeholder for WebFinger's pattern, after the plugins, as it always registered the page. The events, template extensions, walled-garden rule (the manifest, the service worker and WebFinger are public on a private site; the others are not) and body class (`page_class` of the page events is the deleted class's name) are as they were. Differences:
  * **`/service-worker.js` serves the script that ships**, `js/service-worker.min.js`, as `application/javascript`, at both addresses. The page read `js/service-worker.js`, a file the Grunt build writes and git ignores, so it answered a 500 page on every site that had not built it; a release without the shipped file answers the 404 page.
  * **`/search/mentions.json` is `application/json`** (it was `text/json`). Who may call it, and what it returns (handle, name and avatar of each member), are unchanged.
  * **The form token endpoint needs no `url`.** The token is the session's one stored token, so there is nothing to make it for: a request without `url` is answered (it was a 500 page) and the address is not read. Its caching is `Cache-Control: no-store` (the session's `Expires` and `Pragma` as on every page, and no `Last-Modified`): it was the router's XHR headers with `setNoCache()` over them. It still answers only an XHR request (the 403 page otherwise), and a visitor of a private site is still refused.
  * **WebFinger** answers `resource[]=x` with the 404 page (it was a 500 page), and an `acct:` of another host with the 404 page, as before (no account is revealed). The JRD, its `application/jrd+json` type and `Access-Control-Allow-Origin: *` are unchanged, and its `links` is always a list: the `webfinger` event's response is used when it is a list, and any other value a listener returns (the event's default is `true`) gives `[]` (it used to print `"links": true`; a stock site's own listener always returns a list).
  * **`robots.txt`** is sent as `text/plain; charset=UTF-8` (it was `text/plain`).
  * **Other methods, a malformed `Host`, webmentions and XHR** are as for the feeds above: POST, PUT, PATCH and DELETE of these addresses (a POST to `/.well-known/webfinger` was the invalid-token redirect home) and a request with a malformed `Host` are the legacy router's 404 page; a webmention to one of them is answered `400 target_not_found`; an XHR GET gets the headers of the same request that is not XHR.
  * **`hijackRoute()` and `addRoute()`**: as for the feeds, core still registers each pattern (`/robots\.txt`, `/chrome/manifest\.json`, `/service-worker(\.min)?\.js`, `/\.well\-known/webfinger/?`, `/search/mentions\.json`, `/service/security/csrftoken/?`) where it did, with the placeholder, and the legacy router's rules apply: for every one of them but WebFinger a plugin page registered with `hijackRoute()`, an identical `addRoute()`, an exact key, or a pattern matched first still takes the path. WebFinger is registered by `Idno\Core\Webfinger`, which is built AFTER the plugins, and so it is the other way round, as it always was: core's `addRoute()` of `/\.well\-known/webfinger/?` replaces the handler of an identical registration of yours (and of a `hijackRoute()` of it made while your plugin registered its pages) in place, so core's page serves the path. What takes WebFinger's path from core is an exact key (`addRoute('/.well-known/webfinger')`), a different pattern you registered at plugin time that matches it (the patterns are tried in registration order, yours before core's), or a `hijackRoute()` made after core's registration (not while your plugin registers its pages). `/bookmarklet.js` has no registration now: a plugin's broader pattern, or the 404 page, answers it as for any unknown path.

**The post permalink.** `Idno\Pages\Entity\View`, the page that every bundled content type's permalink and the `/view/<id>` address route to, is a deprecated shell, removed in 3.0. A post's GET, HEAD and OPTIONS are served by `Idno\Http\Controller\PermalinkController` (the route `idno_permalink`, which has no `#[Route]`: content types register their own patterns, so the legacy route table decides, as it always did, and hands the request to the controller). The logic is in `Idno\Http\Controller\Permalink\PermalinkPages`, which the shell's `getContent()`, `postContent()`, `deleteContent()` and `webmentionContent()` call, so there is one implementation.

* **A post's address has one layout, `/YYYY/slug`, and `permalink_structure` is gone.** `\Idno\Common\Entity::getPermalinkRoute()` returns the fixed pattern `/[0-9]{4}/([^/.]+)` (it still has the one matching group, the slug) and `Entity::getURL()` builds `<site>/YYYY/slug`; `Config::getPermalinkStructure()` is deprecated and always returns `/:year/:slug`. A plugin that offered or read another structure, or built a post's address from `:month`, `:day` or `:id`, should use `getURL()`. A stored `permalink_structure` is ignored. Core registers `/YYYY/MM/<slug>` and `/YYYY/MM/DD/<slug>` (the other two layouts a site could choose) for the placeholder `Idno\Legacy\Placeholder\PermalinkOtherLayout`, which sends a GET or HEAD to the post's address with a 301 (and `/YYYY/MM/<slug>/annotations/<id>?` and the day's, for the placeholder `Idno\Legacy\Placeholder\AnnotationOtherLayout`, to the address the annotation has now); your own registration of the same patterns, registered before core's or an exact key, takes them as for any pattern. The identifiers that other servers hold (the `uuid`, the ActivityPub object `id`, the feeds' `guid`) never depended on the layout.
* **A content type of yours that registers `\Idno\Pages\Entity\View` for its own pattern is served by the controller**, which is given the arguments the pattern captured, in order (the first is the id or slug). Nothing changes in your plugin. A page of yours that **extends** `Idno\Pages\Entity\View` is served through the shell: its `getContent()` calls the same service, and constructing or serving it logs one deprecation line a process (`Deprecated: <your class> extends Idno\Pages\Entity\View ...`). What a subclass no longer controls is as for the home page above: the service reads the request through the page's context, and `Idno::site()->currentPage()` is an `Idno\Legacy\ControllerPage` while the page is drawn.
* **`lastModifiedGatekeeper()` and the 304 are corrected.** A conditional GET or HEAD of a permalink is answered `304 Not Modified` when its `If-Modified-Since` is a valid HTTP-date that is not before the post's last change (`Idno\Http\Page\PageContext::answerConditionally()`), the check is made only once the viewer is known to be allowed to read the post, and the date is ignored beside an `If-None-Match`. The legacy comparison was the wrong way round: it answered 304 to a copy older than the post and sent the page to a copy that was current, and read any text `strtotime()` understood as a date. A page of yours that calls `lastModifiedGatekeeper()` on the current page while a controller serves the page gets the corrected rule.
* **An XHR GET or HEAD of a permalink gets the headers of the same request that is not XHR**: the session's `Expires`, one `Cache-Control: no-store, no-cache, must-revalidate`, `Pragma: no-cache` and the post's `Last-Modified`. The legacy router answered with `Content-Type: application/json` before the page's, `Expires` in 1997, two `Cache-Control` lines and a `Last-Modified` of the moment.
* **A PUT or a DELETE with no valid form token is the site's 403 page** (it says the page timed out), for every legacy page, `Idno\Pages\Entity\View` and the home page's shell included: nothing is reported and the administrator is not mailed. A legacy page threw the exception of a timed out page, which was the reported 500 page and could be triggered by anyone. A POST with no token is as it was (an "Invalid token." message and a redirect).
* **The JSON that tells a signed API request where to go** after a POST or DELETE of a permalink (`{"location": ...}`) is sent as `application/json` (it was `text/html; charset=UTF-8`).
* **A post the viewer may not read is answered as a post that is not there** (`410`, the "this content isn't here" page). It was the 403 page, which told a stranger the address names a post. Only a post that a `canRead()` rule of yours (or an access edge case) refuses after the finders returned it reaches this; the finders already leave such posts out. A walled garden's refusal of a visitor and the refusals of a POST or DELETE are still 403.
* **A webmention to a post** is received by `PermalinkPages::receiveWebmention()` for the route `idno_permalink`; a post that is not there takes none, as before.
* **`Vary: Accept`** is sent on every answer to a GET or a HEAD of a permalink (a refusal, a missing post, a 304) but not on the answer to OPTIONS or on the refusal of a visitor of a private site, which are made before the page is served; a POST or DELETE through the shell does not send it (the legacy page sent it from `getContent()` only).
* **An ActivityPub request** (`Accept: application/activity+json`) to a permalink is answered with the post's object (the one its followers are sent), not the post owner's actor document. The `activitypub` template type's shell is now the ActivityPub plugin's (`IdnoPlugins/ActivityPub/templates/activitypub/shell.tpl.php`), and it answers from the page being served (`PageDocument`), never from template variables: a plugin that overrides that shell should do the same, because a variable such as `user` may have been set by a template drawn earlier. A template (or a plugin's code) that sets the status during the draw with `http_response_code()` gets the type's headers for that status. `autodetectTemplateType()` now sends `Vary: Accept` through the page (`sendVaryAccept()`), once.

**The shortlink and the annotation pages.** `Idno\Pages\Entity\Shortlink`, `Idno\Pages\Annotation\View` and `Idno\Pages\Annotation\Delete` are deleted (see the table above); a plugin that extends one stops the site booting until it is disabled. Core still registers each pattern where it always did: `/s/:id/?` with `Idno\Legacy\ControllerRoute` and the annotation patterns with `Idno\Legacy\Placeholder\AnnotationView` and `AnnotationDelete` (the constant `ACTION` of each names the controller action), so your `addRoute()`, `hijackRoute()` or exact key for those addresses is served as it was. `/annotation/post/?` is still the legacy page `Idno\Pages\Annotation\Post`.

* **The pages take only the methods they declare.** The shortlink and the list and single annotation take GET, HEAD and OPTIONS; the delete takes POST. Any other method, and any request with a malformed `Host`, is the legacy router's 404 page.
* **The list's title is translated** (`Annotations on: %s`, through the site's translation: `Idno\Http\Controller\Permalink\Annotations::listTitle()`), and the page's JSON, RSS and template variables are what they were.
* **The author of an annotation may delete it.** `Entity::canEditAnnotation()` is `canEdit()` or `isAnnotationAuthor()`; the author is the member whose profile address is the `owner_url` of an annotation stored with `made_here` (`Entity::addAnnotation()`'s new eleventh argument: pass `true` only when the site makes the annotation for a member, as the post page, Micropub and imports do; extra fields can never set it). An annotation stored before the mark counts when its `permalink` is its own key. A template that draws the delete link should ask `canEditAnnotation()` with the annotation's key (`locallink`), as core's do.
* **A webmention's annotation is identified by an address of another site or by its source** (`Entity::addWebmentions()`): the address the source declares for itself is used only when it is not on this site's host; a webmention never replaces an annotation made here, and never one another source stored: an annotation a webmention stores carries the page that sent it (`webmention_source`), `addAnnotation()` replaces only an annotation with the same `webmention_source` (or, for one stored before it was recorded, the same address), a declared address that is another source's annotation is not used, and an author address on this site's host is stored only for a source on this site (`removeWebmentionAnnotations($source, $keep)` removes only what that source stored). A plugin that overrides `addWebmentions()` should do the same.
* **A post the viewer may not read is a 410** from the page itself (it asks `canRead()` again after the finders), never a 403.
* **A webmention to a shortlink** is received by `ShortlinkPages::receiveWebmention()` for the route `idno_shortlink`; a webmention to an annotation page takes none, as before.
* **An annotation a site made itself under an old permalink layout** (stored under `/YYYY/MM/<slug>/annotations/<id>`) is found by its own id: `Entity::getAnnotations()`, the post's JSON and the annotation pages show its address as the post has it now (`Entity::canonicalAnnotationAddress()`), and `Entity::removeAnnotation()` removes it by either address. A plugin that builds an annotation's address from the post's address and the id should look the annotation up by the id (`getAnnotation()` looks up the exact key only).

**The webmention endpoint.** `Idno\Pages\Webmentions\Endpoint`, the page at `/webmention/` that other servers post to, is deleted (see the table above); a plugin that extends it stops the site booting until it is disabled, and one that called `Endpoint::fetchSource()` calls `Idno\Legacy\LegacyWebmentionSources::fetch()` (the same `Webservice::safeSend('get', ...)`). Core still registers `/webmention/?`, public, with the placeholder `Idno\Legacy\ControllerRoute`. What a plugin's page keeps: it receives a mention through its own `webmentionContent($source, $target, $source_response, $source_mf2)`, as before; the endpoint finds it from the target's address as a GET of the address is routed (`Idno\Http\Webmention\WebmentionTargets`), builds it, sets its `arguments` and `setPermalink()`, and calls `webmentionContent()`. A page that declares no `webmentionContent()` of its own takes no mentions: a mention of its address is refused with `target_not_found`, before the sender's page is fetched (it was `source_not_supported`, after). A plugin cannot register a receiver for the pages controllers serve (`ReceivesWebmentions` services are the site's); it is the plugin's page class that receives.

**The WebSub callback.** `Idno\Pages\Pubsubhubbub\Callback`, the page a WebSub hub verifies subscriptions with and delivers content to (`/pubsub/callback/<subscriber>/<subscription>`), is deleted (see the table above); a plugin that extends it stops the site booting until it is disabled. Core still registers `/pubsub/callback/:id/:id/?` with the placeholder `Idno\Legacy\ControllerRoute`; the address is unchanged, because hubs hold your subscriptions to it. **The event a delivery triggers is renamed.** A hub's POST used to trigger `pubsubhubbub/ping` with `subscriber`, `subscription` and `data` (the body, trimmed); it now triggers `websub/received` with the same data, and answers 200 with no body as before. `pubsubhubbub/ping`, now named `websub/ping` (a listener added under either name hears the event triggered by either), is the event the site publishes its own posts to its own hub with (its listener reads the data's `object`); it is no longer triggered by a delivery. The component `Idno\Core\PubSubHubbub` is now `Idno\Core\WebSub`, and the earlier name is an alias, so a plugin that listened to it for incoming content listens to `websub/received` instead. **A delivery is accepted only for a real subscription**: the subscriber must follow the subscription and the subscription must have a hub (before, any two user ids were accepted), and a subscription the site made with a `hub.secret` needs a valid `X-Hub-Signature` (`sha256`, `sha384` or `sha512`; the delivery is answered 200 and ignored when it fails). A hub that signs only with SHA-1 has its deliveries to a new subscription ignored. The subscription request that carries the secret is sent with `Webservice::safeSendWithoutRedirects()`, so a hub's redirect never receives the secret (a redirect to another https address is a subscription that was not made too: it is logged as a warning and its pending entry is removed), and following again someone whose hub is no longer https removes the secret kept for the subscription. A delivery acts as nobody (a request that carries a member's cookie is no longer run as that member), its body is read up to the `webservice_max_download` limit (a longer body is answered `413` and handed to no listener), and a hub's request to the callback is open on a private site. **What a plugin that stores or reads the list of pending subscriptions must know.** The list of subscriptions a member is waiting for (`pubsub_pending`) is an object with the lists `subscribe` (uuids) and `unsubscribe` (ids), now with `at`, the time of each entry; entries expire after a day. Read it with `Idno\Http\Controller\WebSub\PendingList::read()` (only an object of the one class is accepted: an earlier release could leave a plain array, which is read as an empty list) and change it with `PendingList::add()` and `remove()`. The secrets the site sent hubs are in the member's `pubsub_secrets`, by the subscription's id: do not print or export them. A verification must now carry the topic the site subscribed to (the followed user's `pubsub_self`).

* **The request acts as nobody.** The endpoint takes the POST with no form token and no session: a mention sent with a member's or an administrator's cookie is received as a visitor's, so `webmentionContent()` runs with nobody logged on (it ran as the cookie's user).
* **The refusals are JSON** (`Content-Type: application/json`; they were `text/html`), with the error codes the endpoint always used: `unknown_error`, `target_not_found`, `target_not_supported`, `source_not_allowed` (a source the site may not fetch: it was answered with `target_not_supported` and the self-mention text), `source_not_found`, `no_link_found` and `source_not_supported`. A request whose source or target is not text, holds white space or a control character, or is over 2048 bytes is `unknown_error` (it was a server error page, or went on).
* **PUT and DELETE of `/webmention/`** are the site's 404 page, as for every page a controller serves (they were the invalid-token page).
* **A target that names nothing is refused before the sender's page is fetched.** A mention of a post that does not exist or that a visitor may not read (private, members-only, a draft, deleted), of a shortlink or an account that does not exist, or of the home page of a multi-user site is `target_not_found`, the same answer for each (the legacy endpoint fetched the sender's page and answered `source_not_supported`).
* **A refusal is not markup.** Its JSON repeated the sender's target as `text/html` (a `<script>` in a target was sent as it was); it is `application/json` with `X-Content-Type-Options: nosniff`, with `<`, `>`, `&`, `'` and `"` escaped.
* **A webmention changes the post's annotations only, and a repeat changes nothing.** `Entity::addWebmentions()` saves and announces nothing for a mention that stores what is already stored or for a withdrawal of one never stored. A save that only changes annotations is `Entity::saveAnnotations()`: the `updated` event carries `annotations_only`, and a plugin that tells other servers about a post's content (ActivityPub, StandardSiteSync) returns early for it; a plugin's own `updated` listener should do the same. `Entity::addAnnotation()` takes a last argument, `$persist`, true by default, and SAVES the annotation as an annotation-only change itself: a caller must not call `save()` after it (an unmarked second save is an `Update` of the post to followers; the core's own like, reply and Micropub annotation paths no longer do). A webmention to the page of a third-party content type (a legacy class with its own `webmentionContent()`) is not asked whether its target exists: its source is fetched before the page decides.
* **The fragment is no input.** The endpoint used to set the target's `#fragment` as input `#` of its own page, which no target page ever saw; a `webmentionContent()` that read `getInput('#')` never got it and still does not.

**The profile page.** `Idno\Pages\User\View`, the page of a member's profile, is a deprecated shell, removed in 3.0. A profile's GET, HEAD and OPTIONS are served by `Idno\Http\Controller\ProfileController` (the route `idno_profile`, which has no `#[Route]`: the legacy route table decides, as it always did, and hands the request to the controller). The logic is in `Idno\Http\Controller\Profile\ProfilePages`, which the shell's `getContent()`, `postContent()` (the profile edit form, which posts to the profile's own address) and `webmentionContent()` call, so there is one implementation. Core registers `/profile/([^\/]+)/?`, `/profile/([^\/]+)/([A-Za-z\-\/]+)+` and `/actor/([^\/]+)/?` for the shell where it always did, so your `addRoute()`, `hijackRoute()` or exact key for those addresses is served as it was; a page of yours that **extends** `Idno\Pages\User\View` is served through the shell (it logs one deprecation line a process), and what a subclass no longer controls is as for the post permalink above.

* **The ActivityPub plugin still takes `/actor/<handle>`.** The plugin registers the identical key `/actor/([^\/]+)/?`, which replaces core's handler in place, so with the plugin enabled that address is the plugin's actor page, in every form; the profile's own address answers an ActivityPub request (`Accept: application/activity+json`) with the account's actor, as before. Where the plugin is not enabled, `/actor/<handle>` is the profile.
* **A DELETE of a profile address is gone from the shell.** `Idno\Pages\User\View::deleteContent()` looked its argument, the handle, up as an entity's id and deleted what it found, so it deleted the account or the post whose id the address held, and never the profile of a handle. The page now has no DELETE handler and answers a DELETE as any page without one does (a request with a valid form token is answered `501` and forwarded to the home page, a script's request `501`, a request with no token the site's 403 page). An account is deleted by an administrator's session from Admin, Users (a POST to `/admin/users`), at `/delete/<id>`, or by a DELETE of its `/view/<id>` address, which is the post permalink's and refuses everyone else.
* **An XHR GET or HEAD of a profile gets the headers of the same request that is not XHR**, as the permalink does (the session's `Expires`, one `Cache-Control: no-store, no-cache, must-revalidate`, `Pragma: no-cache` and the profile's `Last-Modified`); the legacy router answered with `Content-Type: application/json` before the page's, `Expires` in 1997, two `Cache-Control` lines and a `Last-Modified` of the moment.
* **A signed API request that edits a profile** is told where to go in JSON sent as `application/json` (it was `text/html; charset=UTF-8`), as for the permalink.
* **`HomeStream::profilePageWebmention()` is gone.** The home page of a single-user site passes a webmention to the profile's receiver, `ProfilePages::receiveWebmention('idno_profile', [$handle], $mention)` (found in the services tagged `idno.webmention_receiver` under the name `Idno\Pages\User\View`), where it asked the legacy router for the page at the profile's address and called its `webmentionContent()`; a plugin that hijacked the profile's address no longer takes a single-user site's root mentions. A webmention to a profile is accepted and not stored, as it was: a profile has nowhere to keep one. What the shell's `webmentionContent()` worked out of the source (a title, the mention's content and author) was never used and is not computed.
* **The profile never answers a conditional request** (it sent the page, and still does). Its `Last-Modified` is the later of the account's last change and its newest post's.

**The file page.** `Idno\Pages\File\View`, the page that serves a stored file, is deleted (see the table above); a plugin that extends it stops the site booting until it is disabled, and a plugin that called `View::endOutputBuffers()`, `seekTo()`, `streamRange()`, `streamAll()` or `parseRange()` calls `FileStream` and `ByteRange::parse()` instead (same arguments and results). Core still registers `/file/(:id)(/.*)?` where it always did, still public, with `Idno\Legacy\ControllerRoute`, so your `addRoute()`, `hijackRoute()` or exact key for a file address is served as it was; `/file/upload/`, `/file/picker/`, `/filepicker/` and `/file/mint/` are still legacy pages, registered before it. The page is a `StreamedResponse` that reads the stored file 8 KiB at a time. What it does is what it did, with these changes:

* **A public file's `Expires` is an HTTP date in GMT** (`Fri, 25 Dec 2026 12:00:00 GMT`), where it was an RFC 1123 date with a numeric offset in the server's time zone (`Fri, 25 Dec 2026 12:00:00 +0000`).
* **A download is named after the last segment of its address.** A file whose type a browser could run, or that is not a picture, a PDF, audio or video, is sent with `Content-Disposition: attachment; filename="<name>"`: `/file/<id>/report.zip` is `report.zip` (characters other than letters, digits and `._-` become `_`), and an address with no name is `download`. It was the file's id whatever the address said.
* **A HEAD request reads nothing of the file** (it streamed the whole file for the server to drop), and says how long the body would be.
* **A file is dated by its own modification time, and a conditional request is judged the right way round.** `Idno\Storage\Files\StoredFile` has a new `$lastModified` (the stored file's modification time, from the filesystem; null when the filesystem cannot say) and `Idno\Legacy\FlysystemFile::$lastModified` carries it. The page sends it as `Last-Modified` (none when it is unknown, never the time of the request, which is what it sent) and a GET or HEAD whose `If-Modified-Since` is an HTTP date that is not before it is a 304, before any `Range`, carrying the file's caching lines and date; a date that is not an HTTP date, and any date beside an `If-None-Match`, is ignored. An archive of the site is revalidated like any file. It used to be a 304 when `strtotime()` read the date as not after the change.
* **A file attached to a post the viewer may not read is a missing file** (the 404 page, for every method, range, conditional request and requester); it was a 403. An administrators-only file stays a 403 to anyone else.
* **A shown file is sent as its canonical type** (`image/png`, never the stored string with its parameters), any other file as a download whose type is its stored type if that is a well-formed media type and `application/octet-stream` if not, and every file but a PDF with `Content-Security-Policy: sandbox`.
* **A range no byte of the file satisfies is a 416 with `Content-Length: 0`** (it had no length) and `Content-Range: bytes */<size>`.
* **The page takes only GET, HEAD and OPTIONS.** Any other method, a request with a malformed `Host`, and an address the route does not match (`/file//<id>`) are the legacy router's 404 page. An XHR GET gets the headers of the same request that is not XHR. A name after the id may hold any character, a line break too.
* **Who may have a file is `Idno\Legacy\LegacyStoredFiles`'s** (the rules are the legacy page's): a file attached to a post is sent only to those who may read the post, an administrators-only file (the `restricted` and `site_export` marks, and the recorded export archive) only to an administrator.

**The feed reader is removed.** Following a feed (to read a site's items inside your site) could not work on any supported PHP: the reader called `DOMDocument::loadHTML()` statically, which has been an error since PHP 8, so `/following/add/` and `/following/confirm/` answered the 500 page before anything was saved, `/following/refresh/` had no feed to read, and nothing linked the pages. It is deleted, not repaired: `Idno\Core\Reader` (and `Idno::site()->reader()`, which is gone), `Idno\Entities\Reader\Feed`, `FeedItem` and `Subscription`, the pages `Idno\Pages\Following\Home`, `Add`, `Confirm` and `Refresh`, the templates `following/*`, `entity/FeedItem`, `entity/Subscription` and `content/feed/end` (Twig and `classic`), and the `simplepie/simplepie` dependency. **If a plugin of yours extends or names one of those classes, or calls `reader()`, disable it before you upgrade**: the site cannot start while a plugin names a class that is gone. A theme or plugin that overrides one of those templates keeps a file nothing draws. The five addresses (`/following/`, `/following/add/`, `/following/confirm/`, `/following/refresh/`, `/stream/`) are the site's 404 page, and core registers nothing for them, so a plugin's own page for one is no longer shadowed. Following a *person* is unchanged (the follow bookmarklet at `/account/settings/following/`, `User::addFollowing()`, the `follow` and `unfollow` events and WebSub for those follows); the bookmarklet no longer offers to subscribe to the person's feed afterwards. **No record is deleted.** Records the reader stored (an upgraded site's, in the `reader` collection, or a few a save put in `entities`) stay in the database and in the export archive, and nothing reads or shows them: a listing or lookup that meets one skips it, as it skips any record whose class is gone, and its address is the site's 410 page. The tables stay as they are, and the upgrade from 1.x still copies the old `reader` tables into `idno_reader`.

### Addresses the site decides at run time, and the router's hooks

A few pages are controller actions that the legacy route table routes (content types and plugins register patterns for a permalink): the page class that served an address (a kept shell, or a placeholder where the class was deleted) names the action that serves it, and the legacy router's own choice still decides, so your `addRoute()`, `hijackRoute()` or exact key for such an address is served as it was. A class that extends one of those shells is a page of yours and is served through the shell. A plugin that registers core's shell class for a pattern of its own (a content type's permalink, `Idno\Pages\Entity\View`) is served by the action, which receives the arguments the pattern captured, in order.

One thing changed for code that reads it: the `routes` that the legacy router gives its hooks (`PageHandler::hook()`: `before_request`, `before_handler`, `404`, `after_handler` and `after_request`, in `$params['routes']`) is, for a request the router's choice was recorded for (nearly every request the catch-all serves; one with no recorded choice, such as a malformed `Host`, gives them the whole table), a table with the one entry the router chose, or none when it has no page for the request, where it was the whole route table. The route table itself is `Idno::site()->routes()`. Nothing in core reads the argument.

### Replacing the home page: the `homepage/replace` event

To make the site's root something other than the stream (a static page, a landing page), do not extend `Idno\Pages\Homepage` and `hijackRoute()` the root: listen to the event `homepage/replace`. `Idno\Http\Controller\Home\HomePages::home()` triggers it first, with two values in the event's data:

* `page`: the `Idno\Http\Page\PageContext` of the request (its input, owner, headers, the viewer's request);
* `renderer`: the `Idno\Http\Page\PageRenderer`, which draws a page and makes redirects and refusals.

A listener that sets a `Symfony\Component\HttpFoundation\Response` as the event's response gives the home page; anything else is ignored and the stream is drawn:

    function registerEventHooks()
    {
        \Idno\Core\Idno::site()->events()->addListener('homepage/replace', function (\Idno\Core\Event $event) {
            $data = $event->data();
            $user = \Idno\Core\Idno::site()->session()->currentUser();
            if (!$user) {
                // not for visitors: the stream stays
                return;
            }
            $event->setResponse($data['renderer']->page($data['page'], [
                'title' => 'Welcome back',
                'body'  => $data['renderer']->template('myplugin/welcome', ['user' => $user]),
            ]));
        });
    }

The rules:

* **The first `Response` wins.** Once a listener has set a `Response`, a later listener cannot replace it or erase it by setting its default (`false`): the event is triggered with a rule for the response it keeps, and `setResponse()` leaves an acceptable one alone. A listener that sets anything else (a string, `false`, `null`) is replaced by a later one, and an answer that is no `Response` is ignored. Give a priority to a listener that must come first. Do not set the event's `forward()`: it sends a `Location` and ends the request, as for every event.
* **Draw through the renderer.** Use `$renderer->page()`, `redirect()`, `denied()`, `notFound()` or `gone()` and return what they return. Do not `echo`, `exit`, call `header()` or `drawPage()`: nothing a listener draws is sent or ended by it, so the page's headers, caching and `kernel.terminate` still apply. Set what the page is about on the context first (`$page->setOwner()`, `$page->setPermalink()`, `$page->addHeader('Last-Modified', ...)`).
* **Respect the viewer's access, in two steps.** The site's own rule runs first, before the event: a visitor of a private site (a walled garden) is refused with the 403 page and never reaches your listener, unless a plugin made the home route public (`addPublicRoute('Idno\Pages\Homepage')`; that makes the home route public, whatever is put there). Then your listener answers for the viewer: it must check that this viewer may read what it puts in place of the stream (`canRead()` on an entity) and, when they may not, set no `Response`, so that the ordinary home page is served. Answer neither a refusal (it tells the viewer the page exists) nor a redirect to `/` (it asks for the same page again, for ever). On a private site whose home route is public, a static page with public access is shown to a visitor and one that is not public is not.
* **Only the site's root is replaced, and only the home page's own route.** The event is triggered by the home page's controller for `/` (with any query, in any template type), not for `/content/<types>`, which stays the stream, nor for the feeds, the search and the tag pages. A page of yours that extends the deprecated `Idno\Pages\Homepage` shell and took the root with `hijackRoute()` is not replaced either: it asked to be the home page, and keeps it. A site in a subdirectory, and a request for `/index.php`, are the root.
* **A listener that throws fails the page**, as a page that throws does: the 500 page, with the exception reported once. A listener that answers something that is no `Response` is ignored.
* **The event is counted.** The site's statistics count `event.homepage/replace` on every request for the root, whether or not a listener answers.

The bundled StaticPages plugin works this way: `IdnoPlugins\StaticPages\Pages\Homepage` (a subclass of the shell that hijacked the root) is gone, and `IdnoPlugins\StaticPages\HomepageReplacement` answers the event. What changes for the page a static home page serves: the body class and the `page_class` of the page's events (`page/ready`, `page/head`, `page/get`) are `idno_pages_homepage` and `Idno\Pages\Homepage`, where they were `idnoplugins_staticpages_pages_homepage` and `IdnoPlugins\StaticPages\Pages\Homepage`: a theme that styled the home page by the old body class, or a listener that filtered on the old `page_class`, must use the new names. A chosen page the viewer may not read (private, in a group they are not in, a draft that is not theirs) now gives the ordinary home page; the old class redirected to `/`, which for a visitor was an endless redirect. A page that is gone, or is no static page, is unset when an administrator asks for the home page, and the stream is served with no redirect.

## Whether a request is secure

`Page::sslGatekeeper()` and `Config::hasSSL()` no longer redirect: `sslGatekeeper()` is deprecated and does nothing, and `hasSSL()` and the `force_ssl` and `ignore_ssl_gatekeeper` settings are gone. Redirect http to https in the web server or proxy.

`Page::isSSL()` and `ControllerPage::isSecure()` answer from one function, `Idno\Http\TrustedProxies::isSecure()`. A site that sets the boot setting `trusted_proxies` (the proxies whose `X-Forwarded-Proto` and `X-Forwarded-Port` are believed) gets Symfony's rule: the server's own `HTTPS`, or `X-Forwarded-Proto` from a listed proxy. A site that sets nothing gets the rule `isSSL()` always had (`HTTPS` `1` or `on`, port 443, or `X-Forwarded-Proto: https` from anyone), so a plugin that called `Page::isSSL()` sees no change there. The setting is never stored: `Idno\Core\Config` drops `trusted_proxies` from the stored settings. A plugin that reads `$_SERVER['HTTP_X_FORWARDED_PROTO']` or `HTTP_X_FORWARDED_PORT` itself decides for itself and should call `Page::isSSL()` instead.

## The static helpers of `Idno\Pages\Session\Login`

`Idno\Pages\Session\Login` is no page any more (it is a `final` class that holds the helpers below and nothing else; its page moved to `SessionController`) and `Idno\Pages\Session\Logout` is deleted. A plugin that extends either class stops the site booting until it is disabled. What a plugin of a single sign-on kind does is unchanged: `hijackRoute('/session/login', YourPage::class)` and `addRoute()` of the identical pattern still replace the login page, in every spelling of the address, because core still registers `/session/login` and `/session/logout` where it always did, with the placeholder `Idno\Legacy\ControllerRoute` in place of the classes. The events `login/success`, `login/failure`, `login/failure/nouser` and `logout/success` fire as before. What differs: a GET or HEAD of `/session/logout`, a PUT or DELETE of either address and a request with a malformed `Host` are the site's 404 page (a GET of the logout was an empty page); an XHR GET of the login page gets the headers of the same request that is not XHR, and an XHR logout is sent the caching lines of every XHR POST (two `Cache-Control` lines; it was one); the JSON `{"location": ...}` a signed request is given is sent as `application/json`; an XHR POST of either page with a missing or wrong form token is the site's 403 page (it ended with an empty answer), and a login field that is not text (`email[]=bob`) is a failed login, no longer the 500 page of a PHP error.

`Idno\Pages\Session\CurrentUser` is deleted too (a plugin that extends it stops the site booting until it is disabled); `/currentUser` is served by `CurrentUserController`, GET and POST as before, and core still registers it with `Idno\Legacy\ControllerRoute`, so `hijackRoute()` and `addRoute()` of the pattern keep working. A PUT or DELETE of it is the site's 404 page, and an XHR GET gets the headers of the same request that is not XHR.

`Idno\Pages\Account\Register` is deleted as well (a plugin that extends it stops the site booting until it is disabled); `/account/register` is served by `RegistrationController`, and core still registers it, public, with `Idno\Legacy\ControllerRoute`, so `hijackRoute()` and `addRoute()` of the pattern keep working. The events `user/register/validate` and `site/newuser` fire as before, in the same order (`site/newuser` inside the database step that saves the account and uses up the invitation). What differs: a JSONP request (`?_t=jsonp`) is answered as the HTML settings page, as every page under `/account` is, where it was the JSONP shell, a script any other site could load; an XHR GET gets the headers of the same request that is not XHR; an XHR POST with a missing or wrong form token is the site's 403 page; a PUT or DELETE and a request with a malformed `Host` are the site's 404 page. The page is drawn through `PageRenderer::pageInExactShell()`, in the site's own shell, and answers no `Content-Length`, as before.

`Idno\Pages\Account\Password` and `Idno\Pages\Account\Password\Reset` (the pages that ask for a password reset link and set the new password) are deleted too (a plugin that extends either stops the site booting until it is disabled); `/account/password` and `/account/password/reset` are served by `PasswordResetController`, and core still registers both, public, with `Idno\Legacy\ControllerRoute`, so `hijackRoute()` and `addRoute()` of the patterns keep working. The mail, its link and the events are as they were. What differs: an XHR GET gets the headers of the same request that is not XHR; an XHR POST with a missing or wrong form token is the site's 403 page; a request with a malformed `Host`, a PUT and a DELETE are the site's 404 page. Both forms are drawn through `PageRenderer::pageInExactShell()`, in the site's own shell.

`Login::sanitizeRedirectUrl($url)` is deprecated: call `Idno\Http\RedirectTarget::sanitize($url, $siteUrl)`, which takes the site's address as its second argument (`Idno::site()->config()->getDisplayURL()`) and needs no legacy application. `Login::throttleAttempt($key)` and `Login::throttleReset($key)` are deprecated: call `attempt($key)` and `reset($key)` of the `Idno\Security\LoginAttempts` service. `Login::throttleKeyFor($user)` is unchanged. They still work and give the same answers, with one change to the redirect rule: `RedirectTarget::sanitize()` (and so `Login::sanitizeRedirectUrl()`) now answers the site's address for an address with user information before the host (`https://user@site.example/`), which used to be kept, and makes an `http://` address of the site's own host `https://` (the rest kept) when the site is https: when either the configured `url` or the current request is. An `https://` address is never made `http://`. `RedirectTarget::sanitize()` takes the configured address as an optional third argument; `Login::sanitizeRedirectUrl()` passes it.

## Where file sessions are kept

A site whose sessions are PHP files (an SQLite site always) and whose PHP names no `session.save_path` now keeps them in `var/sessions/` (or `IDNO_SESSION_DIR`, or a private directory under the system's temporary directory), created for the web server's user only, with PHP's garbage collection on (`session.gc_probability` 1, `session.gc_divisor` 1000). A plugin that read or counted session files in the system's temporary directory must ask `session_save_path()` instead. Code that reads and writes `$_SESSION`, and a session handler a plugin supplies (`sessions_storage`), work as before: a handler is never given a directory. Only a web request makes the directory: a script that boots `Idno/start.php` from the command line keeps PHP's own `session.save_path` for its session, as before. Members of an affected site are signed out once by the upgrade. See `docs/install/upgrade.md`.

## Installation and onboarding

The installer and the onboarding pages are gone: what a plugin may have used of them is listed in [Upgrading Idno](../../install/upgrade.md#the-installer-and-onboarding). In short: the pages `Idno\Pages\Onboarding\*` (`/begin/...`) and the classes `Idno\Core\Installer`, `WebInstaller` and `CLIInstaller` are deleted; the template `shell/simple`, its partials and every template under `onboarding/` (and so any extension of them, such as `onboarding/connect/networks`) are gone, and `DefaultTemplate::sendSimpleShellHeaders()` with them: draw a page of your own in the ordinary shell (`drawPage()`). The event `site/firstadmin` is triggered by the installation's last step (or `php bin/console idno:admin:create`), no longer by `Idno\Pages\Account\Register`, which never makes an administrator. Code that created the first user by posting to `begin/register` uses the console command or the service `Idno\Install\FirstAdministrator`. A new administrator lands on `/admin/welcome/`.

## Values from a request in a search

A request can send an array where a page expects text (`email[]=x`, `email[$gt]=a`, a JSON object). Pass such a value to a finder only after checking it is a string: `Entity::getByID()`, `getByUUID()`, `getBySlug()`, `getByShortURL()`, `User::getByEmail()`, `getByHandle()`, `getByProfileURL()`, `UnfurledUrl::getBySourceURL()` and the `Invitation` finders now return `false` for anything else. A search array of your own (`getObjects()`, `getFromX()`, `get()`) whose value for a field is an array must be a map made only of `$not`, `$in`, `$lt` and `$gt`: a plain list, an empty array, an unknown operator or an operator whose operand it cannot use (an empty `$in`) makes the search find nothing (it used to be dropped, leaving the rest of the query to run); `$lt`, `$gt` and `$not` with `0` or `''` now compare, with one warning in the log. Write `['$in' => $list]` where you meant "any of these".

`Idno\Entities\Invitation` is readable by administrators only now. Read or change one inside `Invitation::unrestricted(function () { ... })` when a visitor's request needs it (the registration page does), and compare a code with `Invitation::validate($email, $code)`, which checks every invitation for the address with `hash_equals()`.

A page reads a field it means as one text with `$this->getTextInput('name', $default = '')` (`\Idno\Core\Input::text()`): the string or number the request sent, else the default, so an array is an empty field and a validation message and not a server error.

## Invitations that carry a role

`Idno\Entities\Invitation` has a role (`getRole()`, `setRole()`, `isForAdministrator()`), an expiry (`getExpiry()`, `isExpired()`, `renew()`), a link (`getLink()`) and `send()`, and `Invitation::check($email, $code)` answers `['invitation' => ..., 'problem' => '' | 'expired' | 'invalid']`. `validate()` and `getByEmailAndCode()` return only an invitation that can be used. An invitation is used with `consume()`, which claims it: of two callers at once only one is told true. A plugin must never make an administrator from anything a request says; the only registration that does is one on an invitation an administrator stored as an administrator's.

`Idno\Storage\RecordStore` has a new method, `claim(string $collection, string $id): bool`, which deletes a record and says whether this call removed it (`delete()` is true for an id that is not there). A class of yours that implements `RecordStore` adds it; `DataConcierge` has `claimRecord()` and `atomically(callable $work)` with fallbacks for a backend a plugin supplies (read then delete, and just running the work), so a backend class need not change.

## Deleting an account

`Idno\Entities\User::delete()` is a job in two stages. It first CLOSES the account (`User::close()`, `User::isClosed()`): marked as being deleted, its password, sessions, API key and IndieAuth tokens stop working, and the event `account/closed` is triggered once (listen to it to end a credential of your own: your plugin's token for the account, a subscription). Anything of yours that asks whether a user may sign in or act asks `isClosed()`; `Session::logUserOn()` and `refreshSessionUser()` refuse a closed account already. Then it removes what the account owns, one entity at a time, and the account last, only when nothing is left; with the asynchronous queue a worker does this (the event `account/remove`, run as nobody), otherwise it runs in the request for a bounded time and carries on after the response (a shutdown function, or the kernel's terminate; it runs once), and the administrator can continue it from the Users page. Every step is idempotent.

What it removes is every record of the entity collections whose `owner` is the account, of every class and whatever its access or publish status, except the site's own content. Your entity class is **site content** (it stays when the account that made it is deleted, owner unchanged) when you register it: `\Idno\Core\AccountContent::keep(MyClass::class)`, called from your plugin's `registerEventHooks()`. Core keeps access groups, invitations, link previews, queued events, remote users and objects, generic data items and the StaticPages plugin's static pages; no account is ever content. (Generic data items are kept because plugins use them for anything: a plugin that stores a member's own data in one deletes it itself, from a listener of `account/closed`.) A kept class stays in every listing and readable while its owner's account is closed; every other record of a closed account is left out of every finder, count and feed (`EntityRepository` asks `AccessContext::closedOwners()`) for everyone but an administrator (`find()` of code that ignores access still sees them; `count()` never ignores access, as before). The exclusion is the repository's: `db()->getRecords()` and `countRecords()` read raw records and are not filtered, so a plugin that lists through them shows a closed account's records. The reserved usernames are records of the class `Idno\Entities\ReservedHandle` (administrators only, in no listing). A class that is not kept is deleted through its own `delete()`, so your `delete` and `deleted` listeners and your `deleteData()` run for each entity, and the files you attached with `attachFile()` (and those your `getAttachedFileIDs()` names) are deleted. A listener of `delete` that answers false keeps the entity, and the account stays closed until it is deleted again. A record whose class no longer exists is removed as a record.

While an account is removed `\Idno\Core\Idno::announcementsSuppressed()` is true (it is also true during an import, as `importInProgress()` is): a listener of `delete` or `deleted` that tells another server, or a syndication target, that a post is gone must not do so then; the followers of an ActivityPub account are sent one `Delete` of the actor instead. `User::deleteContent($batch, $seconds)` now returns `'done'`, `'time'` or `'refused'` (it returned a boolean) and does not delete the account; `User::removeAccount()` does both and says `'removed'`, `'time'` (rows were removed and there is more), `'refused'` (nothing more could be removed: look at the log and at `account_removal` on the user) or `'busy'` (another job holds the claim). `Entity::deleteStoredFiles()` deletes every stored file of an entity. `EventQueue::enqueue()` takes `false` as the user to run as: nobody, whoever is logged in. An event that was queued to run as a member whose account has since been closed or deleted is dropped with a log line, not failed. `AccessContext` has two new methods, `closedOwners()` and `siteContentClasses()`. `Invitation::makesAnAdministrator()` is false for an inviter whose account is closed. The username of a deleted account is reserved (`AccountRegistry::handleIsReserved()`): a plugin that creates users checks it as it checks `User::getByHandle()`. `User::canBeDemotedOrDeletedBy()` and `whyNotRemovableBy()` say whether an administrator may delete or demote an account (never their own, never the last administrator's); `Page::mayDeleteRequestedEntity()` asks it, so a delete page of yours that calls it has the rule.

## A member's email address

`User::jsonLDSerialise()` (the schema.org data in the head of every profile and post page) no longer has an `email` key: a member's account email is private. A plugin that read `email` from it, or from a page's JSON-LD, must read the address from the user's own settings, or from the `mailto:` links the member lists in their profile (`profile.url`).

## Writing a mail

A mail is two short Twig files, `templates/email/<name>.html.twig` and `templates/email-text/<name>.txt.twig`, written with the same parts (`idno_include('parts/paragraph', {text: ...})`; the parts are `heading`, `paragraph`, `button`, `quote`, `rows` and `code`, and each escapes what it is given), and the shell of each puts them in the mail. The HTML file says what the mail is with `{% do mail_describe({subject: ..., preheader: ..., reason: ...}) %}`, and `$email->setBodyFromTemplate('your/name', $vars)` writes both bodies and the subject. Build every link from `site_url()`, never from the request. `setHTMLBodyFromTemplate()` and `setTextBodyFromTemplate()` still work, and a `.tpl.php` mail template of your plugin or theme still replaces core's; it is placed in core's shell. `Email::isConfigured()`, `failureKind()` and `explanation()` tell a page whether mail can be sent and why it was not.

## Sending webmentions from a content type

A content type that announces a post to the pages its text links to calls `\Idno\Core\Webmention::queueMentions($post->getURL(), $text)` after it saves, where `$text` is the post's text with its addresses made into links (`\Idno\Core\Idno::site()->template()->parseURLs(...)`). It queues the event `webmention/sendall`, so with the asynchronous queue the save returns without waiting for the other sites, and with the default queue the event runs at once. Calling `Webmention::pingMentions()` directly still works, but sends inside the request. Before announcing a change other than a save (a delete), ask `$post->announcesMentions()`: true only for a public post that is published, never for a draft.

## Where a post is, and who may be told

A post that has a position, a place name or an address (a check-in) may keep them from some readers. `\Idno\Common\Entity::locationFor($viewer)` says what a viewer (a member, or `null` for a visitor who is not signed in, which is also what any other server is) may be told: an array with `precise`, `latitude`, `longitude`, `placename` and `address`, the parts the viewer may not have empty. `location()` answers for whoever is signed in and `publicLocation()` for a visitor. A template, feed, JSON, KML, Markdown or federation code of yours that prints a post's position, place name or address must read them there, and not from `$post->lat`, `long`, `placename` or `address` (only an edit form reads those). Anything that outlives the request or leaves the site (a slug, a stored title, a message to another server, a webhook, a record on another service) is put together while the author is signed in, so it must use `getPublicTitle()` and `publicLocation()`, not `getTitle()` and `location()`. For every entity but a check-in the two answer the same as `getTitle()` and the stored fields.

The password recovery code is stored as its SHA-256. `\Idno\Entities\User::getPasswordRecoveryCode()` returns that hash, so code that compared it with a typed code must call `$user->passwordRecoveryCodeMatches($code)` instead.
